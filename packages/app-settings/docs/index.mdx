## Why this exists

Two separate problems, both caused by copies.

**One query, many field sets.** Every surface that renders a date needed
`publicAppSettings`, so several declared their own `query PublicAppSettings { … }` selecting
different fields. Apollo normalizes by operation, so two components asking for the same
operation with different selections make the cache thrash — one write drops the fields the
other needed and both refetch. `PUBLIC_APP_SETTINGS` here is the single document, and it
selects the union: date/time format, zone, time source, custom-clock anchor, server time,
birth-year bounds and draft retention. Adding a public setting means adding a field here, not
a second query.

**One formatter, many wrappers.** The formatting itself is not in this package — it lives in
`@duncit/datetime`, which the mobile app also uses. This package is only the Apollo adapter
that feeds admin settings into `createDateFormatter`. That split is what keeps mWeb and native
rendering the same wall-clock string (rule 27) even though native talks to the server through
`graphql-request` and has no Apollo at all.

## Use it

`portals/admin/src/components/DateField.tsx`, and every other portal date field:

```tsx
import { useDateFormat } from '@duncit/app-settings';

const fmt = useDateFormat();          // browser-local zone, 'hh:mm a' default
const fmtTz = useDateFormat({ timeZoneAware: true }); // admin's IANA zone, 'HH:mm'

fmt.date(row.created_at);   // configured date pattern
fmt.dayLabel(row.start_at); // Today / Yesterday / the pattern
fmt.dayKey(row.start_at);   // 'yyyy-MM-dd', for grouping
fmt.now();                  // respects the admin's time source
```

Mounting localization — `app/mweb/src/main.tsx` and `packages/shell/src/mountPortal.tsx` both
do exactly this:

```tsx
import { AppLocaleProvider } from '@duncit/app-settings';
import { MWEB_FALLBACK_FLAT } from './i18n/fallback';

<AppLocaleProvider fallback={MWEB_FALLBACK_FLAT}>
  <App />
</AppLocaleProvider>
```

## `useDateFormat()` vs `useDateFormat({ timeZoneAware: true })`

They are not interchangeable and the default is the *less* correct one for shared content.

- Default (`timeZoneAware` unset) formats in the **browser's** zone, default time pattern
  `hh:mm a`. Fine for "when did this row change on my screen".
- `{ timeZoneAware: true }` formats via `date-fns-tz` in the admin-configured `time_zone`
  (falling back to `Asia/Kolkata`), default time pattern `HH:mm`. This is what mWeb's
  `useDateFormat` in `app/mweb/src/utils/dateFormat.ts` passes, so a pod's start time reads
  the same for a host in Delhi and an attendee abroad.

Anything a *second* person also sees — pod times, slot times, event windows — must be
time-zone aware. All formatters return `''` for empty or unparseable input rather than
throwing, so no call site needs a guard.

## Sample data

The three server payloads these hooks read. All are real response shapes.

```ts
/** publicAppSettings — one operation for the whole monorepo. */
const publicAppSettings = {
  date_format: 'dd MMM yyyy',
  time_format: 'hh:mm a',
  time_zone: 'Asia/Kolkata',
  time_source: 'SERVER',
  custom_time: null,
  custom_time_set_at: null,
  server_time: '2026-07-28T09:42:11.000Z',
  min_birth_year: 1940,
  max_birth_year: 2010,
  draft_retention_days: 30,
};

/** publicFeatureFlags */
const publicFeatureFlags = [
  { key: 'shop.pod_shop',              enabled: true  },
  { key: 'pods.backout_keep_my_spot',  enabled: true  },
  { key: 'ads.self_serve_checkout',    enabled: false },
];

/** publicLocales */
const publicLocales = [
  { code: 'en-IN', label: 'English', english_label: 'English (India)', is_rtl: false, is_default: true,  sort_order: 1 },
  { code: 'hi-IN', label: 'हिन्दी',   english_label: 'Hindi (India)',   is_rtl: false, is_default: false, sort_order: 2 },
  { code: 'ar-AE', label: 'العربية',  english_label: 'Arabic (UAE)',    is_rtl: true,  is_default: false, sort_order: 3 },
];

const podStart = '2026-08-02T12:30:00.000Z';   // 18:00 IST
```

## Worked examples

Outputs below come from running the hooks with `useQuery` stubbed to return the payloads
above — the same technique the package's own tests use.

### `useDateFormat`

```ts
const fmt = useDateFormat({ timeZoneAware: true });

fmt.dateFormat                              // 'dd MMM yyyy'
fmt.timeFormat                              // 'hh:mm a'
fmt.timeZone                                // 'Asia/Kolkata'
fmt.clock.source                            // 'SERVER'

fmt.formatDate(podStart)                    // '02 Aug 2026'
fmt.formatTime(podStart)                    // '06:00 PM'
fmt.formatDateTime(podStart)                // '02 Aug 2026 · 06:00 PM'
fmt.dayKey(podStart)                        // '2026-08-02'
fmt.formatPattern(podStart, 'EEE d MMM, h:mm aaa')  // 'Sun 2 Aug, 6:00 pm'
fmt.formatDate(null)                        // ''
```

While the query is still in flight the hook returns a **working** formatter, not an empty
one — nothing renders blank on first paint:

```ts
// data === undefined
const bare = useDateFormat();
bare.dateFormat            // 'dd MMM yyyy'   (FALLBACK_DATE_FORMAT)
bare.timeFormat            // 'hh:mm a'
bare.timeZone              // 'Asia/Kolkata'
bare.formatDate(podStart)  // '02 Aug 2026'
```

### `useFeatureFlag`

```ts
useFeatureFlag('shop.pod_shop')             // true
useFeatureFlag('ads.self_serve_checkout')   // false
useFeatureFlag('chat.voice_notes')          // false — key absent on the server
useFeatureFlag('chat.voice_notes', true)    // true  — your default wins for an absent key

// while loading, with no cached data:
useFeatureFlag('shop.pod_shop')             // false
useFeatureFlag('shop.pod_shop', true)       // true
```

An unknown key and a still-loading query both return `defaultValue`. Default to `false` for
anything that must not flash on before the server confirms it.

### `useFeatureFlagState`

The same read, with the loading beat exposed — what a route gate needs. A gate that reads
only `useFeatureFlag` sees `false` on the first render after a reload and redirects a
bookmarked page away before the flags land; the Admin Auto Pods page did exactly that.

```ts
const { pending, enabled } = useFeatureFlagState('auto_pods');
if (pending) return null;                       // wait — the answer has not arrived
if (!enabled) return <Navigate to="/pods" />;   // decided: the feature really is off
```

### `useProductVisibility`

`is_product_visible` is the one system flag that owns every product surface — the Pod Shop
on a pod, the cart, the catalogue, brand and ShipRocket warehouse registration, product
orders and the E-commerce studio. It ships OFF, and the server refuses product operations
while it is off, so hiding a button is never the only thing holding the line.

```ts
const { pending, visible } = useProductVisibility();

// flags still in flight:
pending   // true
visible   // false  — nothing product-shaped ever flashes on

// server says is_product_visible: true
pending   // false
visible    // true
```

Read `visible` to SHOW or HIDE (false while loading is the answer you want). Wait on
`pending` before you REDIRECT — acting on the loading beat bounces every bookmarked
`/shop` link home even with the feature switched on:

```tsx
function RequireProducts({ children }: Readonly<{ children: JSX.Element }>) {
  const { pending, visible } = useProductVisibility();
  if (pending) return null;
  if (!visible) return <Navigate to="/" replace />;
  return children;
}
```

`PRODUCT_VISIBILITY_FLAG` is the key itself (`'is_product_visible'`), for a caller that
already has the whole flag map from `useFeatureFlags()`.

### `useTranslation`

```tsx
<LocaleProvider fallback={MWEB_FALLBACK} userLocale={user?.locale}>
  <App />
</LocaleProvider>
```

```ts
const { t, has, locale, isRtl, locales, setLocale } = useTranslation();

locale                    // 'hi-IN'  — from publicLocales + the user's saved locale
isRtl                     // false
locales.map((l) => l.code)// ['en-IN', 'hi-IN', 'ar-AE']
t('mweb.shop.title')      // 'पॉड शॉप' when translated, else the fallback bundle's 'Pod Shop'
has('mweb.shop.unknown')  // false
setLocale('ar-AE')        // switches instantly, persists locally, calls onLocaleChange
```

Selecting `ar-AE` also sets `document.documentElement.dir = 'rtl'` and `lang = 'ar-AE'` —
that effect is what actually flips the layout when an admin marks a locale RTL.

Outside a provider the hook still returns a working translator rather than throwing, so a
component rendered in a test or an error boundary never crashes:

```ts
const { t, locale, locales } = useTranslation(MWEB_FALLBACK);
locale     // 'en-IN'
locales    // []
t('mweb.shop.title')  // 'Pod Shop' — from the bundle you passed
```

Pass the bundle. Calling `useTranslation()` bare outside a provider renders raw keys.

## API

### Hooks

| Export | Signature | Default | Meaning |
| --- | --- | --- | --- |
| `useDateFormat` | `(options?: { timeZoneAware?: boolean }) => DateFormatter` | `timeZoneAware: false` | Formatter driven by `publicAppSettings`. |
| `useFeatureFlag` | `(key: string, defaultValue?: boolean) => boolean` | `false` | Returns `defaultValue` while loading and for unknown keys. |
| `useProductVisibility` | `() => { pending: boolean; visible: boolean }` | `{ pending: true, visible: false }` | The product kill switch. Hide on `visible`; wait on `pending` before redirecting. |
| `useTranslation` | `(fallback?: FlatCatalogue) => LocaleContextValue` | — | `{ t, has, locale, isRtl, locales, setLocale }`. Never throws. |

### Providers

| Component | Prop | Type | Required | Default | Meaning |
| --- | --- | --- | --- | --- | --- |
| `LocaleProvider` | `fallback` | `FlatCatalogue` | yes | — | The surface's bundled catalogue. |
| | `userLocale` | `string \| null` | no | — | The signed-in account's saved language; wins over a local choice. |
| | `onLocaleChange` | `(code: string) => void` | no | — | Wire to the `setMyLocale` mutation to persist server-side. |
| | `children` | `ReactNode` | yes | — | |
| `AppLocaleProvider` | `fallback` | `FlatCatalogue` | yes | — | Same, but reads `userLocale` from `useUserData()`. |
| | `children` | `ReactNode` | yes | — | Must sit inside a `UserProvider`. |

Locale precedence: local override → `userLocale` → `localStorage['duncit_locale']` →
`navigator.language` → the platform default.

### Operations

| Export | Operation | Selects |
| --- | --- | --- |
| `PUBLIC_APP_SETTINGS` | `query PublicAppSettings` | `date_format, time_format, time_zone, time_source, custom_time, custom_time_set_at, server_time, min_birth_year, max_birth_year, draft_retention_days` |
| `PUBLIC_FEATURE_FLAGS` | `query PublicFeatureFlags` | `key, enabled` |
| `PUBLIC_LOCALES` | `query PublicLocales` | `code, label, english_label, is_rtl, is_default, sort_order` |
| `PUBLIC_TRANSLATIONS` | `query PublicTranslations($locale: String!)` | `key, value` |

All four use `fetchPolicy: 'cache-first'`. Do **not** redeclare `PublicAppSettings` in a
surface selecting a different field set — same operation name, different selection, and
Apollo's normalized cache thrashes between them. That is why the non-date fields live in
this one document.

## No live preview

`AppLocaleProvider` and `LocaleProvider` render no markup of their own — they are context,
and the hooks return values rather than elements. The docs-site preview runtime mounts React
islands with no Apollo client, and every export here needs one, so a preview would have to
fake the very thing the package exists to do. The worked examples above run the real hooks
against the real payloads instead.

## `AppLocaleProvider` vs `LocaleProvider`

`LocaleProvider` is the primitive: it takes `fallback`, an optional `userLocale` and an
optional `onLocaleChange`. `AppLocaleProvider` is `LocaleProvider` pre-wired to
`useUserData().user?.locale` from `@duncit/user-context`, so the language follows the
**account** and not the browser.

Use `AppLocaleProvider` unless you are rendering above the `UserProvider` — it must sit inside
one. The bug it fixed is easy to reintroduce: the switcher already wrote `profile.locale`
server-side, but nothing read it back, so the same user on a new device silently got the
device language again.

Locale precedence is: in-session override → the signed-in user's saved language → the value in
`localStorage` (`duncit_locale`) → the device language → `en-IN`. The in-session override wins
so switching language is instant and does not wait on the profile write.

`LocaleProvider` also stamps `document.documentElement.dir` and `.lang`. `dir` is what actually
flips layout for a locale an admin marked RTL — without the provider mounted, marking a locale
RTL does nothing visible.

## `useTranslation` does not throw outside a provider

It returns a working translator built from the `fallback` you pass, so a component rendered in
a test or inside an error boundary shows real copy rather than raw keys — but only if the
fallback reaches it. Do not call `useTranslation()` bare at a call site. Each surface ships a
thin wrapper that supplies its bundle once, e.g. `packages/shell/src/i18n/useTranslation.ts`:

```ts
import { useTranslation as useSharedTranslation } from '@duncit/app-settings';
import { SHELL_FALLBACK_FLAT } from './fallback';

export function useTranslation() {
  return useSharedTranslation(SHELL_FALLBACK_FLAT);
}
```

A portal's own namespace comes from the `i18nFallback` it passes to `mountPortal`, which the
provider layers over the shell bundle. Never add `i18next` or a second `t()` (rule 38).

## Re-exports: import from here, not from the transitive package

The index deliberately re-exports the `@duncit/datetime` clock/formatter surface
(`createClock`, `createDateFormatter`, `resolveNow`, `TIME_SOURCES`, `toTimeSource`, …) and the
`@duncit/i18n` core (`createTranslator`, `MWEB_BUNDLE`, `SHELL_BUNDLE`, `WEBSITE_BUNDLE`,
`flattenCatalogue`, `missingKeys`, …). A portal that already depends on `@duncit/app-settings`
should import them from here rather than adding a second workspace dependency it would then
also have to add to a Dockerfile COPY line.

## Not for the mobile app

Apollo, `graphql`, `date-fns` and `date-fns-tz` are **peers** — the surface supplies them.
The native app has no Apollo client (`graphql-request`) and is not a consumer; it takes
`@duncit/datetime` and `@duncit/i18n` directly. Do not add this package to
`app/mobile-app/package.json` to reuse a hook — extract the shared part down into `datetime`
or `i18n` instead.
