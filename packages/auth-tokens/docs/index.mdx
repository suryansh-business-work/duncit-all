## Why this exists

mWeb builds a MUI theme; the mobile app builds a Tamagui theme. Both start from the same
brand palette, and before this package each held its own copy — `app/mweb/src/theme.ts` had
the hex scales inline, the mobile side had them again in its tailwind/NativeWind config. Any
brand tweak was two edits, and "two edits" reliably means one edit.

Now `packages/auth-tokens/tokens.json` is the only place a hex value is written.
`app/mweb/src/theme.ts` imports `{ brand, neutral, semantic, surface }` from here;
`app/mobile-app/tamagui.config.ts` imports `{ dark, light, typography }`. There is
no build step — it is JSON plus two three-line view modules.

## Use it

`app/mobile-app/tamagui.config.ts`:

```ts
import { dark, light, typography } from '@duncit/auth-tokens';

const brandLight = {
  background: light.bg,
  color: light.ink,
  borderColor: light.border,
  primary: light.primary,
  onPrimary: light.onPrimary,
  danger: light.error,
};
```

`app/mweb/src/theme.ts`:

```ts
import { brand, neutral, semantic, light, dark } from '@duncit/auth-tokens';

export const tokens = { brand, neutral, semantic };
const m = isDark ? dark : light; // m.primary = CTA fill, m.accent = red text, m.brand = decoration
```

A default export of the whole object also exists (`import tokens from '@duncit/auth-tokens'`),
but prefer named imports — they are statically analysable, so a bundler can drop the groups a
surface does not use.

## Contrast roles (WCAG 2.2 AA)

Every value above is chosen for a **role**, and `node scripts/verify-contrast.mjs` fails CI
when a pair drops under its threshold. Pick the token by what the colour is doing, not by how
red it should look:

| Role | Token | Guarantee |
| --- | --- | --- |
| A filled call to action | `primary` under `onPrimary` | white text 4.81:1; `primaryHover` / `primaryActive` are darker, never lighter |
| Red **text** — links, "See all", active tab, focus ring | `accent` | at least 4.5:1 on `bg`, `surface` and `soft` of its mode |
| A filled `accent` chip | `accent` under `onAccent` | 4.5:1 — dark ink in dark mode, where `accent` is light |
| Logo, illustration, decorative icon, large display heading | `brand` | none — it is the exact brand red `#f82c2e` and fails as body text (3.5:1 on `bg`) |
| Secondary text | `muted` | 4.5:1 on `bg`, `surface` and `soft` |
| A form field's outline | `inputBorder` | 3:1 against every ground (WCAG 1.4.11) |
| A divider or card hairline | `border` | none — decorative |
| Status text or a status fill | `success` `warning` `error` `info` under `onSemantic` | 4.5:1 as text on every ground and as a fill |

`#d92d2d` clears 4.5:1 on white but only 4.32:1 on the off-white `bg`, which is why red text
uses `accent` (`#c62226`) and not `primary`.

The mode-less `semantic` group is for a component that does not know its mode (an icon colour
passed to `@expo/vector-icons`, a chart stroke). No single colour can be 4.5:1 text on both a
light and a dark page, so each value is chosen to be 4.5:1 text on a white card, 4.5:1 under
white text as a fill, and 3:1 as an icon on every light and dark ground. Status **text** on the
page ground, or in dark mode, reads `light.*` / `dark.*` — which is what MUI's `palette.success`
and Tamagui's `$success` already resolve to.

## Worked examples

`primary` is the **CTA red** `#d92d2d` — the fill of every call to action, identical in both
modes, because white on it clears 4.81:1 where the brand red `#f82c2e` only reached 3.90:1.
Hover and press step darker in both modes (`#c62226` / `#b42323`) so white text stays above
4.5:1 in every state. `accent` is the red for text — links, the active tab, "See all" and the
focus ring: `#c62226` in light mode and `#ff4d4f` in dark mode, where red text on the
near-black cards needs the lift to clear 4.5:1. `brand` keeps the exact `#f82c2e` for the logo
and illustrations only. The page ground is a warm off-white (`#f2f3ef`) with borderless white
cards; dark mode is a near-black ground with hairline-bordered cards.

### mWeb (MUI)

```ts
import { dark, light } from '@duncit/auth-tokens';

const m = isDark ? dark : light;
const theme = createTheme({
  palette: {
    primary:    { main: m.primary, dark: m.primaryActive },  // '#d92d2d' / '#b42323'
    secondary:  { main: m.accent, contrastText: m.onAccent }, // '#c62226' red text
    error:      { main: m.error, contrastText: m.onSemantic }, // '#c62828'
    background: { default: m.bg, paper: m.surface },         // '#f2f3ef' / '#ffffff'
    text:       { primary: m.ink, secondary: m.muted },      // '#16181d' / '#62676f'
  },
});
```

### Native (Tamagui)

```ts
import { dark, light, typography } from '@duncit/auth-tokens';

const brandLight = {
  background:  light.bg,          // '#f2f3ef'
  color:       light.ink,         // '#16181d'
  borderColor: light.border,      // '#e3e5df'
  inputBorder: light.inputBorder, // '#7f8279'
  primary:     light.primary,     // '#d92d2d'
  accent:      light.accent,      // '#c62226'
  brand:       light.brand,       // '#f82c2e'  ← decoration only
  onPrimary:   light.onPrimary,   // '#ffffff'
  danger:      light.error,       // '#c62828'
};

const brandDark = {
  background:  dark.bg,           // '#0e1012'
  color:       dark.ink,          // '#f2f4f1'
  borderColor: dark.border,       // 'rgba(255,255,255,0.08)'
  inputBorder: dark.inputBorder,  // '#767b84'
  primary:     dark.primary,      // '#d92d2d'  ← identical to light
  accent:      dark.accent,       // '#ff4d4f'
  brand:       dark.brand,        // '#f82c2e'
  onPrimary:   dark.onPrimary,    // '#ffffff'
  danger:      dark.error,        // '#f87171'
};
```

Both surfaces read the same nine exports. If a colour on one screen disagrees with the other,
the fix is in `tokens.json` — not in the theme file that noticed it.

### The auth gradient

```ts
const [from, via, to] = auth.bgGradient.dark;   // '#0e1012', '#121417', '#0e1012'
// → linear-gradient(160deg, #0e1012 0%, #121417 55%, #0e1012 100%) — near-flat by design
```

Both gradients are fixed three-stop tuples (`[string, string, string]`), so a consumer can
destructure them without a length check.

## API

Nine named exports plus a default. Every one is a frozen data object — there are no
functions, no options and no defaults to pass.

| Export | Type | Contents |
| --- | --- | --- |
| `brand` | `ColorScale` | The Duncit red ramp, keys `50`–`900`. |
| `neutral` | `ColorScale` | Greys, keys `50`–`900`. |
| `semantic` | `SemanticColors` | `success`, `warning`, `error`, `info`, `secondary`, `accent`. |
| `surface` | `SurfaceColors` | `bg`, `paper`, `soft`, `border` (light-mode surfaces). |
| `light` | `ModeColors` | Light palette — 19 keys. |
| `dark` | `ModeColors` | Dark palette — the same 19 keys. |
| `auth` | `AuthVisuals` | `accent`, `avatars`, `avatarRing`, `bgGradient`, `cardGradient`, `fog`, `legal`. |
| `radii` | `Radii` | `sm`, `md`, `lg`, `xl`, `pill` (numbers, px). |
| `typography` | `Typography` | `fontFamily` plus six named `weight`s. |
| default | the whole object | All nine under one import. |

| Type | Shape |
| --- | --- |
| `ColorScale` | `Record<'50'\|'100'\|…\|'900', string>` |
| `ModeColors` | `bg, surface, soft, ink, muted, border, inputBorder, primary, primaryHover, primaryActive, onPrimary, accent, onAccent, brand, success, warning, error, info, onSemantic` — all `string` |
| `GradientPair` | `{ light: [string, string, string]; dark: [string, string, string] }` |
| `AuthVisuals` | `accent: string`, `avatars: [string,string,string]`, `avatarRing: string`, `bgGradient: GradientPair`, `cardGradient: GradientPair`, `fog: AuthFog`, `legal: { termsUrl, privacyUrl }` |
| `FogLayer` | `veil`, `edge`, `clear` — all `string` |
| `AuthFog` | `light: FogLayer`, `dark: FogLayer`, `mediaOpacity: number`, `edgeStop: number` |

## No live preview

Colour values, not components. The place to *see* these is the surface that consumes them —
mWeb, the native app, or the `@duncit/theme` preview for the console design system, which is
a separate palette (Nunito, `radius.sm: 6`) and not this one.

## The three files, and why the data is in JSON

| File | Read by |
| --- | --- |
| `tokens.json` | the only data. Every other file re-exports it. |
| `tokens.mjs` | Vite/Rollup (mWeb) and Metro (mobile runtime) via `exports.import` |
| `tokens.cjs` | Node build-time configs and Jest via `exports.require` |
| `tokens.d.ts` | `tsc` — the type surface (`ColorScale`, `ModeColors`, `AuthVisuals`, …) |

The data was moved into JSON to fix a real bundler failure: with the values written directly
in `tokens.cjs`, Vite's dev server threw *"does not provide an export named 'default'"*. A JSON
module has a clean default export in every toolchain, so both views just re-export it.

Do not add values to `tokens.mjs` or `tokens.cjs`. Add them to `tokens.json`, add the named
binding to the destructure in `tokens.mjs`, and declare it in `tokens.d.ts`.
`__tests__/tokens.test.ts` asserts the CJS and ESM views are identity-equal to the JSON, so a
group added to one and not the other fails there rather than in a bundle.

## Keep it zero-dependency and framework-free

`package.json` has no `dependencies` at all, and it must stay that way. The mobile app is a
**standalone npm project, not a pnpm workspace member** — it links this package with
`"@duncit/auth-tokens": "file:../../packages/auth-tokens"` and `metro.config.js` widens
`watchFolders` to `../../packages` specifically for it. A dependency added here would have to
resolve inside that isolated install, where the monorepo root `node_modules` is deliberately
not on the resolution path (mixing pnpm's React copy with the app's breaks the bundle).

For the same reason, nothing here may import React, MUI or Tamagui. It is data that both
theme layers consume, not a theme.

## Docker and CI

Both mobile Dockerfiles COPY this package explicitly —
`COPY packages/auth-tokens ./packages/auth-tokens` in `app/mobile-app/Dockerfile` and
`Dockerfile.android`, with matching allowlist entries in `Dockerfile.android.dockerignore`.
A `file:` dependency that is not COPYed fails the image build while passing locally. Adding a
new `@duncit/*` dependency to the mobile app means editing both Dockerfiles and the
dockerignore in the same commit.

`app/mobile-app/.eslintrc.js` turns `import/no-unresolved` off partly because of this — the
eslint import resolver cannot follow the `file:` dep in an isolated CI install. `tsc --noEmit`
is the authoritative import check there.

## `auth` is more than colours

`auth` carries the login-screen visuals: `accent`, a three-colour `avatars` tuple,
`avatarRing`, `bgGradient` / `cardGradient` (each with a `light` and `dark` three-stop tuple),
and `legal.termsUrl` / `legal.privacyUrl`. `app/mobile-app/src/components/LegalLinks` opens
those URLs directly. They are configuration, not business data — a legal URL change belongs in
`tokens.json`, not hardcoded next to a `Linking.openURL` call.

Note the gradients are typed as fixed-length triples (`[string, string, string]`). Adding a
fourth stop is a type change, not a data change.

### `auth.fog` — the haze over an admin's login backdrop

Branding lets an admin put a photo or a looping video behind the login screen, and whatever
they picked has to keep the heading, the subtitle and the legal line readable. `fog` is what
both apps draw over it, and it **follows the theme**: the flat scrim it replaced was always
dark, so light mode darkened the photo and then wrote near-black copy on top of it.

```ts
const fog = isDark ? auth.fog.dark : auth.fog.light;
// media at auth.fog.mediaOpacity (0.9)
// then a flat  fog.veil  over the whole frame
// then fog.edge → fog.clear → fog.clear → fog.edge at
//      0, edgeStop, 1 - edgeStop, 1  ← thicker where the logo and the version sit
```

`clear` is the same colour at zero alpha rather than the string `transparent`, because a
native gradient stop written as `transparent` fades through black on iOS. mWeb spends the
numbers as a CSS `linear-gradient`; native spends them as an `expo-linear-gradient` — same
picture, one source (rule 27).

## Coverage

`vitest.config.ts` sets 100/100/100/100 and, unusually, measures `tokens.mjs` and `tokens.cjs`
directly — there is no `src/` directory. The tests spot-check concrete values
(`brand[500] === '#ff5757'`, `radii.pill === 999`) as well as structure, so a token rename is
caught rather than silently shipped as a missing colour.
