An **Auto Pod** is a pod an admin writes without picking a venue, a host or a
club — the marketplace completes it. A venue accepts the offer and commits one
of its slots, then a host assigns themselves (pricing the pod and picking its
spots), then a club admin claims it for their club — **in that order**. The
moment all three have enrolled it becomes an ordinary pod.

This package is the MUI half of that: mWeb, the Partners portal and the Admin
console all render these components. The native app deliberately does **not**
import it — it keeps Tamagui twins over the same `@duncit/utils` logic (rule 40:
share the logic, never the UI).

## The three enrolments, venue → host → club admin

A fresh physical Auto Pod is visible to venue owners only. Once a venue has
fixed a slot it reaches hosts approved in its sub-category; once a host is on
it, club admins whose club carries it. A **VIRTUAL** offer has no venue, so it
reaches hosts first. `OPEN` means nobody has enrolled yet; `CLAIMING` means
at least one partner has; the last enrolment tips it into `MATERIALIZING` and
then `LIVE`. `AutoPodQueue` puts a role's own enrolments under that role's
heading — the venue's **Assigned slot**, the host's **Assigned Auto Pods**,
the club admin's **Final assigned Auto Pods** (`labels.assignedHeading(role)`).

Every card carries `AutoPodTicks`: **Venue Enroll**, **Host Enroll**, **Club
Admin Enroll**, always in that order. Each is amber and outlined while that
partner has yet to enrol, and turns green and filled the moment they do — so
the state of an offer reads at a glance. The order is presentation only: it is
the same chips whichever partner went first, so a card never changes width as
they enrol. A **VIRTUAL** offer (`row.pod_mode`) has no venue to enrol: it
draws two ticks, carries a "Virtual pod — no venue needed" line, and never
appears in a venue's queue.

The derivation itself is `autoPodTicks()` in `@duncit/utils`, so the Tamagui
twin draws exactly the same ticks from exactly the same rule. Below the
ticks the card says who is still missing — `labels.waitingFor(autoPodMissingRoles(row))`
— and which city the offer belongs to.

```tsx
import { AutoPodTicks } from '@duncit/auto-pods';
import { mwebAutoPodLabels } from '@duncit/utils';

<AutoPodTicks row={row} labels={mwebAutoPodLabels(t)} />;
```

## The first enrolment pins a city

An Auto Pod starts with no city (`row.location` is `null`, and the card reads
`labels.unpinned`). The **first** partner to enrol pins it to one admin Location
row (Country › State › City):

| Who enrols first | Where the city comes from |
| --- | --- |
| A venue | `venue.location_id` — the venue's own city |
| A club admin | `club.location_id` — the club's own city |
| A host | The city selected at the top of the Auto Pods page |

From then on only partners in that city are offered it, the card reads
`labels.pinnedTo(autoPodCityLabel(row.location))` ("In Bengaluru, Karnataka"),
and the server refuses a venue or club from anywhere else. A host has no venue
or club to bring a city with, which is why the host page's location filter is
load-bearing rather than cosmetic — see `HostClaimDialog` below.

## A role's queue

`AutoPodQueue` renders a whole role page: what still needs this partner, then
what they already enrolled in, using `splitAutoPods()` to divide them. The
caller supplies the button, because only the action differs per role.

The three queue queries take the **same** variables (`AutoPodQueueVariables`):
`location_id` narrows to offers pinned to that city **plus every unpinned
offer** (an offer with no city yet is everyone's to take), and `sub_category_id`
narrows a host's queue to one of their approved categories. `null` means no
narrowing, so one hook can drive all three pages.

```tsx
import { AutoPodQueue, HOST_AUTO_PODS, type AutoPodQueueVariables } from '@duncit/auto-pods';
import { mwebAutoPodLabels } from '@duncit/utils';

const variables: AutoPodQueueVariables = {
  location_id: locationId || null,
  sub_category_id: subCategoryId || null,
};
const { data, loading, error, refetch } = useQuery(HOST_AUTO_PODS, { variables });

<AutoPodQueue
  role="host"
  rows={data?.hostAutoPods ?? []}
  labels={mwebAutoPodLabels(t)}
  loading={loading}
  error={!!error}
  onRetry={() => refetch()}
  formatWhen={(iso) => formatDateTime(iso)}
  formatMoney={(n) => money(n)}
  renderAction={(row) => (
    <Button fullWidth variant="contained" onClick={() => setClaiming(row)}>
      {labels.assignMyselfCta}
    </Button>
  )}
  renderEarningsAction={(row) => (
    <AutoPodEarningsButton labels={labels} onClick={() => earnings.open(row)} />
  )}
  earnings={earnings.values}
/>;
```

## Potential earnings

Every card carries a **View Potential Earnings** control under its details and a
"You could earn …" line under its price. The figure is the one for the card's
own `role` — `autoPodRoleEarnings()` in `@duncit/utils` picks it — because the
three partners are paid for different things and a venue used to be shown the
HOST's payout by mistake:

| Role | The figure | Where it comes from |
| --- | --- | --- |
| Venue | `expected_venue_earnings` | Ticket price × the booked space's capacity — what the pod grosses at that space |
| Host | `expected_host_earnings` | The host's payout after every Finance deduction |
| Club Admin | `expected_club_earnings` | The club admin's cut of the same waterfall |

`useAutoPodEarnings()` holds what the viewer works out for themselves, keyed by
Auto Pod id, and the card prefers it over the server's number — it is what they
just typed. Nothing is saved: a potential earning is a partner asking "what if",
not a commitment.

`VenueEarningsDialog` lists the venue's published spaces (`autoPodVenueSpaces()`
falls back to the venue's scalar capacity as one unnamed space) and prices each
one the venue types a ticket price for, spelling the sum out —
"Potential Earnings (Ticket Price × Slots): ₹250 × 6 = ₹1,500".

`HostEarningsDialog` runs the **same calculator Step 4 of Create a Pod does**,
through `useHostProjection()`: a ticket price, a spots slider bounded by the
activity's minimum and the venue's capacity, and the server's own waterfall on
every change. `HostEarningsFields` is that block, and `HostClaimDialog` renders
it too — so the figure a host reads on a card is the figure they commit to.

```tsx
import {
  AutoPodEarningsButton,
  HostEarningsDialog,
  useAutoPodEarnings,
} from '@duncit/auto-pods';

const earnings = useAutoPodEarnings();

<HostEarningsDialog
  row={earnings.row}
  labels={labels}
  open={earnings.row !== null}
  onClose={earnings.close}
  formatMoney={(n) => money(n)}
  onEarnings={earnings.record}
/>;
```

## The filters at the top of every queue

Every queue page — venue, host and club — shows a **Location** filter at the
top; the host page additionally shows a **Category** filter.

- The location filter is the surface's own picker: mWeb opens the header's
  location picker, the portals render `AdminLocationSelect` from
  `@duncit/location`, native opens its `LocationDialog`. `AUTO_POD_LOCATIONS`
  is the active-locations query those pickers read when they need the list.
- `AutoPodCategoryFilter` is the host's category filter: an MUI select of the
  sub-categories **this host is approved in** (read through
  `MY_HOST_CATEGORIES_FOR_AUTO_POD`) with an "All my categories" option
  (`''`). A host approved in nothing sees the select disabled with
  `labels.noHostCategories`.

```tsx
import { AutoPodCategoryFilter } from '@duncit/auto-pods';

<AutoPodCategoryFilter
  value={subCategoryId}
  onChange={setSubCategoryId}
  labels={labels}
  size="small"
/>;
```

## The three dialogs

| Dialog | Role | What it collects |
| --- | --- | --- |
| `VenueAcceptDialog` | Venue | Which of the chosen venue's free slots — each priced as the venue would be paid |
| `HostClaimDialog` | Host | Step 4's calculator (`HostEarningsFields`): a ticket price and a spots slider bounded by the server's own limits, re-priced on every change — and, on a VIRTUAL offer, the meeting platform, link, start and end (`HostMeetingFields`); the template carries none of these |
| `ClubClaimDialog` | Club Admin | Which of their clubs (only category-matching ones) |

Accepting and picking a slot are **one** action: an acceptance with no date
would leave the pod nothing to run on. The slot is booked the instant the
accept succeeds and stays booked until the pod exists, so no ordinary pod can
take it in between.

The venue itself is chosen **above the queue**, with `AutoPodVenuePicker`: an
owner may run several venues, and the queue is what THAT venue could take (its
category and its city — `VENUE_AUTO_PODS` takes `venue_id`), so the picker
writes the venue's category under itself (`venueCategoryPath`) to say why the
list is what it is. `VenueAcceptDialog` takes that `venue` and asks only for
the slot, read from `AUTO_POD_VENUE_SLOTS`: the next few days (Pod Settings'
*Auto Pods — slot window*), nearest first, each carrying `venue_receives` —
what the venue is paid after Finance's deductions — and `viable`, false when
the pod's money could not cover it (`labels.slotNotViable`, and the button
stays shut). The chosen slot's pay shows as `labels.potentialEarning(amount)`.

Every card counts the offer down: `AutoPodCard` renders `AutoPodExpiryNote`
off `row.expires_at` (set on every list — Pod Settings' *Auto Pods —
assignment window* past the roll-out, or the *venue window* if that closes
sooner while no venue is on it) and says "Expires in 5h 12m 30s", ticking
once a second off the admin-configured clock; when it runs out with a role
still missing the server releases the offer, frees the venue's slot and the
host, and emails everyone who had enrolled.

`VenueAcceptDialog` and `ClubClaimDialog` refuse a venue / club outside the
pinned city when there is one, and say so (`labels.noVenueInCity(city)` /
`labels.noClubInCity(city)`) — the server would refuse the enrolment anyway,
so the dialog does not offer it.

The admin console's table draws the same enrolment derivation as a line —
`AutoPodDependencyTimeline`: Venue → Host → Club Admin, a green dot with the
partner's name where they have enrolled, an amber one where the offer is
still waiting. Given `onEnrolledClick(role)`, every green stop is a button
(`data-testid="auto-pod-dependency-<role>"`) — the admin's way into the venue,
the host or the club admin who took that place; a pending stop is never one.

Every card wears its mode — `labels.modePhysical` / `labels.modeVirtual` as a
chip beside the title — because a virtual offer waits on two partners and a
physical one on three. The template carries no price: until a host has set the
ticket price and spots (`autoPodPriced(row)` in `@duncit/utils`) the card says
`labels.pricedByHost` where the two chips would be, rather than "₹0".

`HostClaimDialog` **requires** `locationId` — the city selected at the top of
the host's page (`''` when none) — and takes an optional `locationLabel` for
the copy. On an unpinned offer it is the city the pod will be set to: the
button stays disabled and the dialog shows `labels.pickLocationFirst` until one
is selected, then `labels.willPinTo(locationLabel)` once it is. On a pinned
offer the selection is not sent at all; `autoPodHostNeedsLocation(row,
locationId)` in `@duncit/utils` is the one rule behind both.

```tsx
import { HostClaimDialog } from '@duncit/auto-pods';

<HostClaimDialog
  row={claiming}
  open={!!claiming}
  labels={labels}
  locationId={locationId}
  locationLabel={cityLabel}
  onClose={() => setClaiming(null)}
  onAssigned={() => refetch()}
  formatWhen={formatDateTime}
  formatMoney={money}
/>;
```

The dialog's two fields default to the template's numbers and re-read
`AUTO_POD_HOST_PROJECTION` on every change: the server prices the pod under
the host's own rates, the venue's slot price and the club admin's cut, and
answers with the spot limits too (`min_spots` is the activity's minimum,
`max_spots` the booked space's capacity). The lines under the fields are
`labels.projectionHost(amount)` and the three deductions; `viable` false
shows `labels.projectionNotViable` and keeps the button shut, because the
same waterfall is what `HOST_ASSIGN_AUTO_POD` would refuse.

## Withdrawing

**All three** partners may take their enrolment back while the offer is still
enrolling. Enrolments happen in any order, so a club admin is often not the last
one in — a club that opened the offer for itself is usually the first — and once
everyone needed IS on it the pod exists and the row is no longer pre-live, which
is what closes the door for every role at once.

`AutoPodWithdrawAction` is the Cancel under a role's assigned heading: it draws
nothing unless `autoPodWithdrawable(row, role)`, and opens
`AutoPodWithdrawDialog`, which says (in the product's own words) that the offer
depends on more partners than the one leaving and states the Account Health cost
— `row.withdraw_penalty_points`, Pod Settings' *Auto Pods — cancellation
penalty*, now sent on all three queues. Confirming runs
`VENUE_WITHDRAW_AUTO_POD`, `HOST_WITHDRAW_AUTO_POD` or
`CLUB_WITHDRAW_AUTO_POD`; the offer returns to that role's "Needs your action",
everyone else on it is told, and the penalty lands on the partner's own Account
Health (a venue's on its venue health too, since the owner is who the product
holds responsible).

```tsx
import { AutoPodWithdrawAction } from '@duncit/auto-pods';

<AutoPodQueue
  role="host"
  {...queue}
  renderAction={renderAssign}
  renderMineAction={(row) => (
    <AutoPodWithdrawAction row={row} role="host" labels={labels} onWithdrawn={refetch} />
  )}
/>;
```

## Races

Every enrolment is a single conditional write on the server, so simultaneous
claims have exactly one winner. The loser gets a `CONFLICT`, which each dialog
surfaces as `labels.claimedElsewhere` and the page clears by refetching — the
card simply leaves that queue.

## Copy

Labels come from `mwebAutoPodLabels(t)` (mWeb + native, `mweb.autoPods.*`) or
`shellAutoPodLabels(t)` (the MUI portals, `shell.autoPods.*`), both in
`@duncit/utils`. The two namespaces carry word-for-word identical values; they
cannot collapse into one because the server stores a row per key path.

## Opening one

Two consoles can open an Auto Pod, so the question of which kind lives here
rather than in either of them — but the **form is not here any more**. It is
`@duncit/pod-form` in `autoPod` mode: the same accordion form an ordinary pod
uses, with no club, venue, host, mode or date, and a required category field
in the club picker's place. See "Auto Pod mode" in that package's docs for
`useAutoPodEditorState`, `buildAutoPodInput` and the config to pass.

`PodKindChooser` is what a **New Pod** button asks first: two boxes, Normal Pod
or Auto Pod, each with its own icon and a sentence on who fills in the venue,
the host and the club. It only reports the choice — the caller opens the
matching editor route, because Admin and the Partners console submit through
different mutations. A surface with the `auto_pods` flag off skips it entirely
and opens its ordinary editor, rather than showing a one-sided question.

```tsx
import { PodKindChooser } from '@duncit/auto-pods';
import { shellPodKindLabels } from '@duncit/utils';

<PodKindChooser
  open={choosing}
  labels={shellPodKindLabels(t)}
  onClose={() => setChoosing(false)}
  onPick={(kind) => navigate(kind === 'AUTO' ? '/auto-pods/new' : '/pods/new')}
/>;
```

A Club Admin's Auto Pod is opened **for their club**: `createAutoPod(input,
club_id)` enrols that club at creation — pinning the offer to the club's city
— so it only ever waits on a venue and a host, and the category is fixed to the
club's (`lockCategory: true` in the form config shows it read-only).
