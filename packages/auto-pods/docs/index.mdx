An **Auto Pod** is a pod an admin writes without picking a venue, a host or a
club — the marketplace completes it. A venue accepts the offer and commits one
of its slots, then a host assigns themselves and a club admin claims it for
their club. The moment all three have enrolled it becomes an ordinary pod.

This package is the MUI half of that: mWeb, the Partners portal and the Admin
console all render these components. The native app deliberately does **not**
import it — it keeps Tamagui twins over the same `@duncit/utils` logic (rule 40:
share the logic, never the UI).

## The three enrolments

Every card carries `AutoPodTicks`: **Venue Enroll**, **Host Enroll**, **Club
Admin Enroll**, always in that order and always all three. Each is amber and
outlined while that partner has yet to enrol, and turns green and filled the
moment they do — so the state of an offer reads at a glance.

The derivation itself is `autoPodTicks()` in `@duncit/utils`, so the Tamagui
twin draws exactly the same three ticks from exactly the same rule.

```tsx
import { AutoPodTicks } from '@duncit/auto-pods';
import { mwebAutoPodLabels } from '@duncit/utils';

<AutoPodTicks row={row} labels={mwebAutoPodLabels(t)} />;
```

## A role's queue

`AutoPodQueue` renders a whole role page: what still needs this partner, then
what they already enrolled in, using `splitAutoPods()` to divide them. The
caller supplies the button, because only the action differs per role.

```tsx
import { AutoPodQueue, HOST_AUTO_PODS } from '@duncit/auto-pods';
import { mwebAutoPodLabels } from '@duncit/utils';

const { data, loading, error, refetch } = useQuery(HOST_AUTO_PODS);

<AutoPodQueue
  role="host"
  rows={data?.hostAutoPods ?? []}
  labels={mwebAutoPodLabels(t)}
  loading={loading}
  error={!!error}
  onRetry={() => refetch()}
  formatWhen={(iso) => formatDateTime(iso)}
  formatMoney={(n) => money(n)}
  renderAction={(row) => (
    <Button fullWidth variant="contained" onClick={() => setClaiming(row)}>
      {labels.assignMyselfCta}
    </Button>
  )}
/>;
```

## The three dialogs

| Dialog | Role | What it collects |
| --- | --- | --- |
| `VenueAcceptDialog` | Venue | Which venue, and which of its free slots |
| `HostClaimDialog` | Host | Nothing — confirms, and shows projected earnings |
| `ClubClaimDialog` | Club Admin | Which of their clubs (only category-matching ones) |

Accepting and picking a slot are **one** action: an acceptance with no date
would leave hosts and club admins nothing to enrol against. The slot is booked
the instant the accept succeeds and stays booked until the pod exists, so no
ordinary pod can take it in between.

## Races

Every enrolment is a single conditional write on the server, so simultaneous
claims have exactly one winner. The loser gets a `CONFLICT`, which each dialog
surfaces as `labels.claimedElsewhere` and the page clears by refetching — the
card simply leaves that queue.

## Copy

Labels come from `mwebAutoPodLabels(t)` (mWeb + native, `mweb.autoPods.*`) or
`shellAutoPodLabels(t)` (the MUI portals, `shell.autoPods.*`), both in
`@duncit/utils`. The two namespaces carry word-for-word identical values; they
cannot collapse into one because the server stores a row per key path.

## Opening one

Two consoles can open an Auto Pod, so both the question and the form live here
rather than in either of them.

`PodKindChooser` is what a **New Pod** button asks first: two boxes, Normal Pod
or Auto Pod, each with its own icon and a sentence on who fills in the venue,
the host and the club. It only reports the choice — the caller opens the
matching form, because Admin and the Partners console submit through different
mutations. A surface with the `auto_pods` flag off skips it entirely and opens
its ordinary editor, rather than showing a one-sided question.

```tsx
import { PodKindChooser } from '@duncit/auto-pods';
import { shellPodKindLabels } from '@duncit/utils';

<PodKindChooser
  open={choosing}
  labels={shellPodKindLabels(t)}
  onClose={() => setChoosing(false)}
  onPick={(kind) => (kind === 'AUTO' ? autoEditor.openCreate() : openNormalEditor())}
/>;
```

`AutoPodForm` is the template itself — title, category, description, images,
price, spots, occurrence, hashtags and payment terms, validated by
`autoPodSchema` against the same rules the server applies. It is deliberately
**not** `@duncit/pod-form`: that schema hard-requires a club, a venue, a host
and a slot, and an Auto Pod has none of them yet.

Two things are injected rather than imported, so this package does not take on
the picker's whole dependency tree:

| Prop | Admin passes | Club Admin passes |
| --- | --- | --- |
| `occurrences` | `OCCURRENCES` from `@duncit/pod-form` | the same list |
| `renderCategory` | the full `RhfAdminCategory` Super → Sub cascade | a disabled read-out of the club's own category |

A Club Admin's Auto Pod is opened **for their club**: `createAutoPod(input,
club_id)` enrols that club at creation, so the offer only ever waits on a venue
and a host, and the server fixes the category to the club's — which is why that
surface shows a read-out instead of a picker.

```tsx
import { AutoPodForm, toAutoPodInput } from '@duncit/auto-pods';

<AutoPodForm
  open={editor.open}
  initialValues={editor.initialValues}
  saving={editor.saving}
  error={editor.error}
  t={t}
  dismissLabel={shellAutoPodLabels(t).dismiss}
  occurrences={OCCURRENCES}
  renderCategory={(control) => <RhfAdminCategory control={control} name="category" />}
  hint={t('admin.autoPods.noVenueHostHint')}
  onClose={editor.close}
  onSubmit={(values) => save(toAutoPodInput(values))}
/>;
```
