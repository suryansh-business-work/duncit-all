## Why this exists

The same venue availability screen exists for three actors on two mutation sets. A venue
owner manages their own slots in the Partner console and, since the calendar came to mobile,
in mWeb — both wired to `createVenueSlots` / `updateVenueSlot` / `deleteVenueSlot`. An
operations user manages any venue's slots from the Onboarding portal, wired to the role-gated
`adminVenueSlots` / `adminCreateVenueSlots` / … equivalents.

The grid, the day-cell colour rules, the past/beyond-window disabling, the add-slot form and
the recurring dialog are identical for all of them. They were the copy. This package holds
them once, at two levels:

- **Prop-driven pieces** — `AvailabilityCalendar`, `DayDrawer`, `CalendarToolbar`,
  `CalendarLegend` — take slots and callbacks, never a client. The Onboarding portal composes
  these over its own admin operations.
- **The whole editor** — `VenueAvailabilityEditor` — is the page body a venue owner sees,
  Apollo wiring included, so the Partners console and mWeb mount one component rather than
  two copies of the same page.

The rules behind it (which slot is addable, what a recurring run creates) are not here at
all: they live in `@duncit/slots`, the framework-free package the native app already compiles,
and are re-exported from this one under their old names.

## The whole editor

```tsx
import { VenueAvailabilityEditor } from '@duncit/availability-calendar';

<VenueAvailabilityEditor
  venue={venue}                       // a `myVenues` row: id, venue_name, status, capacity, capacity_items, settings
  onVenueChanged={() => refetchVenues()} // after the dialog writes venue rules / auto-extend
/>;
```

It renders the toolbar, the calendar, the legend, the day drawer and the recurring dialog, and
owns: the view + anchor (anchored on **today**, so Day/Week open on the current period rather
than a past 1st), the `venueSlots` query over the active view's range, the three drawer
mutations followed by a refetch, the 60-day booking window (`MAX_FUTURE_DAYS` — Next disables
at its edge and later days render non-interactive), and the venue's holidays and spaces read
from the row you pass.

Two things it does on purpose, both learned the hard way:

- **The day drawer sorts space first, then time.** A venue with ten courts publishes ten slots
  for the same hour, and chronological order interleaves them into a list where no court's own
  day is readable. A venue with no named spaces sorts by time exactly as before.
- **`capacityItems` is memoised, and the dialog re-seeds on the spaces, not the query.** The
  recurring dialog seeds a price row per space and re-seeds when those rows change. A fresh
  array every render — or re-seeding whenever the cached venue was rewritten by saving a rule
  from inside the dialog — would wipe the prices the owner had already typed.

`EditorVenue` is the shape it reads. `settings` is `unknown` and read leniently through
`readVenueSettings`: a venue registered before settings existed carries none.

## Composing the pieces yourself

From the Onboarding portal's `VenueSlotAvailabilityTab.tsx`, which needs the admin operations:

```tsx
import {
  AvailabilityCalendar,
  DayDrawer,
  type NewSlotInput,
  type VenueSlotRow,
} from '@duncit/availability-calendar';

<AvailabilityCalendar
  month={month}
  slots={data?.adminVenueSlots ?? []}
  selectedDate={selectedDate}
  onSelect={setSelectedDate}
/>

<DayDrawer
  open={!!selectedDate}
  date={selectedDate}
  slots={slotsForSelected}
  onClose={() => setSelectedDate(null)}
  onCreate={handleCreate}          // (input: NewSlotInput, overwrite: boolean) => Promise<void>
  onToggleBlock={handleToggleBlock}
  onDelete={handleDelete}
  spaces={venue.capacity_items}    // [{ label: 'Court 1', capacity: 4 }, …]
/>
```

Every handler returns a promise; `DayDrawer` awaits it and keeps its own busy/error state, so
the page only has to fire the mutation and `refetch()`. `viewRange`, `periodLabel` and
`shiftAnchor` are the toolbar's arithmetic, exported so a composer can drive `CalendarToolbar`
the way the editor does.

## Spaces, and the overwrite the second argument buys

A venue that lists capacity items sells each one separately — "Court 1" and "Court 2" may hold
the same hour — so a slot always says which space it is for. Pass `spaces`; the add form shows
a picker defaulted to the first entry and rides the chosen space's `capacity` along with the
slot. Pass nothing and the venue is a single whole-venue space, exactly as before.

`onCreate`'s second argument is what makes a clash recoverable. The server rejects an
overlapping slot with the `CONFLICT` code; the form recognises it (`isSlotConflictError`),
keeps the rejected payload, and offers an **Overwrite** action on the error. Confirming it —
behind a dialog that names what is deleted — re-sends the same payload with `overwrite: true`,
which the editor maps to `on_conflict: 'REPLACE'` on `BulkCreateVenueSlotsInput`. It sends
`'FAIL'` otherwise: an accidental clash must stay a refusal, never a silent deletion. A booked
slot, or one holding a pending request, is never replaced by any mode.

## The recurring dialog

`RecurringAvailabilityDialog` is the rich one the Partner console always had, now shared: a
date range, the weekdays (with All / Weekdays / Weekends presets and the venue's weekly-offs
greyed), one or more daily windows — or **Whole day**, which books each eligible date entire —
a price per space, and what to do when a generated slot lands on a time the space is already
published for (`SKIP`, the default, or `REPLACE`, whose warning is part of the choice). Under
**Advanced settings** sit four accordions on one shared `AdvancedAccordion` shell:

| Accordion | Writes | Notes |
| --- | --- | --- |
| Venue rules | `updateVenueSettings({ rules })` | buffer, notice, advance cap (≤ 60), bookings per slot, the four toggles |
| Future availability | `updateVenueSettings({ auto_extend })` | a daily job rolls the **default** slot template forward; warns when there is none |
| Save as template | `createSlotTemplate` / `deleteSlotTemplate` | captures weekdays + first window + base price; "Use" applies one back |
| Bulk actions | `bulkDeleteVenueSlots` / `bulkUpdateVenueSlots` | delete, block, unblock or re-price every matching upcoming slot; booked ones are never touched; every action confirms first |

The preview bar under the form and the batch the Create button sends come from the **same**
`generateRecurringSlots` call (in `@duncit/slots`), so "Create 16 slots" is never a promise the
server receives differently. Overlap resolution runs on the server: the batch carries the
chosen `on_conflict` mode and comes back with whatever survived it — the client never reads
the calendar back and guesses.

```tsx
<RecurringAvailabilityDialog
  open={recurringOpen}
  onClose={() => setRecurringOpen(false)}
  venueId={venue.id}
  settings={venue.settings}
  capacityItems={capacityItems}
  venueCapacity={venue.capacity}
  onDone={async () => { await refetch(); }}
/>
```

`PreviewBar` is exported on its own — it is the one piece of the dialog a reader can look at
with a plain `PreviewSummary` in hand, which is what the live demo does.

## Worked examples

Rendered under jsdom, anchored on a "today" of 28 Jul 2026 (so the slots above sit two and
three days out), with `maxDate={addDays(today, 60)}`.

```tsx
<AvailabilityCalendar
  month={today}
  view="month"
  slots={venueSlots}
  selectedDate={new Date('2026-07-30')}
  onSelect={setSelectedDate}
  holidays={['2026-08-02']}
  maxDate={addDays(startOfDay(new Date()), 60)}
/>
```

```text
weekday header : Sun Mon Tue Wed Thu Fri Sat
cells rendered : 35            ← 5 rows; the grid stops early when the month is covered
cell "30"      : "30 1A 1P 1B"   aria-disabled=false  tabindex=0
cell "31"      : "31 1×"         aria-disabled=false  tabindex=0
cell "28"      : (28 Jun, past)  aria-disabled=true   tabindex=-1
```

So the badges are counts, not flags: a day with three slots in three states renders `1A`,
`1P` and `1B` side by side. A `BLOCKED` slot shows as `1×`. A day with no slots renders no
badges at all. Past days — and days after `maxDate` — carry `aria-disabled="true"` and
`tabIndex={-1}`, so they are skipped by keyboard navigation, not merely greyed.

`DayDrawer` for 30 Jul, given those first three slots:

```tsx
<LocalizationProvider dateAdapter={AdapterDateFns}>
  <DayDrawer
    open
    date={new Date('2026-07-30')}
    slots={venueSlots.slice(0, 3)}
    onClose={close}
    onCreate={handleCreate}
    onToggleBlock={handleToggleBlock}
    onDelete={handleDelete}
  />

```

```text
Availability
Thursday, 30 Jul 2026

Existing slots
  09:00 AM – 11:00 AM   ₹1500  AVAILABLE  Studio A — 20 seats     [Block] [Delete]
  12:00 PM – 02:00 PM   ₹1500  PENDING    Requested by pod: Weekend Pottery Pod
                                          Awaiting your decision — approve or decline it
                                          under Slot Requests.
  06:00 PM – 08:00 PM   ₹2200  BOOKED     Booked by pod: Sunset Sound Bath

Add availability
  Whole day · Start date · Start time · End date · End time · Price (₹) · Notes (optional)   [Add slot]
```

Only the `AVAILABLE` row has action buttons. `PENDING` and `BOOKED` are locked — there is no
Block and no Delete on them, which is the rule that stops a slot being deleted out from under
a live booking request.

Two things this output makes concrete. `DayDrawer` and the recurring dialog render MUI X
pickers, so they **must** sit under a `LocalizationProvider` — without one they throw *"Can not
find the date and time pickers localization context"*. And the drawer renders inside a MUI
`Drawer` portal, so it is not in the calendar's DOM subtree.

### `useVenueSlots`

`useVenueSlots(venueId, range)` is the editor's Apollo wiring on its own: `{ slots, pending,
error, refetch, create, toggleBlock, remove }`. `create(input, overwrite)` maps `overwrite` to
`on_conflict` exactly as described above.

### Query documents

`VENUE_SLOTS`, `CREATE_VENUE_SLOTS`, `UPDATE_VENUE_SLOT`, `DELETE_VENUE_SLOT`,
`UPDATE_VENUE_SETTINGS`, `MY_SLOT_TEMPLATES`, `CREATE_SLOT_TEMPLATE`, `DELETE_SLOT_TEMPLATE`,
`BULK_DELETE_VENUE_SLOTS`, `BULK_UPDATE_VENUE_SLOTS` — the owner-side operations, exported so a
test can mock them and a host can refetch them. `VENUE_SETTINGS_FRAGMENT` is the `settings { … }`
selection those venue documents splice in; the Partners `myVenues` query imports it from here so
the calendar and the venue row can never disagree about which settings exist.

### Draft validation

The add-slot form judges its draft with one pure function, which lives in `@duncit/slots` and
is re-exported here so the portals that already import it keep compiling.

| Export | Signature | Meaning |
| --- | --- | --- |
| `checkSlotDraft` | `(draft: SlotDraft, now: Date) => { start: Date; end: Date } \| SlotIssueCode` | The window the draft asks for, or the ONE thing wrong with it. |
| `isDraftIncomplete` | `(code: SlotIssueCode) => boolean` | True for `pickDates` / `pickSlotTimes`. |
| `minTimeOn` / `minEndTime` | `(…, now) => Date \| undefined` | The picker bounds. |
| `slotIssueMessage` | `(code, t) => string` | Literal `availability.*` keys — the namespace every surface ships. |
| `MAX_FUTURE_DAYS` | `60` | Mirrors the server cap in `validateSlotWindow`. |

### Types

| Type | Shape | Notes |
| --- | --- | --- |
| `VenueSlotRow` | `{ id, venue_id, start_at, end_at, whole_day?, price, space_label?, capacity?, status, booked_by_pod_id, booked_pod_title, notes, created_at }` | `space_label` / `capacity` are optional so a row without spaces stays assignable. |

## `month` is the anchor, `selectedDate` only highlights

`AvailabilityCalendar` derives the visible cells from **`month`**, not from `selectedDate`:

- `view="month"` → the 6×7 grid around `startOfMonth(month)`
- `view="week"` → the seven days of `startOfWeek(month)`
- `view="day"` → the single day `month`

So in week and day view the host must move `month` itself — `shiftAnchor` is that step. The
editor keeps a single `anchor` state and shifts it by month / 7 days / 1 day per the view.
`selectedDate` does nothing but draw the selected cell and open the drawer.

## Day badges are `A` / `P` / `B` / `×`

`AVAILABLE`, `PENDING`, `BOOKED`, `BLOCKED`. **`PENDING` means a host's booking request is
waiting on the venue's approval** — it is not "draft". `DayDrawer` treats `BOOKED` and
`PENDING` as locked: you cannot block or delete them from the day editor, because a pending
request must be decided in Slot Requests instead. Do not add an escape hatch here; deleting a
slot out from under a live request is the bug that rule exists to prevent.

## A slot the venue could never have offered

A venue owner opening today's cell at 2:30pm could, until this was fixed, type 9:00–10:00 and
press Add. The server refused it and so did the form — but only after the click. Availability
that has already elapsed is not a formatting mistake to report; it is a value that should never
have been offered. So the rule is enforced three times over: the pickers refuse it
(`minTimeOn` / `minEndTime`), the form re-judges every 30 seconds against a live clock
(`checkSlotDraft`) and re-checks once more at submit, and the server still decides. Whole-day is
exempt from the past check because `wholeDayWindow` has already clamped its start off a
midnight that has gone by.

## Localization

Every sentence here is an `availability.*` key from `packages/i18n/src/bundles/availability.ts`
— a namespace of its own rather than the portal shell's, because mWeb ships `mweb.*` and would
have printed raw keys the moment it opened the calendar offline. All three surfaces (the
shell, mWeb, native) ship that bundle, so one copy renders everywhere (rules 27 + 38).

## Constraints

No third-party runtime dependencies; MUI, `@mui/x-date-pickers`, `date-fns`, React, `react-dom`,
`@apollo/client` and `graphql` are peers supplied by the consuming surface. The workspace deps
are `@duncit/slots` (the rules), `@duncit/datetime` (admin-configured date/time formats),
`@duncit/app-settings` (`useTranslation`), `@duncit/buttons` and `@duncit/dialogs` (the shared
confirm — rule 12).

The prop-driven pieces still take no client, which is what lets the Onboarding portal — on
entirely different, role-gated operations — keep sharing them. Only `VenueAvailabilityEditor`,
`useVenueSlots` and the recurring dialog's accordions reach for Apollo, and they do so through
the owner-side documents exported above.

This is a web/MUI package. The native app renders the same calendar through its own Tamagui
view, on the same `@duncit/slots` rules.

## Coverage

`vitest.config.ts` sets 100/100/100/100 on `src/**` (barrels excluded) under `jsdom`. The
branchy helpers — `cellColors`, `cellShape`, `buildCells`, the locked-status rules — are why the
components are decomposed into module-scope `DayCell` / `DayHeader` / `DayBadges` / `CountBadge`
sub-components rather than nested ternaries. Keep new branches in named helpers so they stay
testable without rendering the whole grid.
