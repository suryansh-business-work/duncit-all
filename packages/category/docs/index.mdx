## Why this exists

Clubs, venues, products, surveys and challenges all classify against the same admin-managed
category tree, and each of them used to own a pair of dependent `<Select>`s plus its own
`query { categories { … } }`. Two costs followed: every screen re-implemented the cascade rules
(clearing the sub when the super changes, narrowing subs by the middle level), and each one
persisted a slightly different subset of ids — so a club and a venue that were "the same
category" did not always agree.

`AdminCategorySelect` emits the **whole** `AdminCategoryValue` — all three ids *and* all three
names — regardless of which fields a given form persists. That is what stops the drift: the
middle `CATEGORY` level is always resolved from the tree even when the caller only stores
`super_id` and `sub_id`.

## Use it

Plain, from `portals/onboarding/src/pages/surveys/ScopePicker.tsx` and the venue sections:

```tsx
import { AdminCategorySelect, EMPTY_CATEGORY, type AdminCategoryValue } from '@duncit/category';

<AdminCategorySelect
  value={value ?? EMPTY_CATEGORY}
  onChange={setValue}
  legend="Category"
  hint="Venues auto-match to this club by location + category."
  required
/>
```

Inside a react-hook-form, one category:

```tsx
import { RhfAdminCategory } from '@duncit/category';

<RhfAdminCategory control={control} name="category" required size="medium" />
```

`RhfAdminCategory` stores the entire `AdminCategoryValue` object at `name` — not an id. Your Zod
schema must model the object.

### Several categories in one field — `RhfAdminCategoryRows`

A venue hosts pods in several categories, a product sells in several: the field is then an ARRAY of
`AdminCategoryValue`, primary first, and the control is a repeatable row of the same picker. Do not
hand-roll `useFieldArray` around `RhfAdminCategory` again — two screens had, and a third and fourth
were about to. From `portals/partners-app/src/pages/register-venue-page/sections/VenueDetailsSection.tsx`:

```tsx
import AddIcon from '@mui/icons-material/Add';
import DeleteOutlineIcon from '@mui/icons-material/DeleteOutlined';
import { DuncitButton, DuncitIconButton } from '@duncit/buttons';
import { RhfAdminCategoryRows } from '@duncit/category';

<RhfAdminCategoryRows
  control={control}
  name="venue_categories"                 // AdminCategoryValue[] — never empty in the form's defaults
  testId="venue-categories"
  direction={{ xs: 'column', md: 'row' }}
  required
  disabled={locked}                       // read-only rows: no add, no remove
  max={config.category_limit}             // from the server — never a number written here
  legend={t('partners.registerVenuePage.categoriesLegend')}
  hint={t('partners.registerVenuePage.categoriesHint')}
  labels={{
    add: t('partners.registerVenuePage.categoryAdd'),
    remove: (n) => t('partners.registerVenuePage.categoryRemove', { vars: { n } }),
    row: (n) => t('partners.registerVenuePage.categoryRow', { vars: { n } }),
    primary: t('partners.registerVenuePage.categoryPrimary'),
    duplicate: t('partners.registerVenuePage.categoryDuplicate'),
    maxReached: categoryLimitMessage(t, config.category_limit),
  }}
  icons={{ add: <AddIcon />, remove: <DeleteOutlineIcon /> }}
  components={{ Button: DuncitButton, IconButton: DuncitIconButton }}
/>
```

The package has no copy and no icon set of its own, so every word is a `labels` entry the calling
surface translates and both icons are passed in. `primary`, `duplicate`, `row` and `maxReached` are
optional: `list-products/CategoryRows.tsx` passes only `add` and `remove`, because a product has no
primary category. The Zod half of the same rules uses the same pure helpers, so the schema and the
field cannot disagree about which row is the repeat:

```ts
import { duplicateCategoryRows, isCompleteCategory } from '@duncit/category';

z.array(categoryRowSchema)
  .min(1, t('…categoryRequired'))
  .max(categoryLimit, categoryLimitMessage(t, categoryLimit))
  .superRefine((rows, ctx) => {
    const duplicates = duplicateCategoryRows(rows);
    rows.forEach((row, index) => {
      if (!isCompleteCategory(row)) ctx.addIssue({ code: 'custom', path: [index], message: t('…categoryIncomplete') });
      else if (duplicates.has(index)) ctx.addIssue({ code: 'custom', path: [index], message: t('…categoryDuplicate') });
    });
  });
```

Put a row's issue at `path: [index]` (the row, not `sub_id` inside it): the row's picker shows
`fieldState.error.message` on its Sub level, and an issue filed one level deeper has no message there,
so the picker falls back to the bare word "Required". A list-level issue (`min` / `max`) is announced
under the rows in a `role="alert"`.

## Worked examples

### The option builders

```js
superOptions(categories)
// [ { value: '…d02', label: 'Fitness' },
//   { value: '…d01', label: 'Food & Drink' } ]        ← sorted by label, not by tree order
```

Every builder sorts with `localeCompare`, so "Fitness" precedes "Food & Drink" regardless of how
admin ordered them. Do not re-sort at the call site.

```js
categoryOptions(categories, '66f1a2b3c4d5e6f708192d01')   // under Food & Drink
// [ { value: '…d11', label: 'Baking' },
//   { value: '…d12', label: 'Coffee' } ]

categoryOptions(categories, '')                            // no super chosen ⇒ every middle
// [ { value: '…d11', label: 'Baking' },
//   { value: '…d12', label: 'Coffee' },
//   { value: '…d13', label: 'Running' } ]
```

### `subOptions` and the skip-the-middle fallback

```js
subOptions(categories, '66f1a2b3c4d5e6f708192d11', '66f1a2b3c4d5e6f708192d01')  // middle = Baking
// [ { value: '…d34', label: 'Cake Decorating' },
//   { value: '…d33', label: 'Sourdough' } ]

subOptions(categories, '', '66f1a2b3c4d5e6f708192d01')   // super only ⇒ every sub under it
// [ { value: '…d34', label: 'Cake Decorating' },
//   { value: '…d35', label: 'Latte Art' },              ← from Coffee, the other middle
//   { value: '…d33', label: 'Sourdough' } ]

subOptions(categories, '', '')                            // nothing chosen ⇒ every sub
// [ 'Cake Decorating', 'Latte Art', 'Sourdough', 'Trail Running' ]
```

The middle row is the one that makes the flow work: a user can open the Sub dropdown straight after
picking a super and still land on a complete value, because picking the sub back-fills the middle
from its `parent_id`. Pass `strict` to the picker to switch that off: the Sub level then stays
locked until a middle Category is chosen, which is what a filter row wants.

### `buildCategoryValue(categories, superId, subId)`

Rehydrating a Club that stored only `super_category_id` and `category_id`:

```js
buildCategoryValue(categories, '66f1a2b3c4d5e6f708192d01', '66f1a2b3c4d5e6f708192d33')
// {
//   super_id:      '66f1a2b3c4d5e6f708192d01', super_name:    'Food & Drink',
//   category_id:   '66f1a2b3c4d5e6f708192d11', category_name: 'Baking',   ← derived, never stored
//   sub_id:        '66f1a2b3c4d5e6f708192d33', sub_name:      'Sourdough'
// }
```

When the sub has since been deleted from admin, the super survives and everything below it empties —
the value does **not** collapse to `EMPTY_CATEGORY`:

```js
buildCategoryValue(categories, '66f1a2b3c4d5e6f708192d01', 'deleted-id')
// {
//   super_id: '66f1a2b3c4d5e6f708192d01', super_name: 'Food & Drink',
//   category_id: '', category_name: '', sub_id: '', sub_name: ''
// }
```

Note the asymmetry: an unknown **super** id is passed through into `super_id` (with an empty
`super_name`), while an unknown **sub** id is dropped to `''`. A Zod rule that requires `sub_id` is
what catches a re-parented or deleted category on the next save.

### `EMPTY_CATEGORY`

```js
{ super_id: '', super_name: '', category_id: '', category_name: '', sub_id: '', sub_name: '' }
```

Always spread it (`{ ...EMPTY_CATEGORY }`) when seeding a `useFieldArray` row — the module-level
object is shared, and appending it directly makes every row the same object.

## Props / API

### `<AdminCategorySelect>` — `AdminCategorySelectProps`

| Prop | Type | Required | Default | Meaning |
| --- | --- | --- | --- | --- |
| `value` | `AdminCategoryValue` | yes | — | The whole structured value — all three ids and names. |
| `onChange` | `(value: AdminCategoryValue) => void` | yes | — | Receives the full value on every pick. |
| `fields` | `CategoryLevel[]` | no | `['super','category','sub']` | Which levels render. `'super'` must stay in the list or the rest never unlock. |
| `required` | `boolean` | no | `false` | Marks every rendered level required. |
| `disabled` | `boolean` | no | `false` | Disables all levels. |
| `size` | `'small' \| 'medium'` | no | `'small'` | MUI size passed to each `Autocomplete`. |
| `direction` | `StackProps['direction']` | no | `'column'` | Stack direction; accepts MUI's responsive object (`{ xs: 'column', md: 'row' }`) so three levels sit in a row on a desktop and stack on a phone. |
| `labels` | `Partial<Record<CategoryLevel, string>>` | no | Super Category / Category / Sub Category | Per-level label overrides. |
| `errors` | `Partial<Record<CategoryLevel, string>>` | no | `undefined` | Per-level error text. |
| `legend` | `string` | no | `undefined` | Setting it wraps the fields in a `<Fieldset>`. |
| `hint` | `string` | no | `undefined` | Fieldset hint — say *why* the category matters. |
| `strict` | `boolean` | no | `false` | Sub unlocks only after the middle Category is chosen — no skip-the-middle. Filters use it (Admin > Pods); forms keep the default so a host can pick a sub straight after the super. |

### `<RhfAdminCategory>`

Takes every `AdminCategorySelect` prop except `value`, `onChange` and `errors`, plus:

| Prop | Type | Required | Meaning |
| --- | --- | --- | --- |
| `control` | `Control<T>` | yes | The RHF control. |
| `name` | `Path<T>` | yes | Field holding the **whole** `AdminCategoryValue` object. |
| `subError` | `string` | no | Sub-level error text the form's own state does not carry (a rows field's "already added"). Wins over the field's error. |
| `onValueChange` | `(value: AdminCategoryValue) => void` | no | Called after a pick is written to the form — for a caller that re-validates as the value changes. |

It renders `fieldState.error.message` on the **sub** level only, and falls back to `EMPTY_CATEGORY`
when the field value is nullish.

### `<RhfAdminCategoryRows>` — `RhfAdminCategoryRowsProps<T>`

Takes every `AdminCategorySelect` prop except `value`, `onChange`, `errors`, `labels`, `legend` and
`hint` (so `required`, `disabled`, `size`, `direction`, `fields`, `strict` reach every row), plus:

| Prop | Type | Required | Default | Meaning |
| --- | --- | --- | --- | --- |
| `control` | `Control<T>` | yes | — | The RHF control. |
| `name` | `ArrayPath<T>` | yes | — | Field holding `AdminCategoryValue[]`, primary first. A `useFieldArray`. |
| `labels` | `AdminCategoryRowsLabels` | yes | — | `add: string`, `remove: (position) => string` — and, optional, `row: (position) => string` (names each row's group), `primary` (marks row 1), `duplicate` (flags a repeated sub category), `maxReached` (note under a full list). `position` counts from 1. |
| `icons` | `{ add: ReactNode; remove: ReactNode }` | yes | — | The two icons, from the surface's own set. |
| `min` | `number` | no | `1` | A row's remove button is disabled at or below this many rows. |
| `max` | `number` | no | no cap | The add button is disabled at this many rows. |
| `disabled` | `boolean` | no | `false` | Read-only rows: every dropdown disabled, no add button, no remove buttons. |
| `levelLabels` | `Partial<Record<CategoryLevel, string>>` | no | the picker's | Per-level label overrides for every row (the picker's own `labels`). |
| `legend` / `hint` | `string` | no | `undefined` | A legend wraps the rows in a `<Fieldset>`. |
| `components` | `{ Button?: typeof Button; IconButton?: typeof IconButton }` | no | MUI's | The surface's own buttons — `DuncitButton` / `DuncitIconButton`. |
| `testId` | `string` | no | `'category-rows'` | Prefix of every test id below. |
| `onRowChange` | `(index: number, value: AdminCategoryValue) => void` | no | `undefined` | Called after a row's pick is written to the form — e.g. `trigger(name)` once the list has failed validation. |

Test ids, with the default prefix: `category-rows` (the rows' container), `category-rows-row-N` (row
`N`, from 0), `category-rows-primary` (the primary mark), `category-rows-remove-N`,
`category-rows-add`, `category-rows-error` (the list-level error) and `category-rows-max` (the limit
note).

What it does not do: it never seeds a row. An empty field renders no rows, so give the form's
defaults one `{ ...EMPTY_CATEGORY }` (a spread copy — rows must not share an object). Removing a row
moves focus to the add button, because the button that had focus is gone.

| Export | Signature / value | Returns |

## Live preview

No live preview yet. The blocker is specific: `AdminCategorySelect` calls `useAdminCategories()`
internally, so a mounted island with no Apollo client in scope throws, and one with a real client
would hit the production API from a docs page. Neither is acceptable.

`docs-site` has the `<Preview>` island runtime; what it needs next is a `MockedProvider` wrapper
seeded with `ADMIN_CATEGORIES` → the `categories` array above. `ADMIN_CATEGORIES` is exported from
this package for exactly that reason. Once the wrapper exists the preview is a three-line island,
and the reader gets to *see* the cascade unlock — which is the one thing the worked examples cannot
show. `<Fieldset>` is previewable today with no mocking at all and is the sensible first one to add.

## `AdminCategorySelect` vs `RhfAdminCategory`

Use `RhfAdminCategory` whenever the form is RHF-driven; it wires `field.onChange` and surfaces
`fieldState.error.message` on the **sub** field only. Reach for the raw `AdminCategorySelect`
when the value does not live in the form state — `packages/club-form/src/sections/BasicSection.tsx`
does exactly this, holding the cascade in local `useState` while persisting only
`super_category_id` and `category_id`, so the middle level survives editing without being a
form field.

## Rehydrating a saved value

A stored record usually has just two ids. `useCategoryValue(superId, subId)` reads the tree and
returns a full value; `buildCategoryValue(categories, superId, subId)` is the pure form for when
you already have the docs.

```ts
const value = useCategoryValue(club.super_category_id, club.category_id);
```

Note the middle level is derived from **the sub's `parent_id`**, not stored. If a sub is
re-parented in admin, previously saved records start resolving to the new middle — which is the
intended behaviour, but it means the middle id is never authoritative history.

## The cascade rules, and what they clear

- Picking a **super** resets everything: `onChange({ ...EMPTY_CATEGORY, super_id, super_name })`.
  A stale sub under a different super is worse than an empty field.
- Picking a **category** clears `sub_id` / `sub_name` and keeps the super.
- Picking a **sub** back-fills the middle level from that sub's `parent_id`, so a user can skip
  the middle dropdown entirely and still end up with a complete value.

`subOptions(categories, categoryId, superId)` has a fallback worth knowing: with a super chosen
but no middle, it returns every sub whose middle sits under that super. That is what makes the
skip-the-middle flow work. With neither chosen it returns all subs.

Only the `super` select is enabled by default — `category` and `sub` unlock once `super_id` is
set. Rendering fewer levels is supported via `fields={['super', 'sub']}`, but the disabled rule
still keys off `super_id`, so `super` must be in the list or the rest stay locked.

## `Fieldset` lives here, and is shared with `@duncit/location`

`Fieldset` is a semantic `<fieldset>` with a legend and a hint. It is exported from this package
but is generic chrome used by both the category and location pickers, and by
`RhfAdminCategoryRows` when it is given a `legend`. Pass `legend` to `AdminCategorySelect` and it wraps itself; import `Fieldset`
directly when you need to group the picker with other fields.

Write the `hint` to say **why** the category matters ("venues auto-match to this club by
location + category"), not to restate the label. That is the convention the existing call sites
follow.

## Constraints

Zero runtime dependencies. Apollo, `graphql`, MUI, React and `react-hook-form` are peers, so
the picker uses the host portal's single Apollo client and MUI instance. `ADMIN_CATEGORIES` is
fetched `cache-first`, so many pickers on one page share one network request — do not wrap it in
another query at the call site.

MUI, so web only. The native app does not render this picker; the mobile pod-idea flow builds
its own Super/Category/Sub cascade against the same server data.

`portals/admin` declares this package in its `package.json` but has no import today — it comes in
transitively through `@duncit/club-form`. Anything Dockerising a portal that reaches this package
must COPY its `package.json`, transitive or not.

## Coverage

`vitest.config.ts` sets 100/100/100/100 on `src/**` under `jsdom`. The pure option builders
(`superOptions`, `categoryOptions`, `subOptions`) and `buildCategoryValue` carry most of the
branches and are exported precisely so they can be tested without rendering Autocompletes. Note
consumers commonly `vi.mock('@duncit/category', …)` — e.g.
`packages/club-form/__tests__/mocks/categoryMock.tsx` — so a change to the emitted value shape is
not caught by their tests. Update the mocks in the same change.
