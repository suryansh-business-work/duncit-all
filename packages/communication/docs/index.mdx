Two channels, one idea: **which vendor carries a message is a config detail.**

```ts
await communication.whatsapp.utility.send({
  campaign: 'booking_confirmation',
  to: '+919876543210',
});
await communication.email.send({
  category: 'transactional',
  to: 'user@example.com',
  subject: '…',
  html: '…',
});
```

Both channels are built the same way — channel, provider, transport — so what
you learn about one is true of the other.

## WhatsApp

Sending a WhatsApp message is one line. Which vendor carries it is a config
detail, and swapping that vendor must not touch a single call site.

```ts
import { createCommunication } from '@duncit/communication';

const communication = createCommunication({
  whatsapp: { aisensy: { apiKey: process.env.AISENSY_API_KEY! } },
});

await communication.whatsapp.utility.send({
  campaign: 'booking_confirmation',
  to: '+919876543210',
  name: 'Suryansh',
  variables: ['POD-1021', '₹299'],
});
```

## The shape

Three layers, and each one only knows about the one below it:

| Layer     | File                   | Knows about                                                 |
| --------- | ---------------------- | ----------------------------------------------------------- |
| Channel   | `whatsapp.ts`          | What a valid message is. Nothing about HTTP or any vendor.  |
| Provider  | `providers/aisensy.ts` | One vendor's field names and its idea of success.           |
| Transport | `transport.ts`         | HTTP, retries, timeouts, redaction. Nothing about WhatsApp. |

That split is the whole point. `whatsapp.ts` has no `fetch` in it, so a new
provider is a new file in `providers/` and nothing else moves.

## The four categories

Meta prices and rate-limits WhatsApp by template category, so the API says which
one a message is:

```ts
await communication.whatsapp.utility.send({ … });        // order updates, tickets
await communication.whatsapp.marketing.send({ … });      // offers, launches
await communication.whatsapp.authentication.send({ … }); // OTPs
await communication.whatsapp.service.send({ … });        // replies inside a 24h window
```

Each is the same `send`, with `category` filled in. `communication.whatsapp.send()`
is there for a caller that carries its own category — or none.

## Every option

```ts
interface WhatsAppSendOptions {
  campaign: string; // required — the approved template/campaign name
  to: string; // required — E.164, e.g. '+919876543210'
  name?: string; // defaults to `to`; AiSensy rejects a blank one
  variables?: (string | number)[]; // positional template placeholders
  media?: { url: string; filename?: string };
  source?: string; // where the send came from, for the vendor's reporting
  tags?: string[];
  attributes?: Record<string, string | number | boolean>;
  category?: WhatsAppCategory;
}
```

## What it refuses to send

Validation runs before the provider is ever reached, so a bad message costs
nothing and the error names the field:

- a blank `campaign` or `to`
- a `to` that is not E.164 — **`'9876543210'` is the common mistake**, it needs
  the `+91`
- a `variables` entry that is empty or null. WhatsApp renders a blank
  placeholder as a gap in the customer's message; catching it here is the
  difference between "Your pod is confirmed" and an error in a log.
- `media` with no `url`

```ts
try {
  await communication.whatsapp.send({ campaign: 'c', to: '9876543210' });
} catch (error) {
  if (error instanceof CommunicationValidationError) {
    error.field; // 'to'
  }
}
```

## The errors

| Class                          | When                                 | `retryable` |
| ------------------------------ | ------------------------------------ | ----------- |
| `CommunicationValidationError` | the message was never sendable       | `false`     |
| `CommunicationConfigError`     | no provider, or no API key           | `false`     |
| `CommunicationProviderError`   | the vendor refused or never answered | depends     |

`retryable` is the field to branch on. A rejected key or an unapproved template
returns `false` — sending it again just burns the rate limit. A 429 or a 5xx
returns `true`.

## Retries and timeouts

The transport retries on its own for 408, 429 and 5xx, and for a thrown network
error. Backoff doubles from 300 ms and is capped:

```ts
createCommunication({
  whatsapp: {
    aisensy: {
      apiKey: key,
      retry: { attempts: 5, backoffMs: 500, maxBackoffMs: 8000 },
      timeoutMs: 20_000, // per attempt, not for the whole call
    },
  },
});
```

A 4xx is never retried — the same request fails the same way.

## Logging

Pass a `logger` and you get a `request`, a `response` and an `error` event per
attempt, with the duration. **Secrets are redacted before the event is built**,
which matters here because AiSensy carries its API key in the request _body_,
not a header:

```ts
createCommunication({
  whatsapp: {
    aisensy: {
      apiKey: key,
      logger: (event) => logs.server.info('aisensy', event.phase, { ...event }),
      // event.detail.body → { apiKey: '[redacted]', campaignName: 'welcome' }
    },
  },
});
```

A logger that throws is swallowed. Losing a log line must never lose a message.

## A key that rotates

`apiKey` and `baseUrl` each take a value **or a getter**. The getter form is
what lets a key rotated in the Tech portal apply without a restart:

```ts
createCommunication({
  whatsapp: {
    aisensy: {
      apiKey: () => getRuntimeEnvValue('AISENSY_API_KEY'),
      baseUrl: () => getRuntimeEnvValue('AISENSY_BASE_URL'),
    },
  },
});
```

## Adding a provider

Implement three members. Nothing else in the package changes, and no call site
changes:

```ts
import type { WhatsAppProvider } from '@duncit/communication';

export class MetaCloudProvider implements WhatsAppProvider {
  readonly name = 'meta-cloud';
  async isConfigured() {
    return Boolean(this.token);
  }
  async send(options) {
    /* map options → Meta's payload, return { messageId, provider, raw } */
  }
}

const communication = createCommunication({
  whatsapp: { provider: new MetaCloudProvider(config) },
});
```

An injected `provider` wins over `aisensy` when both are given — which is also
how a test swaps in a fake without touching the network.

## Two things AiSensy does that cost people a day

1. **Success is the string `"true"`.** AiSensy answers HTTP 200 with
   `{ success: "false", message: "Template not approved" }`. Checking `res.ok`
   alone reports every rejected template as a delivered message. The provider
   checks the flag.
2. **No `+` on the destination.** The package's contract is E.164 everywhere;
   the provider strips the plus on the way out, so the vendor's quirk never
   leaks into a call site.

## Email

One method. Everything is decided by what is in the options — including _why_
the email is being sent:

```ts
await communication.email.send({
  category: 'transactional',
  template: 'booking-confirmation',
  to: 'user@example.com',
  subject: 'Booking Confirmed',
  variables: { bookingId: 'POD-1021', amount: '₹299' },
});
```

There is deliberately **no** `email.transactional.send()`. WhatsApp gets
category helpers because Meta enforces the category per template; email does
not, so one method keeps one code path to test and one place to add a rule.

### The nine categories

`transactional` · `authentication` · `marketing` · `service` · `notification` ·
`support` · `billing` · `legal` · `internal`

They are metadata, not routing. What reads them: suppression (marketing can be
unsubscribed from, a receipt cannot), reporting, and the provider's dashboard —
the category ships as a tag on every send.

### Every option

```ts
interface EmailSendOptions {
  category: EmailCategory; // required — why this is being sent
  to: string | string[]; // required
  cc?: string[];
  bcc?: string[];
  subject: string; // required; a template may override it
  template?: string; // rendered with `variables`
  html?: string; // used when there is no template
  text?: string; // derived from the HTML when omitted
  variables?: Record<string, any>;
  attachments?: Array<{ filename: string; content: Uint8Array | string; contentType?: string }>;
  replyTo?: string;
  from?: string; // falls back to the channel's `from`
  tags?: string[];
  metadata?: Record<string, string>;
  headers?: Record<string, string>;
  idempotencyKey?: string; // derived from the message when omitted
}
```

### The layers

| Layer                   | Knows about                                                                                                                       |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `email.ts`              | the ORDER of a send: validate → render → normalise → middleware → hooks → provider                                                |
| `providers/resend.ts`   | one vendor's field names                                                                                                          |
| `transport.ts`          | HTTP, retries, timeouts, redaction — shared with WhatsApp                                                                         |
| `templates/renderer.ts` | an interface. The default holds templates in memory; a server that renders MJML out of a database implements the same three lines |

### What it refuses to send

- an address that is not an address, in `to`, `cc`, `bcc`, `from` or `replyTo`
- a blank `category`, `to` or `subject`
- **a subject with nothing under it** — no `template`, no `html`, no `text`. That
  is the worst outcome available: it looks like a real message and says nothing.
- an attachment with no filename or no content

The error names the field:

```ts
catch (error) {
  if (error instanceof EmailValidationError) error.field; // 'to'
}
```

### The errors

| Class                     | When                                       | `retryable` |
| ------------------------- | ------------------------------------------ | ----------- |
| `EmailValidationError`    | the message was never sendable             | `false`     |
| `EmailConfigurationError` | no provider, no key, or no from address    | `false`     |
| `EmailTemplateError`      | template missing or unrenderable           | `false`     |
| `EmailProviderError`      | the vendor refused or could not be reached | depends     |
| `EmailRateLimitError`     | throttled — carries `retryAfterSeconds`    | `true`      |

`EmailRateLimitError` is its own class because the answer is different: wait and
send again, rather than fix and redeploy.

### Sending once

Every message carries an idempotency key — yours, or one derived from the
category, recipients, subject and body. Resend de-duplicates on it, so **the
transport's own retry cannot put a second invoice in someone's inbox.** Pass
your own when a queue may redeliver the job:

```ts
await communication.email.send({ …, idempotencyKey: 'invoice-INV-2291' });
```

### The text part

Never optional. A message with no text part scores worse with spam filters and
is what a screen reader shows. If you do not write one it is derived from the
HTML — block ends become newlines, and `<script>` / `<style>` contents are
dropped rather than pasted in as source code.

### Middleware, and why it is not a hook

Middleware can **change** the message. Hooks only **watch**. Keeping those apart
is what stops a metrics counter from silently rewriting a customer's email.

```ts
// Nothing sent from staging may reach a real customer.
const redirect: EmailMiddleware = (email, _ctx, next) =>
  next({ ...email, to: ['qa@duncit.com'], cc: [], bcc: [] });

// An unsubscribe applies to marketing. A booking receipt is not optional.
const suppress: EmailMiddleware = async (email, _ctx, next) => {
  if (email.category === 'marketing' && email.to.some(isUnsubscribed)) {
    return { messageId: null, provider: 'suppressed', accepted: [], raw: {} };
  }
  return next(email);
};

createCommunication({ email: { …, middleware: [redirect, suppress] } });
```

They run outermost-first in registration order. A middleware that calls `next()`
twice is rejected — that would send the email twice.

### Adding a provider

Two members. Nothing else in the package changes, and no call site changes:

```ts
class SesProvider implements EmailProvider {
  readonly name = 'ses';
  async isConfigured() {
    return Boolean(this.credentials);
  }
  async send(email: PreparedEmail) {
    /* map to SES, return { messageId, provider, accepted, raw } */
  }
}

createCommunication({ email: { provider: new SesProvider(config), from: '…' } });
```

`PreparedEmail` arrives validated, rendered and normalised, so a provider is
only ever a field-name translation. That is the same shape SendGrid, Postmark,
Brevo and Mailgun would take.

## Reading an AiSensy template

`templateParamCount` answers the one question a send has to get right: how many
values the body takes. It returns the **highest** `{{n}}`, not how many appear —
a body that repeats `{{2}}` and skips `{{3}}` still needs a 3-long array,
because AiSensy fills positionally.

```ts
import { templateParamCount, templateParamError, renderTemplateBody } from '@duncit/communication';

const body = 'Hi {{1}}, your *{{2}}* Pod is cancelled.\n• Pod: {{2}}\n• Refund: ₹{{4}}';

templateParamCount(body); // 4 — {{3}} is never written, but its slot still ships

templateParamError(['Suryansh', 'Sunset Yoga', '', '299'], 4);
// 'Value 3 is empty — WhatsApp renders a blank there.'

renderTemplateBody(body, ['Suryansh', 'Sunset Yoga', '-', '299']);
// 'Hi Suryansh, your *Sunset Yoga* Pod is cancelled.\n• Pod: Sunset Yoga\n• Refund: ₹299'
```

`templateSegments` is the same parse exposed as pieces, so a preview can render
the filled values as styled spans instead of a flat string.

## The message catalogue

`WA_EVENTS` is every WhatsApp message Duncit sends on its own: the scenario key,
the AiSensy campaign it posts to, who it is for, and one label per `{{n}}` in
order.

```ts
import { WA_EVENT_BY_KEY, waEventArity, isRequiredWaCategory } from '@duncit/communication';

WA_EVENT_BY_KEY.get('USER_POD_REMINDER')?.params;
// ['Recipient name', 'Hours until pod', 'Pod', 'Date', 'Time', 'Pod Link', 'Host']

waEventArity('USER_POD_REMINDER'); // 7
isRequiredWaCategory('billing'); // true — a refund notice cannot be switched off
isRequiredWaCategory('feedback'); // false
```

Two things this file deliberately is **not**:

- **It is not the template.** Bodies, arity and approval state come live from
  AiSensy's Project API. The registry only says which campaign a domain event
  points at, so a template edited in the AiSensy console needs no release here.
- **It is not copy.** The labels travel as data because the Admin console
  renders 67 rows, and a key per row would have to be composed —
  `t('admin.wa.' + key)` — which `scripts/verify-translation-keys.mjs` cannot
  see. The screen's own chrome is localized normally.

`params` carries labels, never values: those live in Mongo and can only be read
server-side. What it pins is the **order and the count**, which is the half that
silently rots — one placeholder inserted mid-body shifts every later value into
the wrong sentence, and AiSensy bills for the message either way.

`WA_REQUIRED_CATEGORIES` (`transactional`, `billing`, `account`) mirrors the
split `mailPreference.categories.ts` already makes for email: a person can
silence reminders, feedback and marketing, but not their ticket, their money, or
being told their account changed. Note this is **our** consent axis, not Meta's:
Meta calls 66 of the 71 templates `UTILITY`, which says how they are priced, not
whether a human may switch them off.

## Why the server does not import this

`server/src` imports zero `@duncit/*` packages by design (project rule 40) — it
runs compiled `dist` on plain Node, where a source-only workspace package does
not resolve. `server/src/modules/platform/aisensy/` and
`server/src/services/email/email.provider.ts` are self-contained mirrors of
this design: the same provider split, the same categories, the same
"success is a string" check on AiSensy, in the server's own idioms and errors.
Same precedent as `@duncit/slack`.

On the server the provider is chosen by the Tech portal's active default entry
— an **EMAIL** entry sends over SMTP, a **RESEND** entry sends over the API —
so switching vendor is one click and no deploy. Both the transactional service
and the CRM's lead emails come through that one layer; they used to keep a
nodemailer transport each, which meant a fix to one was a fix to only one.

**Change one, change the other.** The pair is small on purpose.
