## Why this exists

Every console had a dashboard, and every dashboard was a hand-written `<Stack spacing={2.5}>` of
sections in an order somebody picked once. A finance analyst who only ever looks at pending
payouts still scrolled past the greeting card; a support lead who lives in the SOS count could not
put it beside the callbacks count. Seventeen pages, seventeen fixed arrangements, none of them
anybody's.

This package is the arrangement. A page declares **what** it shows — an array of widgets, each
with a default slot and a minimum size — and the package owns **where**: a responsive twelve-column
grid, drag and resize behind an explicit edit mode, and a layout stored per user so it follows
them from the laptop to the desktop.

## Using it

```tsx
import { DuncitDashboard, type DashboardWidget } from '@duncit/dashboard';
import { PageHeader } from '@duncit/ui';

export default function DashboardPage() {
  const { data, loading } = useQuery(SUPPORT_COUNTS);

  const widgets: DashboardWidget[] = [
    {
      id: 'sos',
      title: 'Active SOS alerts',
      content: <StatTile value={data?.sos ?? 0} loading={loading} />,
      defaultLayout: { x: 0, y: 0, w: 3, h: 2 },
      minW: 2,
      minH: 2,
    },
    {
      id: 'tickets-table',
      title: 'Open tickets',
      headerActions: <Button size="small">View all</Button>,
      content: <DuncitTable tableId="support-open-tickets" {...tableProps} />,
      defaultLayout: { x: 0, y: 2, w: 12, h: 6 },
      disablePadding: true,
      minH: 4,
    },
  ];

  return (
    <DuncitDashboard
      dashboardId="support.overview"
      header={<PageHeader title="Support Dashboard" subtitle="Live overview of your queues." />}
      widgets={widgets}
    />
  );
}
```

### The widget

| Field | Meaning |
| --- | --- |
| `id` | Stable key a saved layout refers to. **Renaming one returns that widget to its default slot for everybody who had moved it** — treat it like a database column name. |
| `title` / `subtitle` | Rendered in the widget header. Omit both for a header-less panel. |
| `headerActions` | The header's right-hand slot — a filter, a "View all", a menu. |
| `content` | The body. It scrolls inside its slot rather than pushing the grid around. |
| `defaultLayout` | `{ x, y, w, h }` in grid units, `w` out of 12, `h` × 76px. |
| `minW` / `minH` | Smallest the user may drag it. Defaults to the declared size, capped at 3×2. |
| `disablePadding` | Body renders edge-to-edge — for tables and charts with their own insets. |
| `bare` | No card chrome at all. For a section that is already a run of cards (a KPI strip). |
| `fitContent` | Height follows the content (GridStack `sizeToContent`) instead of a fixed row count. For content whose natural height the page cannot know — a KPI strip that wraps with the viewport, a chart block — so it is never cut off and never leaves dead space. The user still drags it and resizes its width; height re-snaps to the content. **Leave unset** for bodies that fill whatever height they are given (tables, virtualised lists) — auto would collapse them to their minimum. |

### Where the layout lives

`myDashboardLayout` / `saveDashboardLayout` / `resetDashboardLayout` on the server, keyed by
`(user_id, dashboard_id)`, mirrored into `localStorage` so the grid paints in its saved shape on
the first frame instead of flashing the default arrangement. The server copy wins whenever the two
disagree — the user may have rearranged this dashboard on another machine. Logging out clears the
mirror along with everything else in `localStorage`, so a shared browser never leaks one person's
layout to the next.

**Absent means default.** Reset deletes the row rather than writing the defaults into it, so a
dashboard whose default arrangement changes in a later release reaches everybody who never
customised it.

## Two drifts it survives

A stored layout outlives the release that wrote it, so `resolveLayout` reconciles rather than
trusts:

- a widget the running build **no longer defines** is dropped — its stored slot names nothing;
- a widget shipped **since** the save has no stored slot, and taking its default would drop it on
  top of a widget the user deliberately moved there, so it is appended **below** the saved ones,
  keeping only its size.

That is why the widget catalogue is code and only positions are data.

## Responsiveness

The column count follows the **grid's own width**, not the window's — the sidebar and the Agent
dock take a different share of every window, so a window breakpoint used to cram twelve columns into
a laptop's leftover pane:

| Grid width | Columns | How the twelve-column layout re-flows |
| --- | --- | --- |
| above 900px | 12 | Exactly as stored. |
| 601–900px | 6 | In reading order, a widget half the row wide or narrower takes **half** the row, a wider one the **whole** row — tidy pairs. |
| 600px and below | 1 | One stacked column, in reading order. |

Reading order is top to bottom, then left to right, so a dashboard's default `y` values should read
the way the page should read on a phone. The re-flow is `reflowLayout(items, column)` in
`layout.ts`, handed to GridStack as its column-change layout; GridStack's own default scaled every
widget by the column ratio, which rounds four quarter-width tiles to widths that wrap three-and-one.

Three things keep the stored layout honest at every width:

- The grid is built at twelve columns and only then made responsive, so GridStack caches the full
  layout and **Save always writes twelve-column slots**, whatever width the person edited at.
- A saved layout, a Reset or an Arrange move is loaded at twelve columns and re-flowed back down,
  never clamped into the narrow grid.
- `minW` is declared in twelve-column terms, so it is handed to GridStack only for the length of a
  resize, scaled to the current column count (`minWidthFor`) — a standing minimum of 4 would force a
  half-width tablet slot (3 of 6) up to two thirds.

Widget headers wrap: on a narrow card the `headerActions` drop under the title instead of being
clipped.

## Download

Every dashboard has a **Download** button beside **Customise layout**. It saves the dashboard
exactly as it is arranged on screen — header and widgets, without the toolbar or inline errors —
as `<dashboardId>.png` (e.g. `admin.overview.png`). No page wires anything: it is part of
`DuncitDashboard`.

The rasteriser (`modern-screenshot`) is imported on demand, so it loads the first time someone
downloads rather than with the page. The image is 2x for sharp text, scaled down for a dashboard so
tall that 2x would pass iOS Safari's canvas limit. Download is offered only at rest, so the picture
never carries edit handles; a failure renders inline above the grid, like a failed save.

Chrome that belongs on screen but not in the picture spreads `SKIP_IN_DOWNLOAD` from `download.ts`.

## Editing

Rearranging is behind a **Customise layout** button rather than always live: a dashboard is mostly
read, and a grid that moves when a pointer drifts across a card header is a dashboard people stop
trusting. In edit mode the whole widget header becomes the drag handle (with a grip icon as the
affordance) — GridStack listens on that class alone, so clicking a chart, a table row or a button
inside a widget can never move it. The grip itself is deliberately **not** a `<button>`:
GridStack's `skipMouseDown` list refuses to start a drag from anything inside a real button, which
is also what keeps `headerActions` buttons clickable while their header drags.

**Save** writes the arrangement, **Cancel** puts back what was there when editing began, and
**Reset to default** (behind a confirm) deletes the stored row.

### Without dragging (WCAG 2.2 AA)

Dragging can never be the only way in: 2.5.7 Dragging Movements asks for a single-pointer
alternative, and 2.1.1 Keyboard for one that works with no pointer at all. So in edit mode every
widget also carries an **Arrange** button (the four-way arrow, named `Move or resize {title}`). It
opens a menu of six moves:

| Move | What it does |
| --- | --- |
| Move earlier / Move later | Trades slots with the previous / next widget in reading order (top to bottom, then left to right). Each keeps its own size. |
| Make wider / narrower | One column more or less, never below the widget's minimum. |
| Make taller / shorter | One row more or less. Never offered on a `fitContent` widget — its height is measured. |

A move that would change nothing right now is shown disabled — what is possible is read off the
live grid when the menu opens, because GridStack, not React, owns where the widgets sit. A move
goes through the same path as a drag: the grid pushes and packs neighbours, **Save** lights up,
and **Cancel** undoes it.

The maths is `arrangeLayout(items, id, action, min)`, a pure function over the stored layout —
exported so a test can assert a move without mounting a grid. `DashboardGrid` and
`DashboardWidgetCard` take the menu as an optional `arrange` prop (`DashboardArrange`);
`DuncitDashboard` always passes it.
