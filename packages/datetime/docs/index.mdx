## Why this exists

Project rule 11 says every rendered date follows the admin panel's format, zone and time
source. That only holds if there is one implementation. There were several: the portals'
`useDateFormat` did its own `parseISO` + `format`, the support portal did its own
`formatInTimeZone`, and mobile had plain `formatDate`/`formatDateTime` helpers built on
`new Date()`. They disagreed on the fallback time pattern — a zoned 24h default on one side,
`hh:mm a` on the other — so mWeb and the portals rendered different times while settings were
still loading.

It also fixes a subtler bug: `now`. Reading `Date.now()` directly means an admin's CUSTOM time
anchor moves the displayed dates but not "Today", not countdowns, and not which occasion icon
set is live. The clock lives here so all of that moves together.

Kept framework-free and dependency-free on purpose (date-fns are **peers**) so React Native,
the browser and the Node server can all import the same file. Adding a React import here would
break the Node consumers.

## Use it

From `packages/app-settings/src/useDateFormat.ts` — the Apollo adapter that every web surface
goes through:

```ts
import { createDateFormatter, stampServerTime, toTimeSource } from '@duncit/datetime';

const settings = data?.publicAppSettings;
const serverTime: string | null = settings?.server_time ?? null;

const fmt = createDateFormatter({
  dateFormat: settings?.date_format,
  timeFormat: settings?.time_format,
  timeZone: settings?.time_zone,
  timeZoneAware,
  clock: {
    source: toTimeSource(settings?.time_source),
    serverNow: serverTime,
    // Stamped once per distinct server_time, so the server clock keeps
    // ticking between fetches instead of freezing at the fetched value.
    serverNowReceivedAt: stampServerTime(serverTime),
    customTime: settings?.custom_time ?? null,
    customTimeSetAt: settings?.custom_time_set_at ?? null,
  },
});

fmt.formatDate(pod.starts_at); // '' when the input is empty or invalid
fmt.dayLabel(message.created_at); // 'Today' | 'Yesterday' | the configured pattern
fmt.now(); // the application clock, not the device clock
```

`createDateFormatter` is pure — it never fetches. Fetching is the adapter's job
(`@duncit/app-settings` for web, the zustand store in `app/mobile-app/src/utils/app-formatter.ts`
for native).

## Worked examples

Real outputs, produced by running the exports against the fixtures above. The clock is
pinned so they are reproducible: the settings response arrived at device time
`1_769_593_331_000` and the device has since moved 45 seconds.

### The clock

```ts
const realNow = () => 1_769_593_331_000 + 45_000;

const clock = createClock({
  source: toTimeSource(publicAppSettings.time_source),   // 'SERVER'
  serverNow: publicAppSettings.server_time,
  serverNowReceivedAt: 1_769_593_331_000,
  realNow,
});

clock.source                 // 'SERVER'
clock.now().toISOString()    // '2026-07-28T09:42:56.000Z'  — server time + the 45s elapsed

resolveNow({ source: 'BROWSER', realNow })   // 1769593376000 — the device's own (wrong) clock
```

The BROWSER result is nearly half a year off the SERVER one. That gap is the whole reason
the clock exists: a device with a wrong clock must not decide whether a pod has started.

CUSTOM anchors, with and without a save-stamp:

```ts
// Anchor saved at a known server instant → it ticks forward with the server clock.
resolveNow({
  source: 'CUSTOM',
  customTime: '2026-12-25T00:00:00.000Z',
  customTimeSetAt: '2026-07-28T09:42:11.000Z',
  serverNow: publicAppSettings.server_time,
  serverNowReceivedAt: 1_769_593_331_000,
  realNow,
})                                    // → 2026-12-25T00:00:45.000Z

// No save-stamp → the anchor is frozen.
resolveNow({ source: 'CUSTOM', customTime: '2026-12-25T00:00:00.000Z', realNow })
                                      // → 2026-12-25T00:00:00.000Z
```

Coercion and narrowing:

```ts
toEpochMs('2026-07-28T09:42:11.000Z')  // 1785231731000
toEpochMs('')                          // null
toEpochMs('not a date')                // null

toTimeSource('CUSTOM')                 // 'CUSTOM'
toTimeSource('nonsense')               // 'SERVER'  — DEFAULT_TIME_SOURCE
TIME_SOURCES                           // ['SERVER', 'BROWSER', 'CUSTOM']
```

`stampServerTime` returns the stamp of the *first* sighting of a given string:

```ts
resetServerTimeStamp();
stampServerTime('2026-07-28T09:42:11.000Z', () => 1000)  // 1000
stampServerTime('2026-07-28T09:42:11.000Z', () => 9999)  // 1000  — same string, original stamp
stampServerTime(null)                                    // null  — falls back to the device
```

### The formatter

```ts
const fmt = createDateFormatter({
  dateFormat: publicAppSettings.date_format,
  timeFormat: publicAppSettings.time_format,
  timeZone: publicAppSettings.time_zone,
  timeZoneAware: true,
  clock: { source: 'SERVER', serverNow: publicAppSettings.server_time, serverNowReceivedAt: 1_769_593_331_000, realNow },
});

fmt.formatDate(podStart)                          // '02 Aug 2026'
fmt.formatTime(podStart)                          // '06:00 PM'   — 12:30 UTC in Asia/Kolkata
fmt.formatDateTime(podStart)                      // '02 Aug 2026 · 06:00 PM'
fmt.dayKey(podStart)                              // '2026-08-02'
fmt.formatPattern(podStart, 'EEEE, d MMMM')       // 'Sunday, 2 August'

fmt.dayLabel(new Date(fmt.clock.nowMs()))         // 'Today'
fmt.dayLabel(new Date(fmt.clock.nowMs() - 86400000)) // 'Yesterday'
fmt.dayLabel(podStart)                            // '02 Aug 2026'

fmt.formatDate(null)                              // ''
fmt.formatDate('garbage')                         // ''
```

`06:00 PM` is the payoff of `timeZoneAware: true`. With it `false` the same input renders in
whatever zone the device happens to be in, which is how the same pod showed two start times
on two phones.

With no settings at all, the fallbacks still produce real output — nothing renders blank
while the query is in flight:

```ts
createDateFormatter().formatDate(podStart)        // '02 Aug 2026'
FALLBACK_DATE_FORMAT                              // 'dd MMM yyyy'
FALLBACK_TIME_FORMAT                              // 'hh:mm a'
FALLBACK_TIME_ZONE                                // 'Asia/Kolkata'
```

### Occasions

```ts
const at = (iso: string) => Date.parse(iso);

resolveActiveOccasion(occasions, at('2026-07-28T09:42:11Z'))?.slug  // 'monsoon-season'
resolveActiveOccasion(occasions, at('2026-08-15T09:42:11Z'))?.slug  // 'independence-day'
resolveActiveOccasion(occasions, at('2026-11-05T09:42:11Z'))?.slug  // 'diwali'
resolveActiveOccasion(occasions, at('2026-03-04T09:42:11Z'))        // null — Holi is is_active: false
```

On 15 August the Monsoon window (`sort_order: 1`) and Independence Day (`sort_order: 20`)
both cover the instant; the higher `sort_order` wins, which is how a short campaign layers
over a long season. Ties break on the later `starts_at`.

## API

### Clock

| Export | Signature | Default | Meaning |
| --- | --- | --- | --- |
| `createClock` | `(input: ClockInput) => Clock` | — | `{ nowMs(), now(), source }` for the configured source. |
| `resolveNow` | `(input: ClockInput) => number` | — | The current instant in ms, one shot. |
| `toEpochMs` | `(value: string \| number \| Date \| null \| undefined) => number \| null` | — | `null` for anything unusable. |
| `toTimeSource` | `(value: string \| null \| undefined) => TimeSource` | `'SERVER'` | Narrows an untrusted string. |
| `stampServerTime` | `(serverTime: string \| null \| undefined, realNow?: () => number) => number \| null` | `Date.now` | Device time of a distinct `server_time`'s first arrival. |
| `resetServerTimeStamp` | `() => void` | — | Test seam; clears the module cache. |
| `TIME_SOURCES` | `readonly TimeSource[]` | — | `['SERVER','BROWSER','CUSTOM']`. |
| `DEFAULT_TIME_SOURCE` | `TimeSource` | — | `'SERVER'`. |

`ClockInput` fields — `source` is the only required one:

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `source` | `'SERVER' \| 'BROWSER' \| 'CUSTOM'` | yes | Which clock to read. |
| `serverNow` | `string \| number \| Date \| null` | no | `server_time` from the settings response. |
| `serverNowReceivedAt` | `number \| null` | no | Device time that response arrived — pass `stampServerTime(...)`. |
| `customTime` | `string \| number \| Date \| null` | no | CUSTOM anchor instant. |
| `customTimeSetAt` | `string \| number \| Date \| null` | no | Server time the anchor was saved; omit to freeze it. |
| `realNow` | `() => number` | no (`Date.now`) | Injectable real clock for tests. |

Any source falls back to the device clock when its inputs are missing, so a misconfigured
setting can never render a 1970 date.

### Formatter

| Export | Signature | Meaning |
| --- | --- | --- |
| `createDateFormatter` | `(settings?: DateFormatterSettings) => DateFormatter` | Pure; never fetches. |
| `FALLBACK_DATE_FORMAT` | `'dd MMM yyyy'` | Used when `dateFormat` is empty. |
| `FALLBACK_TIME_FORMAT` | `'hh:mm a'` | Used when `timeFormat` is empty. |
| `FALLBACK_TIME_ZONE` | `'Asia/Kolkata'` | Used when `timeZone` is empty. |

| `DateFormatterSettings` field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `dateFormat` | `string \| null` | `FALLBACK_DATE_FORMAT` | date-fns pattern from the admin panel. |
| `timeFormat` | `string \| null` | `FALLBACK_TIME_FORMAT` | date-fns time pattern. |
| `timeZone` | `string \| null` | `FALLBACK_TIME_ZONE` | IANA zone; only used when `timeZoneAware`. |
| `timeZoneAware` | `boolean` | `false` | Format in `timeZone` via date-fns-tz instead of the device zone. |
| `clock` | `ClockInput` | `{ source: 'BROWSER' }` | Drives `now`, `dayLabel` and occasion matching. |

`DateFormatter` members: `formatDate`, `formatTime`, `formatDateTime`, `dayLabel`, `dayKey`,
`formatPattern(input, pattern)`, `now()`, plus the resolved `dateFormat` / `timeFormat` /
`timeZone` / `clock`. Every formatter takes `string | number | Date | null | undefined`.

### Occasions

| Export | Signature | Meaning |
| --- | --- | --- |
| `resolveActiveOccasion` | `<T extends OccasionWindow>(occasions, nowMs: number) => T \| null` | Highest `sort_order` among the windows covering `nowMs`. |

`OccasionWindow`: `slug` (required), `label?`, `starts_at?`, `ends_at?`, `is_active?`,
`sort_order?`. Windows with `is_active: false` or an unusable date are skipped; the generic
returns *your* object, so extra fields survive.

## No live preview

Pure functions with no UI. The `<Preview>` runtime mounts React islands; there is nothing
here to mount, and the worked examples above show the real return values instead.

## `stampServerTime` is stateful, and that is the point

The SERVER clock must keep ticking between settings fetches. `stampServerTime(serverTime)`
records the device time at which a *distinct* `server_time` string first arrived, in a
module-level single-entry cache deliberately kept outside React so hooks, plain functions and
native stores share it and it survives re-renders. `resolveNow` then returns
`serverNow + (deviceNow − receivedAt)`.

Call it on every render with the current `server_time` — repeat calls with the same string are
free and return the original stamp. Do **not** pass `Date.now()` as `serverNowReceivedAt`
yourself; that re-anchors on every render and the clock freezes at the fetched value. Tests
that need a clean slate call `resetServerTimeStamp()`.

## Which formatter method

| Need | Method |
| --- | --- |
| The admin's date pattern | `formatDate` |
| The admin's time pattern | `formatTime` |
| Both, joined with ` · ` | `formatDateTime` |
| Today / Yesterday / date | `dayLabel` |
| Grouping key, `yyyy-MM-dd` | `dayKey` |
| A genuine one-off pattern | `formatPattern(input, pattern)` |

Every one of them returns `''` for empty or invalid input rather than throwing — parsing and
formatting both sit inside the guard, so a hostile date string, an unknown IANA zone or a bad
pattern renders empty instead of blanking a page. Reserve `formatPattern` for real one-offs; a
hardcoded pattern is exactly what rule 11 forbids.

## date-fns v2 and v4 must both work

The portals and mWeb are on date-fns v2, the mobile app on v4. Only the API present in both is
used: `format`, `parseISO` and `formatInTimeZone`. Do not reach for `utcToZonedTime` /
`toZonedTime` — they were renamed across `date-fns-tz` majors and will resolve on one surface
and fail on the other.

## `timeZoneAware` changes parsing, not just output

With `timeZoneAware: false` (the web default) strings are parsed with `parseISO`, matching the
portals' historic behaviour. With it `true` — what mobile uses — strings go through the `Date`
constructor and output is rendered via `formatInTimeZone` in the admin's zone. Mobile sets it
so a pod at 6pm IST reads 6pm on both mWeb and native (rule 27), regardless of device zone.

## Occasions ride the same clock

`resolveActiveOccasion(windows, clock.nowMs())` picks the festive icon set covering the
*application* instant, so a custom admin time switches the icons too. Inactive windows and
windows with unusable dates are skipped; when several overlap the highest `sort_order` wins,
ties breaking on the later start — that is how a short campaign layers over a long season.
Native uses `slug` as its local asset folder name, so slugs are not free to rename.

## Coverage

`vitest.config.ts` sets 100/100/100/100 across `src/**`. The fallback branches — missing
`serverNow`, a CUSTOM anchor with no save-stamp, an invalid date — are each covered, because
every one of them is a path a misconfigured admin setting can actually reach in production.
