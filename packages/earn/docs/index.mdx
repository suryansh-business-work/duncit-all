The **rendered** Earn with Duncit feature for MUI surfaces: journey cards,
the pending-meeting reschedule/cancel actions, both dialogs and the GraphQL
documents they fire. mWeb's `/earn` page and the Partners portal's sidebar
"Earn with Duncit" entry render the exact same components from here.

The *rules* — which journeys exist, their copy, and when a card is locked,
pending or approved — stay in `@duncit/onboarding` (framework-free), which the
native app also consumes for its Tamagui twin. This package is the MUI layer on
top: two MUI surfaces may share whole components, native shares logic only
(rule 40).

## Mount it

Wrap the list in an `EarnSurfaceProvider`. The config is the full list of
things the two surfaces disagree on:

```tsx
import {
  EarnJourneyList,
  EarnSurfaceProvider,
  mwebEarnMeetingLabels,
  type EarnSurfaceConfig,
} from '@duncit/earn';
import { EARN_KINDS } from '@duncit/onboarding';
import { mwebCurrentLabel, mwebMeetingLabels } from '@duncit/slots';

const config: EarnSurfaceConfig = {
  // Unlocked card click — the application flow.
  openJourney: (journey) => navigate(journey.surveyPath),
  // Approved-role next step.
  runCta: (cta) => {
    if (cta.target === 'internal') { navigate(cta.internalTo); return; }
    globalThis.window.location.replace(partnerPortalUrl(cta.partnerPath));
  },
  // Slot-picker copy from the surface's namespace (portal: shellMeetingLabels).
  meetingSlotLabels: (rescheduling) => mwebMeetingLabels(t, rescheduling),
  currentSlotBadge: mwebCurrentLabel(t),
  // The dialogs' own copy, from the same namespace (portal:
  // shellEarnMeetingLabels).
  meetingLabels: mwebEarnMeetingLabels(t),
};

<EarnSurfaceProvider config={config}>
  <EarnJourneyList showProducts={showProducts} kinds={EARN_KINDS} />
</EarnSurfaceProvider>;
```

On the Partners portal the same four callbacks invert: `partner` CTA paths are
*in-portal* routes (`navigate(cta.partnerPath)`), while the survey flow and the
host CTA live on mWeb and open externally via `urlConfigs.mwebUrl`.

## What it deliberately does not own

- **Page chrome** — mWeb keeps its Back button + heading; the portal renders
  its own header inside the shell. Only the card stack downward is shared.
- **The product-visibility decision** — `EarnJourneyList` takes a
  `showProducts` boolean. mWeb passes its generic `useFeatureFlag`; a portal
  without one uses the exported `useEarnProductsVisible()` (same
  `is_product_visible` semantics, default hidden).
- **Which journeys to show** — `EarnJourneyList` takes a required `kinds`
  array. Both hub pages pass `EARN_KINDS` (the whole menu); the Partners
  sidebar links a not-yet-partner straight at one journey ("Be a Host",
  "Become an E-Commerce Brand Partner") and passes just that kind, so the
  entry lands ON the onboarding flow rather than on a menu containing it.
- **Journey copy and lock rules** — `@duncit/onboarding`.

## GraphQL

`EARN_ME` (roles + `myMeetings` + each card's `earn_card_images`, set in
Onboarding Portal > Earn with Duncit), `MEETING_SLOTS`, `RESCHEDULE_MY_MEETING`,
`CANCEL_MY_MEETING`, `PUBLIC_FEATURE_FLAGS`. The package calls
`@apollo/client` hooks directly — both consumers already mount an
`ApolloProvider`, so nothing is injected.

## Test ids

Every card, action and dialog carries a `data-testid`, named after the native
twin's `testID` (`app/mobile-app/src/components/earn`) so the mWeb, Partners
and native E2E specs select the same strings:

| Element | `data-testid` |
| --- | --- |
| The card stack | `earn-journey-list` |
| A card's loading placeholder | `earn-box-<role>-skeleton` |
| A card (`EarnBox` takes a `testId` prop, default `earn-box`; the list passes `earn-box-<role>`, e.g. `earn-box-HOST`) | `<testId>` |
| Its clickable area (disabled while locked) | `<testId>-open` |
| Its title / description | `<testId>-title`, `<testId>-description` |
| The locked chip ("Already enabled", "Meeting scheduled", "Onboarding in process.") | `<testId>-enabled` |
| An approved role's next-step button | `<testId>-cta` |
| A pending meeting's actions (by `kind`) | `earn-meeting-actions-<kind>`, `reschedule-<kind>`, `cancel-<kind>`, `reschedule-used-<kind>` |
| Reschedule dialog | `reschedule-dialog`, `reschedule-title`, `reschedule-loading`, `reschedule-current`, `reschedule-empty`, `reschedule-moving`, `reschedule-error`, `reschedule-close`, `reschedule-confirm` |
| Cancel dialog | `cancel-dialog`, `cancel-title`, `cancel-body`, `cancel-error`, `cancel-keep`, `cancel-confirm` |
| The reason field (`MeetingReasonForm` takes a `testId` prop, default `meeting-reason`; the dialogs pass `reschedule-reason` / `cancel-reason`) | `<testId>`, `<testId>-input`, `<testId>-ai-monitoring` |

The slot calendar inside the reschedule dialog is `@duncit/slots`' own
`SlotCalendar` and keeps its ids (`slot-calendar`, `slot-tile-<start_at>`).
