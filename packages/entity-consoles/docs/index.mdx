## What this is

Duncit keeps a directory of four things: every **venue**, every **club**, every
**club admin**, every **host**. Each one has a dedicated console at its own
subdomain — `venues.duncit.com`, `clubs.duncit.com`, `club-admins.duncit.com`,
`hosts.duncit.com` — gated on its own access role (`ALL_VENUES_ACCESS` and
siblings), granted from Admin → Users.

All four are the **same screen over a different entity**: a brief of how many
there are and where they stand, then a list, then a row's full detail. That is
why they share a spec instead of being four near-identical consoles. A fifth
entity is one more spec, not one more console.

## Why one package and not four

Four packages would have meant four sets of coverage thresholds, four
`docs/index.mdx`, four demo files and four `COPY` lines in every Dockerfile that
consumes them — for code whose shared part *is* the scaffold. Rule 40 says
extending beats creating; this is that applied to the consoles themselves.

## The counts are one round trip

A dashboard's numbers come from a **single** document with every tile's count
aliased beside the others:

```graphql
query VenueDirectoryCounts {
  total: venuesTable(query: { page_size: 1 }) { total }
  approved: venuesTable(query: { page_size: 1, filters: [{ field: "status", op: eq, value: "APPROVED" }] }) { total }
  pending: venuesTable(query: { page_size: 1, filters: [{ field: "status", op: eq, value: "SUBMITTED" }] }) { total }
  declined: venuesTable(query: { page_size: 1, filters: [{ field: "status", op: eq, value: "REJECTED" }] }) { total }
}
```

Four separate queries would let four tiles report four different moments — a
venue approved between request two and three gets counted as both pending and
approved, and the tiles stop adding up to the total.

`page_size: 1` because only `total` is read. Asking for a page of rows to throw
them away is the same query at twenty times the cost.

**Every filter field must be on that entity's server-side `filterFields`
allowlist.** A field that is not on it does not come back empty — the table
engine rejects the query and the whole dashboard errors. Clubs are the entity to
watch: they have no `status` field at all, so their tiles read `is_active` and
`is_verified`.

## Mounting a console

```tsx
import { EntityDashboard, VENUES_SPEC } from '@duncit/entity-consoles';

export default function DashboardPage() {
  return <EntityDashboard spec={VENUES_SPEC} />;
}
```

Pass `listPath` once the list route exists, and every tile becomes a way into
the list already filtered to what it counted:

```tsx
<EntityDashboard spec={VENUES_SPEC} listPath="/venues" />
```

Without `listPath` the tiles render as plain figures. That is deliberate: a tile
that navigates nowhere is worse than a tile that simply reports its number.

The lists read that query back with `useUrlColumnFilters(columns)` (pure form:
`urlColumnFilters(params, columns)`), which turns `?status=REJECTED` into
`{ field: 'status', op: 'eq', value: 'REJECTED' }` and `?is_active=false` into
`{ field: 'is_active', op: 'is_false' }`, and hands them to the table as
`externalFilters`. The columns are the allowlist: only an `enum` column's own
option or a `boolean` column's `true`/`false` is honoured, so a hand-edited URL
cannot send the server a field or value the table itself could not. The Venues,
Clubs, Hosts and Club Admins lists (and anything built on `ConsoleListPage`)
all do this; All Pods keeps its own `?lifecycle=` params (below).

## Copy lives in one namespace

`directory.common.*` is what every console says (`Total`, `Awaiting review`,
`Declined`); `directory.<entity>.*` is only what is genuinely specific. Four
namespaces would be four copies of "Awaiting review" drifting apart one console
at a time. The bundle is `DIRECTORY_BUNDLE` in `@duncit/i18n`, and each portal
layers it over the shell's with `i18nFallback`.

## Coverage

`coverageGate: false`, and the vitest thresholds start at the floor. This is a
**ratchet, not a target**: the consoles landed during the repo-wide test pause,
so the numbers are raised as suites arrive and never lowered. The Shared
packages gate enforces whatever is written in the config, so a threshold above
the real coverage reds the build for everyone.

## Every record is editable, and every edit is recorded

A console is not a report. `VenueEditorPage` is mounted at both `/venues/new`
and `/venues/:venueId/edit` and edits the WHOLE record — the venue's details,
its type and capacity, its food menu, its amenities, its documents, its owner,
its payout, its closed dates, its operating hours and booking rules, both
cancellation ladders, its review status and its money split:

```tsx
import { VenueDetailsPage, VenueEditorPage, VenuesPage } from '@duncit/entity-consoles';

// Static before dynamic, so /venues/new is never read as a venue id.
<Route path="/venues/new" element={authed(<VenueEditorPage />)} />
<Route path="/venues" element={authed(<VenuesPage />)} />
<Route path="/venues/:venueId" element={authed(<VenueDetailsPage />)} />
<Route path="/venues/:venueId/edit" element={authed(<VenueEditorPage />)} />
```

One press of Save runs the FOUR mutations a venue's writes are split across
(`adminUpdateVenue`, `updateVenueSettings`, `setVenueDeductions` and — only when
the switch actually moved, because it emails the owner — `setVenueActive`). The
split exists on the server because four different people write those fields in
production; an admin is not one of the four, so the editor is one form.

### The same form the owner fills in

The venue editor and the Partners portal's "Register Venue" form are two
windows onto one record, so they are laid out as ONE form: the first eight
sections are the owner's, under the same names and in the same order, and the
staff-only ones follow.

| # | Section | Holds | Owner's form has it |
| - | ------- | ----- | ------------------- |
| 1 | Venue Details | name, description, cover + gallery, **categories**, address, city and area | yes |
| 2 | Type & Capacity | venue type, total capacity, named spaces | yes |
| 3 | Food Menu | offers food, the dishes | yes (plus QR ordering) |
| 4 | Amenities & Security | amenities, facilities, security | yes |
| 5 | Venue Documents | GSTIN, PAN, uploads | yes |
| 6 | Owner Details | owner account (create only), name, email, phone, DOB, address | yes |
| 7 | Payout Method | method, holder, account number, IFSC, UPI | yes |
| 8 | Leaves & Holidays | closed dates | yes |
| 9 | How it operates | hours, weekly off, booking rules, auto-extend, internal tags | no — staff only |
| 10 | Cancellations | reschedule-only, charge bands, auto-cancel trigger, refund bands | no — staff only |
| 11 | Status and money | status, live switch, share %, commission %, Pod Request limit | no — staff only |

The list lives in `venues/editor/sections/venue-editor-sections.ts`, and
`VenueEditorNav` draws it as a `DuncitTabs` strip above the form. It is the
owner form's section rail with one difference that is deliberate: the editor
stays ONE page with ONE Save (staff correct several sections in a sitting), so
picking a section scrolls to its card instead of swapping a panel. The pick is
held in `?selectedtab=`, so `/venues/:id/edit?selectedtab=payout` opens on the
payout card.

**Several categories.** A venue may be filed under several Super → Category →
Sub triples; the first is the primary. The form holds them as `categories`
(an array of `AdminCategoryValue`) in the shared `RhfAdminCategoryRows` from
`@duncit/category` — the same field the owner's form uses — hydrates them
through `venueCategoryList` (`@duncit/utils`, which also reads the lone
`venue_category` of a record stored before the list existed) and sends them as
`step1.venue_categories`. Three rules, and where they differ from the owner's
form:

- Every STARTED row must be a whole triple and no sub category may repeat
  (both flagged on the row). Same as the owner's form.
- At most `venueRegistrationConfig.category_limit` rows — handed to
  `makeVenueFormSchema(t, foodLimits, categoryLimit)`; `NO_CATEGORY_LIMIT` until
  the config answers. Same as the owner's form.
- **No row is required**, and a row nobody picked anything in is simply not
  sent. That is staff leniency: a venue is registered here from partial
  information. An EMPTY list makes the server leave the stored categories
  alone, so a venue that already has categories keeps at least one row (the
  last row's remove button is disabled) rather than offering an edit that
  would not save.

The record page and the list show every category too — `VenueCategoryLines`
(one path per line, in the summary and About cards) and the table's Category
column, both through `venueCategoryPaths`. The server still sorts that column
on the primary and filters on any.

**One capacity.** The server derives the scalar `capacity` from
`capacity_items` whenever a save carries any. So once a venue has named spaces
the Total capacity field is read-only and shows their sum (`capacityTotal`), and
`valuesToStep1` sends that sum; only a venue with NO named spaces has a total
that is typed in.

**One set of formats.** Fields both forms validate use one source: GSTIN, PAN
and the postal code from `@duncit/forms`; the owner's phone (`PHONE_INTL_PLUS`),
the account number, the IFSC and the UPI id from `@duncit/regex`. What differs
is only what may be left EMPTY — nearly everything, for staff.

### The food menu

The **Food Menu** section carries an **Offers food** switch (`offers_food`) and, while
it is on, the venue's menu (`food_menu`): each dish's name, description, menu
section, price, food type, spice level, availability and photos (uploaded to
`/venues/menu`). Both ride on `adminUpdateVenue`'s `step1`, and the rules are the
server's:

- The food types, spice levels and the three bounds (`food_menu_limit`,
  `food_image_limit`, `food_price_max`) come from `venueRegistrationConfig` and
  are handed to `makeVenueFormSchema(t, limits)` — nothing is restated in the
  client. Until the catalogue answers the form runs on `UNCAPPED_FOOD_LIMITS`
  and the server stays the judge.
- A stored dish goes back under its own `id` (held in the form as `item_id`,
  because `useFieldArray` owns `id`), so it stays the same dish; a row added in
  the form carries none and is created.
- `food_ordering` is **read, never written**. QR ordering charges the venue
  OWNER's Razorpay account, which is linked only from the Partners portal;
  leaving the key out of `step1` is what leaves the owner's settings untouched.
  Switching `offers_food` off makes the server turn ordering off and keep the
  menu.

`VenueDetailsPage`'s Overview tab shows the same data read-only in its Food card
(`VenueFoodCard`): offers food, QR ordering on/off, the discount, and the menu.
The food type and spice level wording is one map, `venues/food-labels.ts`, shared
by the editor's selects and the card.

`ChangeLogsSection` is the other half, and the reason editing here is safe:

```tsx
import { ChangeLogsSection } from '@duncit/entity-consoles';

<ChangeLogsSection entityType="VENUE" entityId={venue.id} tableId="venues-console-change-logs" />
```

It reads `entityChangeLogsTable`, which is ONE append-only collection covering
venues, hosts, clubs, club admins and regions with the entity as a column — so a
console added later gets its history by passing its type. Omit `entityId` and the
same component renders the console-wide feed (`entityChangeFeedTable`) instead.

The trail is captured on the MODEL, not in the services: every write through
mongoose is diffed against what was stored a moment earlier, so a field that
moves through a path nobody thought about is still recorded, with who moved it
and which surface they were on.

## The hosts console, and what it shares with the venues one

`hosts.duncit.com` is the same three screens over `hostsTable` /
`host(host_doc_id:)`: the list, the record (identity, verification, categories,
payout, the pods they run) and the editor at `/hosts/new` + `/hosts/:hostId/edit`.

```tsx
import { HostDetailsPage, HostEditorPage, HostsPage } from '@duncit/entity-consoles';

<Route path="/hosts/new" element={authed(<HostEditorPage />)} />
<Route path="/hosts" element={authed(<HostsPage />)} />
<Route path="/hosts/:hostId" element={authed(<HostDetailsPage />)} />
<Route path="/hosts/:hostId/edit" element={authed(<HostEditorPage />)} />
```

Two things about a host save are worth knowing before touching it:

- **The commission is not on the host record.** It lives on the host's USER
  account, so it is written with `setHostDeductions(user_id:)` rather than
  through `adminUpdateHost`.
- **Categories are a REPLACE, not a merge.** `adminUpdateHost(categories:)`
  swaps the whole set, which is why removing a row in the editor is how a
  category is taken away — and why a row with an incomplete Super→Category→Sub
  triple is dropped from the payload rather than sent. The server rejects a
  partial triple outright, and one abandoned row must not fail the whole save.
- **The monthly Pod Request limit is admin-only and its own write.** Partners
  never see or change it. The venue editor ("Maximum Host Requests / Month") and
  the host editor ("Maximum Venue Requests / Month") hold it as text (empty =
  the default of 10) and save it with
  `setVenueHostRequestLimit` / `setHostVenueRequestLimit` only when it moved;
  `shared/podRequestLimit.ts` reads the one rule in `@duncit/forms/schemas`.

**What the two editors share, and what they do not.** The frame is one component:
`EditorPageShell` owns the form, the back arrow, Save (in the header AND at the
foot, because these pages are tall), the save error and the media dialog. So does
everything both records genuinely have in common — `StatusFields` for the
four-state lifecycle plus the live switch (whose warning exists because both
`setVenueActive` and `setHostActive` notify the partner), `PayoutFields` for the
`BankAccountVerification` block they literally share, `AccountPicker` for
"which account is this", and `EntityPodsTab` for a record's pods (`venue_id` and
`host_user_id` are both allowlisted `podsTable` filters).

What is NOT shared is the sections. A venue has eleven and a host has four, and
they are about different things — pushing them behind one configurable component
would be the abstraction rule 40 warns about rather than the reuse it asks for.

## Who can edit, and who can approve

The five `ALL_*_ACCESS` roles used to gate the portal LOGIN and nothing else:
every query behind these consoles still asked for SUPER_ADMIN / CITY_ADMIN /
ZONAL_ADMIN (or ONBOARDING_MANAGER), so somebody granted `venues.duncit.com`
signed in and saw an empty screen. Fine while the consoles were read-only; not
fine once the record is edited here.

There are now three levels, defined once in
`server/src/modules/portals/console-access.ts`:

| Level | Who | What |
| --- | --- | --- |
| READ | platform admins, onboarding, **the console role** | the list, the record, its change log |
| EDIT | same | the record's own details — name, address, photos, documents, contact, operating hours, categories, which clubs an admin runs |
| GOVERN | platform admins, onboarding — **NOT the console role** | approve and reject, the commission and share percentages, the live on/off switch, the monthly Pod Request limit, the auto-cancel window and refund ladder (Finance too), and appointing a Club Admin |

`useConsoleAccess()` is the client half. It does not decide anything — the server
enforces the split, including refusing a `status` argument on `adminUpdateVenue`
/ `adminUpdateHost` from a caller who cannot govern — it exists so the screen
does not OFFER a control that would be refused:

```tsx
import { useConsoleAccess } from '@duncit/entity-consoles';

const { canGovern } = useConsoleAccess();
// StatusFields shows the values either way; canGovern decides whether they move.
<StatusFields canGovern={canGovern} governedByNote={t('directory.venueEditor.governedBy')} … />
```

The editor hooks use the same flag to SKIP the governance writes rather than
send-and-fail: a console-role editor saving a venue sends `adminUpdateVenue`
(without a status) and `updateVenueSettings`, and never `setVenueDeductions` or
`setVenueActive`. `updateVenueSettings` still carries the auto-cancel window and
refund ladder, which the Cancellations section shows read-only to that editor:
the server accepts them unchanged and refuses (FORBIDDEN) any move from a caller
who is not a governor or `FINANCE_MANAGER` — the venue owner included.

### The pods console

`pods.duncit.com` admits `ALL_PODS_ACCESS`, and every READ its pages make
answers that role through `consoleReaders('POD')`: the brief, All Pods —
including cancelled pods, by the **Include cancelled** switch or the Cancelled
stage — a pod's record with its cancellation risk and its Offer codes table, the
Auto Pods table and an Auto Pod's own page. Writes, money and platform settings
stay with the platform admins; **Pod Settings** shows the server's refusal at
the top of the page rather than leaving every card looking merely out of range.

All Pods keeps its filters in the URL — `?club_id=` and `?lifecycle=`
(`UPCOMING`, `ONGOING`, `COMPLETED`, `CANCELLED`) — so the brief's tiles open
an already-filtered list, changing one filter keeps the other, and a link to
the Cancelled stage switches **Include cancelled** on by itself:

```tsx
<Link to="/pods?lifecycle=UPCOMING">Upcoming</Link>
```

## The club-admins console

`club-admins.duncit.com` reads `clubAdminProfilesTable`, and its editor is the
short one — three sections rather than eight — because a Club Admin record IS
short: who they are, the clubs they run, and the decision.

Three things about it are not obvious from the schema:

- **"Add" is an APPOINTMENT.** There was no create mutation, because the record
  is minted as a side effect of granting the CLUB_ADMIN role (`ensureForUser`).
  `adminCreateClubAdminProfile(user_id:, input:)` now does that properly: it
  grants the role — which mints the record — then writes the details and returns
  it. Inserting a row without the role would give somebody a record in every
  table and picker while they cannot open the Partners console.
- **The status is not a field.** APPROVED and REJECTED are two mutations that
  write the decision, its timestamp and the reason, so the editor calls
  `approveClubAdminProfile` / `rejectClubAdminProfile` and only when the value
  actually MOVED — re-sending the status somebody already holds would re-approve
  them and re-send their email.
- **The clubs are not on this record.** `Club.admin_user_ids` has always been
  that answer, so the form holds the set it is about to assign and the save
  writes it through `assignClubAdminClubs`. Assigning is an EDIT, not
  governance — it is which clubs somebody runs, not whether they may run any.

## A club's hosts, admins and pods, inside the club

`clubs.duncit.com/clubs/:id` lists the club's **hosts** and **pods** as tables
(Hosts and Pods tabs) and each **admin's name** on the overview as a link. Every
one opens the record's full page — the hosts, club-admins and pods consoles' OWN
pages, not copies — editable from there without leaving the club:

```tsx
import {
  ClubAdminEditorPage,
  ClubAdminInClubPage,
  HostEditorPage,
  HostInClubPage,
  PodEditorInClubPage,
  PodInClubPage,
} from '@duncit/entity-consoles';

<Route path="/clubs/:clubId/hosts/:hostId" element={authed(<HostInClubPage />)} />
<Route path="/clubs/:clubId/hosts/:hostId/edit" element={authed(<HostEditorPage />)} />
<Route path="/clubs/:clubId/club-admins/:clubAdminId" element={authed(<ClubAdminInClubPage />)} />
<Route path="/clubs/:clubId/club-admins/:clubAdminId/edit" element={authed(<ClubAdminEditorPage />)} />
<Route path="/pods/:id" element={authed(<PodInClubPage />)} />
<Route path="/pods/:id/edit" element={authed(<PodEditorInClubPage />)} />
```

Two shapes, on purpose:

- **Hosts and admins live UNDER the club.** Either can belong to several clubs,
  so Back has to know which one the reader came from — the URL carries it. The
  record pages resolve their own Edit and Save links from the path they are on
  (`useRecordEditPath` / `useRecordParentPath`), which is what lets one page live
  at `/hosts/:hostId` AND `/clubs/:clubId/hosts/:hostId`.
- **Pods stay at `/pods/:id`.** A pod has exactly one club, so Back is that club
  whichever way the reader came in — and a host's own Pods tab links there too.

The club's hosts are `hostsTable` scoped with `user_id in [...]` over the ids
`Club.hosts` resolves, and its admins' records are `clubAdminProfilesTable`
scoped the same way over `admin_user_ids` — `user_id` is on both allowlists for
exactly this. An `in` filter with no values is DROPPED by the table engine (it
would list every host), so a club with nobody to list never asks.

The tables are `EntityRecordsTab`, the frame `EntityPodsTab` is now a thin layer
over; a club's pods and a venue's pods share one query and one column set
(`shared/recordPods`).

## Club Settings

`ClubSettingsPage` is the Clubs console's settings page (`/club-settings`). It edits the
platform setting `club_chat_retention_days`: a club's chat never closes, so messages older than
this many days (1–3650, default 30) are deleted by the server's hourly chat retention sweep.
Pod chat retention (`pod_chat_retention_hours`, hours after the pod ends) lives on Pod Settings
beside the other pod lifecycle cards. Both read and write `appSettings` / `updateAppSettings`,
so the same admin roles that edit Pod Settings edit these.

```tsx
import { ClubSettingsPage } from '@duncit/entity-consoles';

<Route path="/club-settings" element={authed(<ClubSettingsPage />)} />
```

## Hiding a pod or a club

Pods and clubs both carry a **Hide / Show** action — on each list row and in the
record's header — and it is one implementation, `shared/visibility`, mounted by
both consoles:

```tsx
const visibility = useVisibility('CLUB', () => refetchRef.current?.());

<VisibilityIconButton hidden={!!club.is_hidden} onClick={() => visibility.request({ id, name, hidden })} />
{visibility.dialog}
```

- **Hiding asks for a reason, always.** `request` opens `HideReasonDialog` (React
  Hook Form + Zod, at most 500 characters) and the server refuses a hide without
  one. Showing again is a plain confirm.
- **Hidden is not cancelled.** Nothing is refunded and no booking is touched; the
  record just stops being offered in the app — feeds, search, its page, new
  bookings. People already in a hidden pod keep their ticket.
- **A club takes its pods with it.** Hiding a club marks every pod in it
  `hidden_by_club`, which is stored apart from the pod's own `is_hidden`. So
  showing the club brings back only the pods it took down — a pod an admin hid on
  its own stays hidden — and the Pods console says which it is: **Hidden**, or
  **Hidden with club** (with the club's reason on hover).
- **The two consoles cannot disagree**, because neither holds the state: both
  read `is_hidden` / `hidden_by_club` off the same pod. After a change the hook
  refetches every active query and calls `onChanged` for the caller's table,
  which reads through the table engine rather than a watched query.

The action is offered to `useConsoleAccess().canGovern` only; the server gate is
the same one `updatePod` / `updateClub` sit behind.

## A venue's booking offers, and completing a pod at one

Venue bookings are offers the host and the venue bargain over. The venue record
reads both sides of that back, read-only:

- **Operations → Booking offers** (`VenueOffersCard`): the fewest guests a host's
  offer may be for and the hours either side has to answer, each as it is in
  effect (`Venue.offer_min_guests` / `offer_response_hours`), saying "Duncit's
  default" when the venue left its own (`settings.offers`) at 0. The owner edits
  them in Partners (and mWeb) > Venue settings; the defaults live in Admin >
  Settings > Venue offers. Copy: `venueSettings.offers.*`.
- **Pods → Agreed terms** (`booking-terms/VenueBookingTermsCard`): each booking's
  money (venue receives, Duncit's fee on top, host pays) with the ask behind it
  (`BookingTermsAsk`) — the guests from the venue's minimum to the pod's spots, the
  round it is on, whose move it is, when the pending answer is due, what the
  venue was asked to provide and the note on the terms (`adminVenueBookingTerms`).

The Pods console's **Complete Pod** dialog follows the host's own rules
(`@duncit/forms/schemas`' `addVenueBillIssues` + `addVenueUsageIssues`): on a paid
pod at a venue the venue's final bill — its total AND the file — is required as
the proof of the agreed amount, anything the venue charged beyond it goes in as
extra charges (0–1,000,000, paid on top once Finance approves), and the input is
the shared `buildPodCompleteInput` — `venue_extra_amount` always, never
`include_slot_price`. The live preview sends the same, and shows the agreed terms
(`venue_agreed_model` + `venue_agreed_rate`), the guests a per-guest booking is
paid for (`venue_pax`, never below `venue_min_guests`) and the extra charges
above the split — every figure the server's. A free pod, or a pod with no venue,
asks for no bill.
