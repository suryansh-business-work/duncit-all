## Why this exists

Rule 10 puts every portal on react-hook-form + Zod, and every portal arrived there separately.
The result was a `components/FormField.tsx` in admin, another in crm, another in support — and
a `forms/validation` module in each holding its own `email`, `password` and `personName` Zod
builders. Same rules, different error strings, and a fix to the email length cap landed in one
portal at a time.

The rules here are the **union** of those copies, which is why several take an options object:
crm reported "too long" before "enter a valid email" and support used `required_error` rather
than `min(1)`. Both spellings survive as flags (`lengthFirst`, `requiredError`) so the portals
could adopt one module without changing a single user-visible message.

## Use it

Schema — `portals/admin/src/pages/users-page/create-user/create-user.form.ts`:

```ts
import { z } from 'zod';
import { zodRules } from '@duncit/forms';

export const createUserSchema = z.object({
  first_name: zodRules.personName('First name'),
  last_name: zodRules.personName('Last name'),
  email: zodRules.optionalEmail('Email'),
  phone_extension: zodRules.phoneExtension('Phone code'),
  phone_number: zodRules.phoneNumber('Phone number'),
  city: zodRules.optionalText('City', 80),
  zone: zodRules.optionalText('Zone', 80),
});
```

Field — the dialog that renders it:

```tsx
import { RhfTextField } from '@duncit/forms';

<RhfTextField control={control} name="first_name" label="First name" hint="As on ID" />;
```

Every rule takes the field's **label** as its first argument and builds the message from it, so
`personName('First name')` says "First name is required". Pass the label the user actually
sees, not the schema key.

## Sample data

The main input is a form's values object. This is the admin create-user payload, with the
field names the schema above actually uses — one valid, one deliberately broken.

```ts
export const validCreateUser = {
  first_name: '  Aarav ',            // untrimmed on purpose — the rules trim
  last_name: "O'Neill",
  email: '  Aarav.Mehta@Example.COM ',
  phone_extension: '+91',
  phone_number: '9820011223',
  city: 'Mumbai',
};

export const invalidCreateUser = {
  first_name: '9Aarav',              // digits are not allowed to lead a name
  last_name: "O'Neill",
  email: 'not-an-email',
  phone_extension: '+91',
  phone_number: '98200',             // 5 digits, the rule wants 6–15
  city: 'Mumbai',
};
```

## Worked examples

Actual `safeParse` output from running `createUserSchema` (the schema in "Use it") against
those two fixtures.

```ts
createUserSchema.safeParse(validCreateUser);
// {
//   success: true,
//   data: {
//     first_name: 'Aarav',                    ← trimmed
//     last_name: "O'Neill",
//     email: 'aarav.mehta@example.com',       ← trimmed AND lowercased
//     phone_extension: '+91',
//     phone_number: '9820011223',
//     city: 'Mumbai',
//   },
// }

createUserSchema.safeParse(invalidCreateUser).error.issues.map((i) => [i.path.join('.'), i.message]);
// [
//   ['first_name',   'First name can use letters, spaces, apostrophes, periods and hyphens only'],
//   ['email',        'Invalid input'],
//   ['phone_number', 'Phone number must contain only digits (6-15 digits)'],
// ]
```

That `'Invalid input'` is not a typo and it is worth knowing before you ship a form:
`optionalEmail` is a **union** with `z.literal('')`, and Zod reports a failed union with its
own generic message rather than the branch's `Enter a valid email`. If the field is required,
use `zodRules.email(...)` — it produces the specific message:

```ts
zodRules.optionalEmail('Email').safeParse('');       // { success: true, data: '' }
zodRules.email('Email').safeParse('x'.repeat(300));  // 'Enter a valid email'  ← format first
zodRules.email('Email', { lengthFirst: true })
  .safeParse('x'.repeat(300));                       // 'Email is too long'    ← cap first
```

The rest of the builders, with their real messages:

```ts
zodRules.password('Password').safeParse('abc');      // 'Password must be at least 8 characters'
zodRules.requiredText('Bio', 10, 200).safeParse('too short');
                                                     // 'Bio must be at least 10 characters'
zodRules.optionalText('City', 5).safeParse('Bengaluru');
                                                     // 'City must be 5 characters or fewer'

optionalUrl('Link').safeParse('mailto:a@b.com');     // { success: true, data: 'mailto:a@b.com' }
optionalUrl('Link').safeParse('ftp://x.com');        // 'Link must be a valid URL'
optionalUrl('Link').safeParse('/pods/123');          // 'Link must be a valid URL'
optionalUrl('Link', true).safeParse('/pods/123');    // { success: true, data: '/pods/123' }
```

And the patterns, as booleans:

```ts
PERSON_NAME_PATTERN.test("O'Neill");        // true
PERSON_NAME_PATTERN.test('9Aarav');         // false
PHONE_NUMBER_PATTERN.test('9820011223');    // true
PHONE_NUMBER_PATTERN.test('98200');         // false
SLUG_KEY_PATTERN.test('club-admin');        // true
SLUG_KEY_PATTERN.test('Club Admin');        // false
PAN_PATTERN.test('AAPFU0939F');             // true
GSTIN_PATTERN.test('27AAPFU0939F1ZV');      // true
OTP_PATTERN.test('482913');                 // true
POSTAL_CODE_PATTERN.test('400 001');        // true
```

## API reference

### `RhfTextField<T>`

| Prop | Type | Required | Default | Meaning |
| --- | --- | --- | --- | --- |
| `control` | `Control<T>` | yes | — | The `useForm` control. Always explicit here. |
| `name` | `Path<T>` | yes | — | Typed field name. |
| `hint` | `string` | no | `' '` | Helper text shown while the field has no error (the blank keeps the height stable). |
| …rest | `TextFieldProps` minus `name`/`value`/`onChange`/`onBlur`/`error`/`helperText` | no | `fullWidth: true` | Everything else goes to MUI `TextField`. |

### `FormField<T>` (legacy)

| Prop | Type | Required | Default | Meaning |
| --- | --- | --- | --- | --- |
| `name` | `Path<T>` | yes | — | Typed field name. |
| `control` | `Control<T>` | no | surrounding `FormProvider` | Omit it inside a `FormProvider`. |
| `hint` | `string` | no | `' '` | Helper text with no error. |
| `errorMode` | `'always' \| 'touchedOrDirty'` | no | `'always'` | `'always'` = admin/crm behaviour; `'touchedOrDirty'` = support behaviour. |
| …rest | `TextFieldProps` (same omissions) | no | `fullWidth: true` | Passed to MUI `TextField`. |

### `zodRules` (also exported as `validationRules`)

| Rule | Signature | Produces |
| --- | --- | --- |
| `email` | `(label = 'Email', { lengthFirst? }) => ZodString` | Trimmed, lowercased, required, `.email()`, max 254. `lengthFirst` swaps the cap ahead of the format check. |
| `optionalEmail` | `(label = 'Email') => ZodUnion` | `''` passes; a filled value is trimmed, max 254, validated and lowercased. |
| `password` | `(label = 'Password', { required?, requiredError? }) => ZodString` | Min 8, max 128. `required` prepends `min(1)`; `requiredError` puts the message on `required_error` instead. |
| `personName` | `(label: string) => ZodString` | Trimmed, required, `PERSON_NAME_PATTERN`. |
| `phoneNumber` | `(label = 'Phone number') => ZodString` | Trimmed, `PHONE_NUMBER_PATTERN` (6–15 digits). |
| `phoneExtension` | `(label = 'Phone code') => ZodString` | Trimmed, `PHONE_EXTENSION_PATTERN` (optional `+`, 1–5 digits). |
| `optionalPhoneNumber` | `(label = 'Phone number') => ZodString` | `''` passes; a filled value must match `PHONE_NUMBER_PATTERN`. `.default('')`. |
| `optionalPhoneExtension` | `(label = 'Phone code') => ZodString` | `''` passes; a filled value must match `PHONE_EXTENSION_PATTERN`. `.default('')`. |
| `optionalText` | `(label, max: number, { defaultEmpty? }) => ZodString` | Trimmed, capped. `defaultEmpty` appends `.default('')`. Also a top-level export. |
| `requiredText` | `(label, min: number, max: number) => ZodString` | Trimmed with both bounds. Also a top-level export. |
| `optionalUrl` | `(label, allowRelative = false, { defaultEmpty? }) => ZodEffects` | `''` passes; otherwise parsed with `URL` and restricted to `http:`, `https:`, `mailto:`, `tel:` (plus a leading-slash path when `allowRelative`). Also a top-level export. |

Every rule takes the **label the user sees** as its first argument and builds its message from
it, so pass `'First name'`, not `'first_name'`.

Reach for the `optional…` phone pair whenever the form edits an EXISTING account rather than
creating one. Duncit stopped collecting a phone at signup, so "no number" is an ordinary
state of a real record — and a required rule over it keeps Save switched off forever, which
looks to the person using it like a page that cannot save at all:

```ts
zodRules.optionalPhoneNumber('Phone number').safeParse('');           // { success: true, data: '' }
zodRules.optionalPhoneNumber('Phone number').safeParse('9845012345'); // { success: true }
zodRules.optionalPhoneNumber('Phone number').safeParse('98450');      // fails — too short
```

### Patterns

| Constant | Pattern | Matches |
| --- | --- | --- |
| `PERSON_NAME_PATTERN` | `/^[A-Za-z][A-Za-z .'-]{0,59}$/` | Letter-led name, up to 60 chars. |
| `PHONE_NUMBER_PATTERN` | `/^\d{6,15}$/` | Digits only. |
| `PHONE_EXTENSION_PATTERN` | `/^\+?\d{1,5}$/` | Country code, `+` optional. |
| `SLUG_KEY_PATTERN` | `/^[a-z0-9]+(?:[-_][a-z0-9]+)*$/` | Role and pod-plan keys. |
| `PAN_PATTERN` | `/^[A-Z]{5}\d{4}[A-Z]$/` | Indian PAN. |
| `AADHAR_PATTERN` | `/^\d{12}$/` | Aadhaar. |
| `GSTIN_PATTERN` | `/^\d{2}[A-Z]{5}\d{4}[A-Z][A-Z0-9]Z[A-Z0-9]$/` | 15-char GSTIN with the literal `Z`. |
| `PUBLIC_URL_PATTERN` | `/^https?:\/\/\S+$/i` | An absolute http(s) link a vendor can fetch — a WhatsApp header asset. Narrower than `optionalUrl`, which also takes `mailto:` and `tel:`. |
| `OTP_PATTERN` | `/^\d{4,8}$/` | OTP codes. |
| `POSTAL_CODE_PATTERN` | `/^[\dA-Za-z -]{3,12}$/` | Postal / ZIP codes. |
| `TIME_OF_DAY_PATTERN` | `/^([01]\d\|2[0-3]):[0-5]\d$/` | A scheduled job's wall-clock `HH:mm`, 24-hour and zero-padded. |

## `PackagingFields` — shipping & packaging

The section every product form shares: the Products portal's product page, the Partners app's
listing form and the E-commerce portal's bulk packaging edit. It renders the packed parcel of one
unit (weight and L × B × H), six one-click presets (`PACKAGING_PRESETS` from `@duncit/utils`), a
live "Chargeable weight" readout and — when the box out-weighs its contents — a warning naming the
weight the courier will bill.

```tsx
import { PackagingFields } from '@duncit/forms';

// Product-level: every field, product-wide ones included.
<PackagingFields control={control} setValue={setValue} t={t} />

// One variant row: its own parcel only; type, HSN and flags stay product-wide.
<PackagingFields control={control} setValue={setValue} t={t} prefix={`variants.${index}.`} productFields={false} />

// A parcel about to be booked: every measurement is marked required (the schema still decides what blank means).
<PackagingFields control={control} setValue={setValue} t={t} productFields={false} required />
```

The values stay the form's own — the consumer's Zod schema validates them. Copy comes from
`PACKAGING_BUNDLE` (`packaging.*`), which each consuming portal layers into its `i18nFallback`.

## `WalletStatementDialog` — the wallet's "Download statement"

One dialog for mWeb's wallet and the partner console's. It picks a period (a preset or a custom
range) and a format, validates with `makeWalletStatementSchema`, runs the surface's own
`myWalletStatementFile` query and hands the file to the browser. It then shows one of three
outcomes: downloaded, downloaded but the period was empty, or failed with Retry.

The package imports no app hook. Each surface passes what it resolved:

```tsx
import { WalletStatementDialog, WalletStatementFields, type WalletStatementFormFieldsProps } from '@duncit/forms';

// The fields, bound once to the surface's translator, date format and date picker.
function StatementFields(props: Readonly<WalletStatementFormFieldsProps>) {
  const { t } = useTranslation();
  return <WalletStatementFields {...props} t={t} dateFormat={useDateFormat()} DateField={DateField} />;
}

// Mounted only while open, so the form starts blank.
function StatementForm({ onClose }: Readonly<{ onClose: () => void }>) {
  const { t } = useTranslation();
  const [fetchFile] = useLazyQuery(WALLET_STATEMENT_FILE, { fetchPolicy: 'no-cache' });
  return (
    <WalletStatementDialog
      t={t}
      dateFormat={useDateFormat()}
      Fields={StatementFields}
      runQuery={fetchFile}
      closeLabel={t('mweb.common.close')}
      onClose={onClose}
    />
  );
}
```

| `WalletStatementDialog` prop | Type | Default | Meaning |
| --- | --- | --- | --- |
| `t` | `Translate` | — | The surface's translator. The copy is `withdraw.statement.*` (`WITHDRAW_BUNDLE`). |
| `dateFormat` | `WalletStatementClock` | — | `now()` and `timeZone`. `useDateFormat()` satisfies it. "Today" is read in the business zone. |
| `Fields` | `ComponentType<WalletStatementFormFieldsProps>` | — | The surface's bound `WalletStatementFields`. Pass a stable component, not an inline function. |
| `runQuery` | `({ variables }) => Promise<WalletStatementQueryResult>` | — | The surface's statement query. Apollo's lazy-query function fits as it is. Use `fetchPolicy: 'no-cache'`. |
| `closeLabel` | `string` | — | The Close button's label, from the surface's own common copy. |
| `onClose` | `() => void` | — | Ignored while the file is being fetched. |
| `fontWeight` | `number` | `700` | The weight of the title and the Download button. The partner console passes `900`. |
| `spinner` | `boolean` | off | Show a spinner on Download while fetching, instead of only disabling it. |

| `WalletStatementFields` prop | Type | Default | Meaning |
| --- | --- | --- | --- |
| `control`, `errors`, `preset`, `disabled` | `WalletStatementFormFieldsProps` | — | Handed over by the dialog. |
| `t` | `Translate` | — | The surface's translator. |
| `dateFormat` | `WalletStatementDateFormat` | — | The clock plus `formatDay`, which prints a preset's days in the admin's format. |
| `DateField` | `ComponentType<WalletStatementDateFieldProps>` | — | The surface's own date picker. It takes and emits `yyyy-MM-dd`. |
| `datesInline` | `boolean` | off | Put the two custom days side by side from `sm` up. Stacked when off. |

The dialog owns its busy state: from the moment a valid form is submitted until the query
settles, the fields lock, Close is disabled and Escape does nothing. A query that resolves
without a file is a failure, with the query's own error message when it has one and
`withdraw.statement.failed` when it does not.

Every control keeps a `data-testid`: `statement-dialog`, `statement-preset` (options
`statement-preset-<PRESET>`), `statement-range`, `statement-custom-days`, `statement-from`,
`statement-to`, `statement-format` (options `statement-format-<FORMAT>`), `statement-done`,
`statement-error`, `statement-retry`, `statement-close` and `statement-submit`.

`@duncit/buttons` and `@hookform/resolvers` are optional peers, needed only by this dialog.

## Complete Pod: the venue's usage

`PodCompleteValues` carries `venue_pax` and `overtime_hours` beside the bill: the guests the venue
charged for (its booking is priced per guest) and the hours the pod ran past the slot. Both are optional
— empty, the server counts for itself (the people who came on a per-guest offer, never fewer than its
minimum) and adds no overtime — and both stand without a bill,
because they price the slot, not the bill. `addVenueUsageIssues` checks them against the server's
bounds (`VENUE_USAGE_LIMITS`: a whole guest count up to 10,000, up to 48 hours) and `venueUsageInput`
maps them for the completion and its live preview. `VenueUsageFields` (package root, MUI) draws the
two fields; the host's dialog (@duncit/host-pod-actions) and the Admin console's both mount it.

```tsx
import { VenueUsageFields } from '@duncit/forms';

<VenueUsageFields control={control} paxName="venue_pax" overtimeName="overtime_hours" labels={venueBillLabels} idPrefix="pod-complete" />
```

## A venue offer's ask — `VenueOfferAskFields`

Beside the price, a host's offer to a venue says what the venue should provide (one point per
line, at least one on a new offer) and may add a note. `VenueOfferAskFields` (package root, MUI)
draws the two multiline fields; Create Pod on mWeb, the Partners pod form (@duncit/pod-form) and
the resubmit dialog (@duncit/host-pod-actions) all mount it, so the three ask the same way.

The rules are not here — they are `/schemas`' `offeringsTextField(t, required)` and
`offerNoteField(t)` (bounded as the server bounds them, `VENUE_OFFER_ASK_LIMITS`), embedded in each
surface's own step schema, or `makeVenueOfferAskSchema(t)` on its own. The note field also stops
typing at the server's 1000 characters. `venueOfferInput({ ...source, offerings, note })` in
@duncit/utils turns the typed text into the offer's `offerings` array and trimmed `note`, while
`venueOfferPriceInput` drops both for a live quote, so typing them never asks for a new price.

```tsx
import { VenueOfferAskFields } from '@duncit/forms';

<VenueOfferAskFields
  control={control}
```

The test ids are `<idPrefix>-offer-ask`, `<idPrefix>-offer-offerings` and `<idPrefix>-offer-note`.

## `RhfTextField` vs `FormField`

`RhfTextField` is the one to use in new code. `FormField` is the legacy wrapper kept for the
portals that adopted it first — crm's lead-form sections are all built on it — and it differs
in two ways:

- `control` is **optional**; it falls back to the surrounding `FormProvider`. `RhfTextField`
  always takes an explicit `control`.
- It has an `errorMode`: `'always'` (default, the admin/crm behaviour) surfaces the error
  immediately; `'touchedOrDirty'` waits for interaction (the support behaviour).

Do not migrate a working `FormField` call site just to change the import — the error-display
timing is user-visible and `RhfTextField` has no `errorMode`.

Both default `fullWidth` to `true` and both coerce `value ?? ''`, because an uncontrolled MUI
input that later receives a value logs React's controlled/uncontrolled warning. Both also fall
back to `' '` for `helperText`, so the field's height does not jump when an error appears —
supply a real `hint` instead of relying on that space.

## Rule options exist to preserve messages, not to configure behaviour

| Option | What it changes |
| --- | --- |
| `email(label, { lengthFirst })` | Runs the 254-char cap before the format check, so over-long garbage reports "too long" |
| `password(label, { required })` | Prepends `min(1, '<label> is required')` |
| `password(label, { requiredError })` | Puts the required message on the base string — only differs when the parsed value is `undefined` |
| `optionalText` / `optionalUrl` `{ defaultEmpty }` | Appends `.default('')` so `undefined` parses to `''` |

Reach for one only when matching an existing portal's wording. A new form should take the
defaults; adding a fourth spelling of "email is required" is the thing this package exists to
stop.

`optionalEmail` is a union with `z.literal('')`, so blank passes and a filled value is
lowercased. It is not `email().optional()` — that would reject `''`, which is what an empty
MUI input actually submits.

`optionalUrl(label, allowRelative)` accepts `http:`, `https:`, `mailto:` and `tel:` only, plus
a leading-slash relative path when `allowRelative` is true. It parses with `URL` rather than a
regex, so a protocol outside that set fails even though it looks well-formed.

## Patterns here vs `@duncit/regex`

`src/patterns.ts` is the superset of the per-portal `forms/validation` constants, copied
verbatim so no portal's validation changed on adoption. That means some of it overlaps
`@duncit/regex` — `PHONE_NUMBER_PATTERN` is `/^\d{6,15}$/`, the same range as that package's
`PHONE_INTL`.

Rule of thumb: if a rule is shared with mWeb, native or the server, the pattern belongs in
`@duncit/regex` (which is zero-dep and framework-free and ships prebuilt for Metro). These
exports are for portal leaf-form schemas — `SLUG_KEY_PATTERN` for role and pod-plan keys,
`PAN_PATTERN`, `AADHAR_PATTERN`, `GSTIN_PATTERN`, `OTP_PATTERN`, `POSTAL_CODE_PATTERN`.

`GSTIN_PATTERN` here is the correct 15-character form with the literal `Z` in position 14 —
the same shape as `@duncit/regex`'s `GSTIN`, and **not** mWeb checkout's 14-character variant,
which rejects every valid GSTIN. Do not copy that one in.

## Peers and coverage

MUI, React, react-hook-form and Zod are peer dependencies — the package has no runtime
dependencies. Two copies of react-hook-form in a bundle means `FormField`'s `FormProvider`
lookup finds a different context than the one `useForm` populated, and every field silently
renders empty; keeping RHF a peer is what prevents that.

`vitest.config.ts` enforces 100/100/100/100 over `src/**`. Every option flag above is a branch,
so adding one means adding its test.

## `/schemas` — the contracts mWeb and the native app share

The package root renders MUI, so it can never reach the native app. The **rules** can, and
must: mWeb and the app had written each of these form contracts twice, and they had already
drifted on the things that decide whether a person can sign in.

```ts
import { makeLoginSchema } from '@duncit/forms/schemas';
```

`@duncit/forms/schemas` imports no React, no MUI and no toolkit. The app reaches it through
`file:../../packages/forms` with `COPY packages/forms` in both mobile Dockerfiles; the portals
never import it, which is why `@duncit/regex` and `@duncit/utils` are OPTIONAL peers.

### What was actually different

| | mWeb | native app |
| --- | --- | --- |
| `loginSchema` email | `.min(1)` + `.email()` + `.max(254)` | `.email()` only |
| empty email box says | "Email is required" | "Enter a valid email" |
| a 300-character address | refused | accepted, then refused by the server |
| change-password messages | hard-coded English | hard-coded English |
| contact-change messages | hard-coded English | hard-coded English |

The login row is the one that mattered: the app validated no length and no presence, so the
two surfaces refused different input with different sentences for the same account. `/schemas`
ships mWeb's version, which is what the server enforces.

### Every export is a factory

Messages are localized copy (rule 38), and a Zod schema is built outside React — so the schema
has to take the translator rather than close over one:

```ts
export function makeLoginSchema(t: Translate) { … }
```

A surface binds them **once**, against its own bundled-English fallback, and re-exports under
the name its call sites already use:

```ts
// app/mweb/src/forms/login/login.types.ts
import { makeLoginSchema } from '@duncit/forms/schemas';
import { fallbackT } from '../../i18n/fallback';

export { loginDefaults, makeLoginSchema, type LoginFormValues } from '@duncit/forms/schemas';
export const loginSchema = makeLoginSchema(fallbackT);
```

A form with a live translator passes its own `t` instead, and the messages follow the reader's
language. The `*Defaults` objects carry no copy, so they are plain constants and are imported
directly.

`makeContactValueSchema(channel, t, current?)` returns a different object schema per channel
rather than one schema with every field optional. A schema that accepts a blank number because
the caller *might* have meant an email is a schema that lets "Send code" through with nothing
typed. It is typed `z.ZodType<ContactValueValues>` so both branches present ONE type to
`useForm` — a raw union gives react-hook-form a union to resolve field paths against, which it
cannot do.

`current` is the account's `ContactSnapshot` (what `me` holds now). On the two number channels
the box refuses the account's own number — `contactNumberIsCurrent` from `@duncit/utils`, so the
country code counts — BEFORE it looks at the number's shape, under
`mweb.contactChange.phoneCurrent` / `whatsappCurrent`. Every rule about the number runs inside
one object-level `superRefine` for exactly that reason: a field-level regex is reported ahead of
anything the object says, and a number stored before today's rules would then read "enter a
valid phone number" when the person has not changed it at all.

Otherwise phone numbers validate against `PHONE_INTL` (6-15 digits), not the 10-digit Indian
pattern: there is a country-code picker beside the box, and a `+91`-only rule would refuse
numbers the picker itself offers. The one exception is India's own dial code — `+91` is
additionally held to `PHONE_NUMBER_IN`, so a 9-digit number no longer passes just because it fits
the international range.

### One saved address

`makeAddressSchema(t)` is here for the same reason `makeContactValueSchema` is: mWeb's dialog
and the native sheet had written it out separately, which is how the recipient's name and number
ended up with no rule at all on either of them — a `max(120)` and a `max(20)`, and nothing
about what the characters could be.

The shapes come from `@duncit/regex`, so a parcel refused on one app is refused on the other.
The number is read through `toDigits` first, so a pasted number is judged on its digits rather
than its spacing:

```ts
makeAddressSchema(t).safeParse({ ...blankAddress, phone: '+91 98765 43210' }); // the number passes
makeAddressSchema(t).safeParse({ ...blankAddress, name: 'Doe_123' }); // address.validation.nameInvalid
```

mWeb offers a "default address" flag that native does not, so it extends rather than re-declares:
`makeAddressSchema(t).extend({ is_default: z.boolean() })`.

### A courier ship-to

`makeShipToSchema(t)` is what a brand fills in to fix a pod-shop order's delivery address
before ShipRocket has it (mWeb's and the native Studio's Brand Orders → Fix address). It is the
saved-address contract with `label` dropped and the three parts a courier cannot deliver without
made strict — the same three the server's `brandUpdateProductOrderAddress` refuses: a recipient
name, an Indian mobile (`PHONE_NUMBER_IN` on the last ten digits, as the server stores it) and a
six-digit `PINCODE`. `shipToValues(order.shipping_address)` gives the form its starting values —
every part a string, India when the order has no country.

```ts
makeShipToSchema(t).safeParse({ ...shipToValues(null), pincode: '1010' }); // address.validation.pincodeInvalid
```

### One signup, not two

`makeSignupSchema` is the contract BOTH signup surfaces validate against. They used to hold a
copy each, and the copies had already drifted on three rules that decide whether a real person
can join:

| Rule | mWeb said | the app said |
| --- | --- | --- |
| Name length | 1–60 | 2–80 |
| Confirm password | "did you fill it in" | "at least 8 characters" |
| Blank email | "Email is required" | "Enter a valid email" |

So `Al` passed one surface and not the other, a long Indian full name passed the app and was
refused by mWeb, and the confirm box reported a length problem under a field whose real problem
is that it does not match. One copy, one answer.

The name carries TWO length rules on purpose — Zod stops at the first failure, so an empty box
says *required* and a one-letter name says *too short*, rather than one message doing both jobs
badly.

```ts
const schema = makeSignupSchema(t, minAge, requiredPolicyIds);

schema.safeParse({ ...values, name: '' });   // nameRequired
schema.safeParse({ ...values, name: 'A' });  // nameMin
schema.safeParse({ ...values, dob: '' });           // dobRequired
schema.safeParse({ ...values, dob: '23/04/98' });   // dobInvalid — a 'YYYY-MM-DD' calendar day
schema.safeParse({ ...values, dob: '2015-04-23' }); // dobMinAge — names the admin's minimum
```

The date of birth is a FULL calendar day, held as 'YYYY-MM-DD' exactly as both pickers emit
it, and gated by `isEligibleDob` from `@duncit/datetime` — so the form, the profile editor and
the server all gate on one calendar. A birth year was tried and taken out again: it cannot say
whether this year's birthday has happened yet, so it had to round in the applicant's favour.

### The WhatsApp row, asked at two doors

Signup collects ONE number, and `makeWhatsappNumberSchema(t)` is it: the dial code, the digits,
and `whatsappIsMobile` — the tick box saying whether that number is the person's mobile number
too. Unticked, the profile phone is left **blank**; the person has said the two differ, and
filing the WhatsApp number as their mobile would put a number they never gave us on their
account.

It is its own schema because two doors ask for it. The email form asks as step two —
`makeSignupSchema` spreads this schema's `.shape` in, so the row cannot change for one door and
not the other. Google hands back a credential with no form attached, so it asks on a step of
its own: `makeGoogleSignupSchema(t, minAge)` is that step — the same row plus the date of
birth, because a Google credential carries no birthday either — asked before `signupWithGoogle`
is called, since that mutation needs the number, the code that proved it, and the date of birth.

```ts
const schema = makeWhatsappNumberSchema(t);

schema.safeParse(whatsappNumberDefaults); // phoneRequired — the number is the one blank box
schema.safeParse({ ...whatsappNumberDefaults, phoneNumber: '9845012345' }); // passes

const google = makeGoogleSignupSchema(t, 18);

google.safeParse({ ...googleSignupDefaults, phoneNumber: '9845012345' }); // dobRequired
google.safeParse({ ...googleSignupDefaults, phoneNumber: '9845012345', dob: '1998-04-23' }); // passes

// Apple rides the same step. Apple shares a name only on the first authorisation, so when
// the credential carried none the third argument makes the name a real question.
const apple = makeGoogleSignupSchema(t, 18, true);
apple.safeParse({ ...googleSignupDefaults, phoneNumber: '9845012345', dob: '1998-04-23' }); // nameRequired
```

Whether the number is already on another account is the server's answer, checked twice: before
a code is sent, and again before the account it belongs to is created.

### The withdrawal floor

`makeWithdrawSchema(max, min, t)` is the one rule here worth reading twice. The server enforces
**two** conditions — the wallet balance must clear the role-wise floor AND the amount requested
must clear it — so a schema that validated only the balance let somebody with ₹10,000 in the
wallet submit ₹100 against a ₹500 floor and meet a raw server error instead of a field message.

```ts
makeWithdrawSchema(10_000, 500, t).safeParse({ amount: '100', … }); // withdraw.minimumAmount
makeWithdrawSchema(10_000, 0, t).safeParse({ amount: '1', … }); // 0 disables the floor
```

Which payout details are required depends on the method, and it is a `superRefine` rather than
a discriminated union so react-hook-form keeps one set of registered fields while the reader
switches the picker. UPI asks for a UPI id; IMPS and NEFT ask for an account number and an IFSC
code. Neither asks for the other's.

The messages live in the shared `withdraw.*` namespace rather than `mweb.wallet.*` or
`partners.walletPage.*`, because all three surfaces render them — it rides into the portals
through `SHELL_FALLBACK` and into the apps through their own fallback bundles. The partner
console's amount rules were plain English literals before this moved.

### The wallet statement period

`makeWalletStatementSchema(now, timeZone, t)` is the "Download statement" form on the partner
console, mWeb and the native app. The form holds a preset, two custom days (`yyyy-MM-dd`) and a
format. A preset is never validated, because its days are computed. A `CUSTOM` period is checked
with `statementRangeError` from `@duncit/utils` — the same rules the server enforces.

Pass the surface's own clock and the business time zone (`useDateFormat().now()` and
`.timeZone`). "Today" and the financial year are read in that zone, not the device's.

```ts
const schema = makeWalletStatementSchema(fmt.now(), fmt.timeZone, t);

schema.safeParse({ preset: 'CUSTOM', from: '', to: '2026-06-30', format: 'PDF' });
// issue on `from`: withdraw.statement.errorMissing
schema.safeParse({ preset: 'CUSTOM', from: '2026-06-30', to: '2026-04-01', format: 'PDF' });
// issue on `to`: withdraw.statement.errorOrder

buildWalletStatementVariables({ preset: 'LAST_MONTH', from: '', to: '', format: 'CSV' }, now, 'Asia/Kolkata');
// { input: { from: '2026-09-01', to: '2026-09-30' }, format: 'CSV' } — the myWalletStatementFile variables
```

A missing start day is reported on `from`. Every other problem is reported on `to`, the box the
reader moves to fix it. The too-long message receives `{days}` (366).

### A Pod Shop return

`makePodShopReturnSchema(t)` is the "Return items" form in mWeb and the app. Each line carries
its own `max` — what the server says can still go back — so the quantity rule holds in the
schema as well as in the stepper that bounds it:

```ts
makePodShopReturnSchema(t).safeParse({ lines: [{ …, max: 2, qty: 0 }], reason: 'damaged', comments: '' });
// mweb.podShopReturns.errorPickItem — nothing picked
```

It also refuses more units than `max`, an empty reason, and comments over `RETURN_COMMENTS_MAX`
(2000, the server's limit). Defaults and the mutation input come from `returnFormDefaults` /
`toReturnInput` in `@duncit/utils`.

### A venue food order

`makeFoodCheckoutSchema(t)` is who a food order is for — the "Your details" block of the cart
sheet on a venue's menu, in mWeb and the app. The limits are the server's own
(`FOOD_ORDER_LIMITS` in `@duncit/utils`) and the mobile is `PHONE_NUMBER` from `@duncit/regex`:

```ts
import { foodCheckoutDefaults, makeFoodCheckoutSchema } from '@duncit/forms/schemas';

makeFoodCheckoutSchema(t).safeParse({ ...foodCheckoutDefaults, name: 'Asha', phone: '98765' });
// mweb.venueFood.checkout.phoneInvalid — not a 10-digit mobile
```

`name` is trimmed and must be 2–80 characters; `table` (20) and `note` (300) are optional and
only capped. The too-long messages receive `{max}`. `subscribe` is the "tell me about events
here" tick box — a consent, so it is a plain boolean that starts `false` and is never required.
`FoodCheckoutValues` is the inferred shape and `foodCheckoutDefaults` the blank form.

`makeFoodFeedbackSchema(t)` is what a guest says about a served order — the rating form on the
order page, in mWeb and the app. Its limits are `FOOD_FEEDBACK_LIMITS` in `@duncit/utils`:

```ts
import { foodFeedbackDefaults, makeFoodFeedbackSchema } from '@duncit/forms/schemas';

makeFoodFeedbackSchema(t).safeParse(foodFeedbackDefaults);
// mweb.venueFood.feedback.ratingRequired — no stars chosen yet
```

`rating` is a whole number from 1 to 5 and the only thing required; `comment` is trimmed and
capped at 500 characters, `images` at 3 uploaded photo addresses. The limit messages receive
`{max}`. `FoodFeedbackValues` is the inferred shape and `foodFeedbackDefaults` the blank form.

`makeFoodOrderCancelSchema(t)` is the owner's reason for cancelling a paid food order with a full

`makeFoodCouponSchema(t)` is a venue's food coupon, checked the way the server checks it: the

limit means "no limit". `foodCouponToValues(coupon)` opens the form (a new coupon blank and on) and

```ts
import { makeFoodCouponSchema, toFoodCouponInput } from '@duncit/forms/schemas';
```

### GST on venue food

ONE set of rules for the three forms that set it — Finance → Food Menu Defaults, the owner's
venue form (Partners) and the Venues console editor. The bounds are the server's
(`FOOD_GST_LIMITS` from `@duncit/utils`: a whole percent from 0 to 28), and every message is a

```ts
import {
  makeFoodGstinRule,
  makeFoodTaxDefaultsSchema,
  makeVenueFoodTaxRefinement,
  venueFoodTaxShape,
} from '@duncit/forms/schemas';

// Finance's default — the percent is coerced from its text field.
makeFoodTaxDefaultsSchema(t).parse({ tax_mode: 'EXCLUSIVE', gst_pct: '18' }); // { tax_mode: 'EXCLUSIVE', gst_pct: 18 }

// A venue form: loose shape beside its food_ordering, checked only while the venue overrides.
const checkTax = makeVenueFoodTaxRefinement(t);
z.object({ food_ordering: z.object({ ...venueFoodTaxShape }) })

// The venue's GST number: optional, compared upper-cased (GSTIN from @duncit/regex).
makeFoodGstinRule(t).safeParse('22ABCDE1234F1A5'); // shell.foodTax.gstinInvalid
```

```tsx
import { FoodTaxFields } from '@duncit/forms';
```

### A venue's food menu — `food-menu`

The dishes, QR ordering and the invoice GST number, checked ONE way by the menu editor
(@duncit/venue-food, native), the Partners venue form's Food section and the Venues console
editor's. Shapes are loose (`venueFoodShape`, `foodDishShape`, `foodOrderingShape`) and the rules

(`FOOD_DISH_NAME_MAX` and friends). `editsAccount` says whether the form picks the Razorpay

```ts
import { makeFoodMenuSchema, makeVenueFoodRefinement, venueFoodShape } from '@duncit/forms/schemas';

// The menu editor's whole form, GST number included.
makeFoodMenuSchema(t, { limits, editsAccount: true });

// A bigger venue form holding the food block under the same names.
z.object({ ...otherFields, ...venueFoodShape }).superRefine(makeVenueFoodRefinement(t, { limits, editsAccount: false }));
```

### Venue and dish videos — `video-link`, `venue-videos`

Owners add an uploaded clip or a YouTube link. `makeYoutubeLinkSchema(t)` validates a pasted link against
`@duncit/regex` `YOUTUBE_URL` (channels and playlists are refused). `venueVideoOf(url)` reads the kind from the
address — a YouTube one carries its privacy-enhanced `embedUrl`, `watchUrl` and `thumbnailUrl`, a file its
`sourceUrl` — and `venueVideosOf(list)` drops blanks. They live here, not in `@duncit/utils`, because they
read `@duncit/regex`, which utils does not depend on.

### Venue cancellation policy

`makeCancellationPolicySchema(t)` is what a venue owner's cancellation policy is checked
against — in the Partners console today, and in mWeb and the native app as they gain the
same settings page. The policy is a list of **bands**: cancelling INSIDE `hours_before` of the
slot start costs `value`, either a `PERCENT` of the slot price or a flat `AMOUNT`. A booking
cancelled outside every band is free, and `reschedule_only` takes cancelling off the table
altogether without deleting the bands.

The form holds `hours_before` and `value` as **strings** (`CancellationTierValues`), because
they come out of text inputs; the schema coerces them, so the parsed output is the server's
`VenueCancellationPolicy` with numbers. Two rules the server also enforces are refused on the
row instead of after a round trip:

```ts
const schema = makeCancellationPolicySchema(t);

schema.safeParse({
  reschedule_only: false,
  tiers: [
    { hours_before: '24', charge_type: 'PERCENT', value: '50' },
    { hours_before: '6', charge_type: 'AMOUNT', value: '500' },
  ],
}); // { success: true, data: { …, tiers: [{ hours_before: 24, … value: 50 }, { hours_before: 6, … value: 500 }] } }

schema.safeParse({ reschedule_only: false, tiers: [{ hours_before: '24', charge_type: 'PERCENT', value: '150' }] });
// tiers.0.value — venueSettings.validation.percentMax   (more than the booking)

schema.safeParse({ reschedule_only: false, tiers: [band24, { ...band24, value: '20' }] });
// tiers.1.hours_before — venueSettings.validation.duplicateWindow   (two bands, one window)
```

The other refusals are the window's shape — whole hours, none negative, at most 8760 (a
year) — and a charge that is a number and not negative. Every message is a
`venueSettings.validation.*` key, a namespace all three surfaces ship.

Two mappers sit either side of the form. `toPolicyValues(policy)` turns the saved
`VenueSettings.cancellation` into form values (a venue with no policy yet edits an empty one),
and `toPolicyInput(values, t)` parses the form back into `VenueSettingsInput.cancellation` —
throwing rather than sending an invalid policy. The bands are kept even while
`reschedule_only` is on, so switching it back off restores what the owner wrote instead of an
empty list. `emptyTier` is the band "Add a charge" appends: 24 hours, 50%.

### Cancelling a pod at the venue

`makeVenueCancelPodSchema(t)` is the one thing a venue owner has to give before a pod at their
venue is cancelled and its attendees refunded: a reason, which goes into the email the host and
everyone booked in receive. It is trimmed and must be at least 5 characters, and the refusal is
`mweb.venuePods.reasonRequired` — a key mWeb and the native app both ship. mWeb and the app had
each written this rule beside their own dialog; the sentences around that dialog (the Account
Health warning, the success notice, why Cancel is off) are `@duncit/utils`' `venueCancel*`
helpers. `venueCancelPodDefaults` starts the form blank.

```ts
const schema = makeVenueCancelPodSchema(t);

schema.safeParse({ reason: '  Venue flooded overnight  ' }); // { success: true, data: { reason: 'Venue flooded overnight' } }
schema.safeParse({ reason: 'Rain' });                        // reason — mweb.venuePods.reasonRequired
```

### Pod Requests between venues and hosts

`makePodRequestNoteSchema(t)` is the optional note sent with a Pod Request, trimmed and capped at
`POD_REQUEST_NOTE_MAX` (500, the server's own limit; `podRequests.noteTooLong` names it).
The monthly Pod Request limit is admin-only (partners never see or change it).
`makePodRequestOverrideSchema(t)` backs it in the Venues / Hosts portals and at onboarding: an empty
field becomes `null` (the default of 10 applies), else typed text coerced to a whole number 0–
`POD_REQUEST_OVERRIDE_MAX` (`podRequests.overrideInvalid`).

```ts
makePodRequestOverrideSchema(t).safeParse({ limit: '25' }); // { success: true, data: { limit: 25 } }
makePodRequestOverrideSchema(t).safeParse({ limit: '' });   // { success: true, data: { limit: null } }
```

### A Club Admin marking attendance without a scan

`makeForceMarkSchema(labels)` backs the override a Club Admin uses when the host never scanned
anybody: they are read names down a phone line about a pod that has already happened. Every
field is optional and every filled field is checked — a blank row is a legitimate answer ("I was
not given that name") and must not hold the mark, while a one-letter name or half a number on
the roster is worse than an empty row, because it reads as a record. `forceMarkInitialValues(n)`
opens `n` blank rows, one per seat still unaccounted for.

It takes a built `PodAttendanceLabels` rather than a `t`, because every attendance surface
already builds that object. It lived in `@duncit/host-pod-actions` while only MUI had this path;
the native app cannot consume that package, so bringing the Club Admin's mark to the phone would
have meant a second copy of these rules (rules 27 and 40). The MUI dialog imports it back from
here.

```ts
const schema = makeForceMarkSchema(labels);

forceMarkInitialValues(2);
// { companions: [ { name: '', phone_extension: '+91', phone_number: '' }, …one more ] }

schema.safeParse({ companions: [{ name: '', phone_extension: '+91', phone_number: '' }] });
// { success: true } — the admin was not told, and the seat is still marked

schema.safeParse({ companions: [{ name: 'R', phone_extension: '+91', phone_number: '' }] });
// name — labels.otpNameRequired
```

### How a partner is paid out

`BANK_PAYOUT_METHODS` is the three values the server’s `BankAccountVerification`
accepts, beside `''` for a payout that is not set up yet:

```ts
import { BANK_PAYOUT_METHODS } from '@duncit/forms';

BANK_PAYOUT_METHODS; // ['UPI', 'IMPS', 'NEFT']
```

It lives here because a form that offers a fourth value is normalized back to
`''` by the server, which reads to the person who saved it as “my edit did not
save”. The venue and host editors both render their payout dropdown from it, so
the options and what the server accepts cannot drift (rules 2 + 34).

### Still to move

`accountEditSchema` and `checkoutSchema` are the next pair and they have drifted further —
bio caps at 500 on mWeb and 280 on native, GSTIN at 20 vs 15, and mWeb trims before length
checks where the app does not (so `"   "` passes as a city there). Those are behaviour changes,
not a refactor, and want their own review.

### Complete Pod — `makePodCompleteSchema`

The host completion form on mWeb, the Partners console and the native app. A paid pod at a venue
completes against the amount agreed with the venue, and the venue's final bill is its proof: the
bill's total and the file are both required (`hasVenue` — pass false for a free pod, whose host
settles the venue directly). Anything the venue charged beyond the agreed amount goes in
`venue_extra_amount` (0 to 1,000,000) and is paid on top once Finance approves it.
`buildPodCompleteInput` sends the bill, its file and the extra charges (0 included) and never the old
`include_slot_price` — that is how the server knows this build completes against the agreed amount.
`addVenueBillIssues` is the same rule for the Admin console's own schema, and `venueExtraAmountOf`
reads the extra charges for a live preview. The messages come from `@duncit/utils`
`mwebVenueBillLabels` / `shellVenueBillLabels`.

```ts
import { makePodCompleteSchema, buildPodCompleteInput } from '@duncit/forms/schemas';

const schema = makePodCompleteSchema(hasVenue, venueBillLabels);
const input = buildPodCompleteInput(values, pod.id);
```
