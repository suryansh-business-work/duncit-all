## Why this exists

Every portal has a `__tests__/mocks/` folder full of hand-written objects fed to Apollo's
`MockedProvider`. Hand-written means hand-guessed: the server renames `pod_name`, the mock keeps
the old field, every test still passes, and the drift only surfaces in the browser.

A mock typed against the generated schema cannot drift. Rename a field on the server, re-run
codegen, and seventeen portals' mocks fail `tsc` in the same commit that changed the schema.

The file is generated by the server's own codegen run, not by this package:

```
server/codegen.ts →  packages/gql-types/src/schema.ts
```

That output block uses the plain `typescript` plugin only — no `typescript-resolvers` — so it
carries no server context type and stays importable from any workspace.

## Use it

From `portals/ai/__tests__/mocks/prompt.mock.ts`:

```ts
import type { AiPrompt } from '@duncit/gql-types';

export const makeAiPrompt = (over: Partial<AiPrompt> = {}): AiPrompt => ({
  __typename: 'AiPrompt',
  id: 'p1',
  name: 'Prompt',
  content: 'content that is long enough',
  is_active: true,
  created_at: '2026-01-01T00:00:00.000Z',
  ...over,
});
```

The `Partial<T>` override + full literal shape is the pattern across all seventeen portals: the
factory returns a complete, schema-valid object, and each test overrides only the field it cares
about.

## Always keep `__typename`

Codegen runs with `skipTypename: false`, so every object type carries `__typename`. Keep it in
the mock. `MockedProvider` normalizes with `addTypename` on by default, and a mock missing
`__typename` either throws at runtime or forces `addTypename={false}` — which then hides real
cache-normalization bugs from the test.

## It is a devDependency, and it should stay one

Every portal lists `@duncit/gql-types` under `devDependencies`. It exists to type **tests**.
Importing it from `src/` puts a 13k-line generated file into the app's type graph and couples
runtime code to the server's internal schema output instead of to that portal's own codegen
client types. Portal runtime code uses its local `src/generated/graphql`.

Being a devDependency also means it never needs a `COPY packages/gql-types/package.json` line in
a service Dockerfile — the images build runtime deps only.

## Regenerating

```
cd server && npm run codegen
```

Never edit `src/schema.ts`. `overwrite: true` is set, so the next codegen run discards the edit
silently. If a type looks wrong, the schema in `server/src/modules/**/*.schema.ts` is what needs
fixing.

Codegen options that the mocks depend on, all set in `server/codegen.ts`:

- `maybeValue: 'T | null'` — nullable fields are `T | null`, never `undefined`. A mock that
  omits a nullable field fails typecheck; write `field: null` explicitly.
- `enumsAsTypes: true` — enums are string-literal unions, so a mock uses `'ACTIVE'`, not an
  imported enum member.
- `scalars` — `ID` and `DateTime` are `string`, `JSON` and `Upload` are `unknown`. Dates in
  mocks are ISO strings, which is what the API actually returns.

## No tests, no coverage gate

This package has no `vitest.config.ts` and nothing to test — it is generated declarations with a
one-line barrel (`export * from './schema'`). Its correctness gate is the seventeen portals'
typechecks.
