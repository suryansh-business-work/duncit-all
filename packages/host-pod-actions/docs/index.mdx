## Why this exists

A host runs the same five errands on a pod wherever they are signed in: check people in at the
door, complete it and settle their share, fix a typo, resubmit it when the venue says no, or call
it off. mWeb grew those five dialogs first; the native app grew its Tamagui twin (rule 27); then
the Partners console needed them too.

That third surface is the reason this package exists. Copying `host-manage-page/*` into
`portals/partners-app` would have meant two Zod schemas for the same edit, two settlement previews
reading the same waterfall, and two versions of the rule that a `DECLINED` pod opens the
resubmission flow rather than the limited edit. One of them drifts, and a host gets a different
answer depending on which tab they had open.

The native app keeps its own Tamagui views — rule 40's mWeb ↔ native pair shares logic, never UI.
The two **MUI** surfaces share the whole dialog.

## Mount the provider once

Three things genuinely differ per surface, so they are supplied rather than guessed: the media
picker (mWeb's is Pexels-backed, the portals use ImageKit), where a profile or one of the pod's
two links goes, and which namespace the copy is read from.

`onOpenPodMedia` is optional and gates a whole row: the menu shows Upload Pod Media — with its
Share and Copy buttons — only where the surface actually has that route, because handing a guest a
link to a page this console cannot open would send them somewhere that 404s.

```tsx
import {
  HostPodActionsProvider,
  shellHostPodLabels,
} from '@duncit/host-pod-actions';
import { MediaListField } from '@duncit/media-picker';
import { buildSlotLabels } from '@duncit/slots';

<HostPodActionsProvider
  labels={shellHostPodLabels(t)}            // mwebHostPodLabels(t) in mWeb
  slotLabels={buildSlotLabels(t, 'shell.slots')}
  podMediaLabels={shellPodMediaLabels(t)}   // mwebPodMediaLabels(t) in mWeb
  renderMediaField={({ value, onChange, error, label, folder, deviceOnly }) => (
    <MediaListField
      label={label}
      value={value}
      onChange={onChange}
      folder={folder}
      helperText={error}
      deviceOnly={deviceOnly}
    />
  )}
  onViewProfile={openExternally}
  linkBaseUrl={urlConfigs.mwebUrl}
  onOpenFeedback={(podId) => openExternally(podFeedbackPath(podId))}
  onOpenPodMedia={(podId) => openExternally(podMediaPath(podId))}
  notifySuccess={notifySuccess}
  notifyError={notifyError}
>
  {children}
</HostPodActionsProvider>
```

A dialog rendered outside the provider throws rather than falling back to defaults: silently losing
the media picker and showing raw translation keys reads as a broken feature, not a missing mount.

That applies to `PodAttendanceView` too, and it is easy to miss because the board looks like a
read-only roster. It is not: a host's board carries the door scanner, so the view mounts
`TicketScanDialog` — and `podAttendanceBoard` answers `viewer: HOST` whenever the caller hosts
the pod, on whichever console they opened it. A club admin hosting a pod in their own club is the
ordinary case, so the Club Admin's section sits inside the provider exactly like the host's list
does. The dialog is mounted only when `canScanTickets(board)` is true, which keeps a
club-admin-only board renderable, but that is the narrow case, not the contract.

## The attendance board

`PodAttendanceView` is the roster a pod is paid on: who is marked, who is not, and the one action
that changes it. Both MUI surfaces render this one component — mWeb's Host Studio page and the
Partners console's Club Admin section — over the single `podAttendanceBoard` read (rule 41), so
"is this person marked" has one answer.

What the viewer may do comes from the server, not from the call site: `viewer`, `can_mark`,
`lock` and `otp_required` are all on the board. A surface supplies only its copy, its date
format and where to report to.

```tsx
import { PodAttendanceView } from '@duncit/host-pod-actions';
import { shellAttendanceLabels } from '@duncit/utils';   // mwebAttendanceLabels(t) in mWeb

<PodAttendanceView
  podId={podId}
  labels={shellAttendanceLabels(t)}
  formatDateTime={formatDateTime}
  notifySuccess={notifySuccess}
  notifyError={notifyError}
/>
```

## Wire a list to it

`useHostPodActions` owns the five "which pod is being …" states, so a list only renders rows.

```tsx
const { menuHandlers, dialogs } = useHostPodActions(() => refetch());

<PodsTable renderActions={(pod) => <HostPodActionsMenu {...menuHandlers(pod)} />} />
{dialogs}
```

`menuHandlers` also decides which edit a pod gets: a venue-**DECLINED** pod opens the full
`PodResubmitDialog` (new venue + slot, same pod reused); every other pod opens the narrow
`PodEditDialog` — title, description, media, the pod's capacity and its multi-ticket discount.

### The rows are their own file

`HostPodActionsMenu` is the button, the anchor and the popover; the ROWS inside it live in
`HostPodActionsItems`, which the menu spreads its remaining props onto. The split happened when the
menu passed the 200-line ceiling (rule 9) — nothing about the menu's public props changed.

### "Request Change Host" is opt-in

Pass `onRequestChange` and an already-translated `requestChangeLabel` and the menu grows one row,
directly above Cancel: asking Duncit for a different host keeps the pod and everyone's seat, so a
host should pass it on the way to the destructive one. The label is handed in rather than built
here because it lives in `changeRequest.*` — a namespace owned by `@duncit/pod-change-requests`,
which this package deliberately does not depend on. A surface with no board to answer the request
on passes neither prop and keeps the menu it had.

### Complete Pod is a PAST-pod action

`menuHandlers` reads `canCompletePod` from `@duncit/utils` off the pod's own
`pod_date_time` / `pod_end_date_time` and hands it to the menu as `canComplete`. An **upcoming**
or **ongoing** pod carries no Complete row at all — not a disabled one.

Completing a pod IS the settlement: it prices the host, venue and club-admin payouts off the
seats scanned in and hands Finance the releases to approve. Run on a pod whose door is still
open, it freezes that answer early — every guest who walks in afterwards is a seat the host is
never paid for. Host Studio therefore offers it only once the pod is over, which is the same
instant `podPhase` calls `PREVIOUS`, so the Past filter and the menu can never disagree.

The native `PodActionsSheet` takes the identical `canComplete` prop from the same helper
(rule 27).

### Capacity, after the pod is live

A host who published 12 spots at a space that holds 30 used to be stuck at 12 forever: the only
spot control lived in Create-a-Pod. `PodEditDialog` now renders `SpotsStepper` from
`@duncit/ui` — the same slider Create-a-Pod uses — bounded by the server's `podSpotLimits`.

The range is a SERVER answer on purpose. A live pod's slot is BOOKED, so `venueAvailableSlots`
no longer returns it and the ceiling is unreadable here; the seats already sold, which set the
floor, were never on the client at all. The same rules guard the write, so this dialog cannot
offer a seat the mutation would refuse:

- a **host** may only ever RAISE the capacity — people already bought into the size they saw;
- a **Club Admin** or an **admin** may also lower it, but never below `seats_taken`;
- nobody may exceed the booked space's own capacity.

The field renders only once the limits land, and `buildHostUpdateInput(values, { includeSpots })`
omits `no_of_spots` until then — sending the seeded `0` would ask the server to empty the pod.

### The multi-ticket discount, after the pod is live

A pod can sell a single booking of several tickets cheaper — **2+ tickets → 10% off, 4+ → 20%**.
`PodEditDialog` lets the host change that ladder on a live pod by rendering `@duncit/ui`'s shared
`TicketDiscountField` (the same editor Create-a-Pod and the portal pod form use) through
`PodTicketDiscountField`. The tier rules themselves live once in `@duncit/utils`
(`ticketDiscountTierIssues`), beside the server's twin that re-checks every write. Payments freeze
the discount they were sold at, so changing tiers never re-prices a booking already made.

- The section is **hidden on a free pod** (`pod_type` includes `FREE`, or `pod_amount` is 0), and
  the input then sends `ticket_discount_enabled: false` with no tiers.
- The highest ticket count a tier may ask for follows the capacity control above it:
  `ticketDiscountMaxTickets(no_of_spots)` — spots minus the host's free seat, or 10 when uncapped.
- The highest discount is the admin's `publicAppSettings.ticket_discount_max_pct`, read from the
  shared `PUBLIC_APP_SETTINGS` operation of `@duncit/app-settings`.
- An **untouched** discount is not re-validated, exactly as the server skips it: an admin lowering
  the cap must not stop a host fixing a typo in their title. Change any tier and the whole ladder
  is checked.
- The list that opens the dialog must select `pod_type`, `pod_amount`, `ticket_discount_enabled` and
  `ticket_discount_tiers { min_tickets discount_pct }`. If it does not select the tiers,
  `podEditTicketDiscount` answers `null` and the dialog neither shows nor sends the discount — a
  narrow list can never switch a host's real offer off on an unrelated save.

```ts
import {
  buildHostUpdateInput,
  buildPodEditSchema,
  mwebHostPodLabels,
  podEditInitialValues,
  podEditTicketDiscount,
} from '@duncit/host-pod-actions';

const labels = mwebHostPodLabels(t); // labels.ticketDiscount carries the tier messages
const pod = {
  id: 'DUN-POD-4821',
  pod_title: 'Sunday Badminton Doubles',
  pod_type: 'PAID',
  pod_amount: 499,
  no_of_spots: 12,
  ticket_discount_enabled: true,
  ticket_discount_tiers: [{ min_tickets: 2, discount_pct: 10 }],
};

const discount = podEditTicketDiscount(pod, 50); // 50 = publicAppSettings.ticket_discount_max_pct
const values = {
  ...podEditInitialValues(pod),
  ticket_discount_tiers: [
    { min_tickets: 2, discount_pct: 10 },
    { min_tickets: 4, discount_pct: 20 },
  ],
};

buildPodEditSchema(labels, discount).safeParse(values); // the new 4+ tier is validated
buildHostUpdateInput(values, { includeSpots: true, ticketDiscount: discount });
// → { …, no_of_spots: 12, ticket_discount_enabled: true,
//     ticket_discount_tiers: [{ min_tickets: 2, discount_pct: 10 }, { min_tickets: 4, discount_pct: 20 }] }
```

| Export | Signature | Meaning |
| --- | --- | --- |
| `podEditTicketDiscount` | `(pod: HostPodTarget \| null, maxPct: number) => PodEditTicketDiscount \| null` | `{ free, maxPct, stored }` for the dialog; `null` when the pod carries no tiers to edit. |
| `buildPodEditSchema` | `(labels, ticketDiscount?: PodEditTicketDiscount \| null)` | Adds the tier `superRefine` when a discount context is given. |
| `buildHostUpdateInput` | `(values, { includeSpots?, ticketDiscount? })` | Spreads `ticketDiscountInput(values, free)` when a discount context is given. |
| `PodEditFormInput` | type | The form's raw values — what a `Control` over the edit form holds. |

`PodResubmitDialog` does not carry the discount: a venue-rejected resubmission changes the venue,
the slot and the copy, never the price.

## The pod's media

A pod's photos and videos belong to the POD, not to the dialog that completes it. `PodMediaView`
is the page behind Upload Pod Media, rendered identically for the host and for a guest who
followed the shared link — the server decides in what capacity each arrived and answers
`viewer: HOST | GUEST | NONE` with an empty list for the third, so a forwarded link explains
itself instead of leaking the photos.

```tsx
// The whole page: labels, notifications and the picker come from the provider.
<PodMediaView podId={podId} />
```

Both the ⋮ menu's row and the page's own card hand out the SAME link through
`useHostPodMediaLink` — one address per pod, minted once as a tracked short link
(`POD_MEDIA`). `PodCompleteDialog` then SHOWS that media rather than asking for it again: the
old inline picker was a second place to upload the same photos, whose answer only ever reached
the payment release.

## Copy lives in two namespaces

`mweb.podFeedback.*` / `mweb.hostScan.*` / `mweb.podMedia.*` for mWeb and native,
`shell.podFeedback.*` / `shell.hostScan.*` / `shell.podMedia.*` for the portals — word-for-word identical values. They cannot collapse into one
namespace because the server stores one Localization row per key path, and they are written out as
literal `t('…')` calls because `scripts/verify-translation-keys.mjs` greps for the literal key. Same
shape, and same reasons, as `@duncit/slots`' `buildSlotLabels`.

## What it deliberately does not own

The **Admin** console's Complete Pod dialog. That is a different job — staff pick which co-host is
the payout beneficiary and attach notes — and its settlement preview already renders through
`@duncit/ui`'s `FinanceWaterfallList`. This package renders the same list with host-voiced lines
(`buildHostShareLines`): "You receive", not "Host receives".
