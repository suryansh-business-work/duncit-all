## Why this exists

A venue, a club and a CRM lead all have to land on the **same** admin location row, or the
platform cannot match a venue to a club in that locality later. Every form that let a user type a
city was a form that produced `Bangalore`, `Bengaluru` and `bengaluru ` as three distinct places.

So the picker is strict: four dropdowns, no free text, every option read from the admin-managed
Location DB. `portals/partners-app` (register venue), `portals/onboarding` (admin venue create),
`portals/crm` (lead location field) and `packages/club-form` all render this one component, so a
change to the cascade rules lands in all four at once.

Runtime deps are zero — MUI, Apollo, React and react-hook-form are **peer** dependencies,
supplied by the host portal so there is exactly one copy of each in the bundle.

## Use it

Uncontrolled/controlled form value, as in
`portals/partners-app/src/pages/register-venue-page/sections/VenueDetailsSection.tsx`:

```tsx
import { AdminLocationSelect, Fieldset, MapEmbedCard, type AdminLocationValue } from '@duncit/location';

const locValue: AdminLocationValue = {
  location_id: values.location_id ?? '',
  country: values.country ?? '',
  country_code: values.country_code ?? '',
  state: values.state ?? '',
  state_code: values.state_code ?? '',
  city: values.city ?? '',
  locality: values.locality ?? '',
  pincode: values.postal_code ?? '',
};

<AdminLocationSelect value={locValue} onChange={handleLocationChange} disabled={locked} />
```

When the form stores the whole object under one field, use the react-hook-form wrapper instead
and let Zod validate that object (typically: require `location_id`). From
`__tests__/RhfAdminLocation.test.tsx`:

```tsx
import { RhfAdminLocation } from '@duncit/location';

<RhfAdminLocation control={control} name="location" />
```

It takes every `AdminLocationSelect` prop except `value`, `onChange` and `errors` — those three
come from the `Controller` — and renders a field-level error message on the City dropdown.

## Worked examples

### The cascade, one level at a time

```js
countryOptions(locations)
// [ { value: 'IN', label: 'India' },
//   { value: 'AE', label: 'United Arab Emirates' } ]     ← value is the country_code

stateOptions(locations, 'IN')
// [ { value: 'Karnataka',  label: 'Karnataka' },
//   { value: 'Maharashtra', label: 'Maharashtra' } ]     ← value is the state NAME, not the code

cityOptions(locations, 'IN', 'Karnataka')
// [ { value: 'Bengaluru', label: 'Bengaluru', location_id: '66f1a2b3c4d5e6f708192a6e' },
//   { value: 'Mysuru',    label: 'Mysuru',    location_id: '66f1a2b3c4d5e6f708192a6f' } ]

localityOptions(locations, '66f1a2b3c4d5e6f708192a6e')
// [ { value: 'Indiranagar', label: 'Indiranagar', pincode: '560038' },
//   { value: 'Koramangala', label: 'Koramangala', pincode: '560034' },
//   { value: 'Whitefield',  label: 'Whitefield',  pincode: ''       } ]  ← null → ''
```

`stateOptions` returns the state **name** as its value because `state_code` is not always set in the
admin DB. That is why `AdminLocationValue` carries both `state` and `state_code` and why matching on
the code alone loses rows.

`cityOptions` is the only builder that carries `location_id` — the city *is* the document, and that
id is what every consumer persists.

### `buildLocationValue` — the pincode fallback

```js
buildLocationValue(locations, '66f1a2b3c4d5e6f708192a6e', 'Indiranagar')
// { location_id: '66f1a2b3c4d5e6f708192a6e', country: 'India', country_code: 'IN',
//   state: 'Karnataka', state_code: 'KA', city: 'Bengaluru',
//   locality: 'Indiranagar', pincode: '560038' }         ← the ZONE pincode

buildLocationValue(locations, '66f1a2b3c4d5e6f708192a6e', 'Whitefield')
// { …, locality: 'Whitefield', pincode: '560001' }       ← zone has none ⇒ the CITY pincode
```

An id with no matching doc keeps the id and the requested locality, and blanks the rest, so a saved
record renders as "something is selected but unresolved" rather than as empty:

```js
buildLocationValue(locations, '66f1a2b3c4d5e6f7081ffff0', 'Indiranagar')
// { location_id: '66f1a2b3c4d5e6f7081ffff0', country: '', country_code: '', state: '',
//   state_code: '', city: '', locality: 'Indiranagar', pincode: '' }
```

Note that a **locality** that does not exist on the matched doc is silently dropped to `''`, while
an unmatched **location_id** is kept. The two failure modes differ; don't assume either.

### `buildLocationValueFromNames` — for forms that stored strings

```js
buildLocationValueFromNames(locations, {
  country: 'India', state: 'Karnataka', city: 'bengaluru', locality: 'Koramangala',
})
// { location_id: '66f1a2b3c4d5e6f708192a6e', country: 'India', country_code: 'IN',
//   state: 'Karnataka', state_code: 'KA', city: 'Bengaluru',
//   locality: 'Koramangala', pincode: '560034' }
```

The lower-case `'bengaluru'` matched, and the value came back with the admin **canonical** casing
plus a `location_id` the record never stored. That upgrade path is the point of the helper.

With no admin row for the city, the saved names survive and `location_id` stays empty:

```js
buildLocationValueFromNames(locations, { country: 'India', state: 'Goa', city: 'Panaji' })
// { location_id: '', country: 'India', country_code: '', state: 'Goa', state_code: '',
//   city: 'Panaji', locality: '', pincode: '' }
```

A Zod `location_id` requirement is what should catch this on save — the field is deliberately not
blanked, so the user still sees what they typed.

### Map helpers

```js
buildMapQuery(['Third Wave Coffee', '  ', 'Indiranagar', 'Bengaluru'])
// 'Third Wave Coffee, Indiranagar, Bengaluru'        ← the blank part is dropped, no ", ,"

buildMapQuery(['Indiranagar', 'Bengaluru'], 12.9784, 77.6408)
// '12.9784,77.6408'                                  ← both coords present ⇒ parts ignored

mapEmbedUrl('Third Wave Coffee, Indiranagar, Bengaluru')
// 'https://maps.google.com/maps?q=Third%20Wave%20Coffee%2C%20Indiranagar%2C%20Bengaluru&z=14&output=embed'

mapEmbedUrl('12.9784,77.6408', { apiKey: 'AIza-EXAMPLE-KEY', zoom: 17 })
// 'https://www.google.com/maps/embed/v1/place?key=AIza-EXAMPLE-KEY&q=12.9784%2C77.6408&zoom=17'

mapEmbedUrl('')
// ''                                                 ← empty query ⇒ empty src, never a broken iframe

mapSearchUrl('Third Wave Coffee, Indiranagar, Bengaluru')
// 'https://www.google.com/maps/search/?api=1&query=Third%20Wave%20Coffee%2C%20Indiranagar%2C%20Bengaluru'
```

Default zoom differs by strategy: **15** keyed, **14** keyless.

### `EMPTY_LOCATION`

```js
{ location_id: '', country: '', country_code: '', state: '',
  state_code: '', city: '', locality: '', pincode: '' }
```

## Props / API

| `fields` | `LocationLevel[]` | no | `['country','state','city','locality']` | Which levels render. |
| `required` | `boolean` | no | `false` | Marks every rendered level required. |
| `disabled` | `boolean` | no | `false` | Disables all levels (used while a venue is locked). |

| `direction` | `'row' \| 'column'` | no | `'column'` | Stack direction. |
| `labels` | `Partial<Record<LocationLevel, string>>` | no | Country / State / City / Locality | Per-level label overrides. |
| `errors` | `Partial<Record<LocationLevel, string>>` | no | `undefined` | Per-level error text. |
| `legend` | `string` | no | `undefined` | Setting it wraps the fields in a `<Fieldset>`. |
| `hint` | `string` | no | `undefined` | Fieldset hint — say what maps from the location. |

### `<RhfAdminLocation>`

Every `AdminLocationSelect` prop except `value`, `onChange` and `errors`, plus `control: Control<T>`
and `name: Path<T>` (the field holding the whole `AdminLocationValue`). The field-level error
renders on the **City** dropdown.

### `<MapEmbedCard>` — `MapEmbedCardProps`

| Prop | Type | Required | Default | Meaning |
| --- | --- | --- | --- | --- |
| `title` | `string` | no | `'Map preview'` | iframe title (accessibility) and the default heading. |
| `parts` | `readonly MapQueryPart[]` | no | `undefined` | Address fragments joined with `", "`. |
| `lat` / `lng` | `number \| null` | no | `undefined` | When **both** are set, the query becomes `"lat,lng"` and `parts` is ignored. |
| `query` | `string \| null` | no | `undefined` | Pre-built query; overrides `parts`/`lat`/`lng` when non-empty. |
| `apiKey` | `string \| null` | no | `undefined` | Uses the keyed Embed API when set (unless `keyless`). |
| `keyless` | `boolean` | no | `undefined` | Forces the always-working `output=embed` map. |
| `zoom` | `number` | no | `15` keyed / `14` keyless | Map zoom. |
| `heading` | `ReactNode` | no | `title` | Header label. |
| `buttonLabel` | `ReactNode` | no | `'Open in Maps'` | Deep-link button text. |
| `hideWhenKeyMissing` | `boolean` | no | `false` | Render nothing (instead of the fallback message) when a keyed map is required but the key is absent. |
| `missingKeyFallback` | `ReactNode` | no | "Add VITE_GOOGLE_MAP_API…" | Shown in place of the iframe in that case. |

## Live preview

No live preview yet, and the reason is the same as `@duncit/category`: `AdminLocationSelect` calls
`useAdminLocations()` itself, so an island without an Apollo client throws and one with a real
client would call the production API from a docs page.

`docs-site` has the `<Preview>` island runtime. The missing piece is a `MockedProvider` wrapper
seeded with `ADMIN_LOCATIONS` → the `locations` array above — which is precisely why that query is
exported. `<MapEmbedCard>` is the exception: it takes plain props, needs no Apollo, and works
keyless, so it can be previewed as soon as this package is a `docs-site` dependency. Add that one
first, with `parts={['Third Wave Coffee', 'Indiranagar', 'Bengaluru']}` from the example above.

## Which entry point to pick

| You have | Use |
| --- | --- |
| One RHF field holding the whole value | `RhfAdminLocation` |
| Flat form fields (`city`, `state`, …) | `AdminLocationSelect` with a manual `value`/`onChange` |
| A persisted `location_id` on an edit form | `useLocationValueFromId(id, locality)` |
| Persisted country/state/city **names** | `buildLocationValueFromNames(locations, names)` |
| Your own bespoke field layout | `useAdminLocations()` + the `*Options` helpers |

`portals/crm`'s `LocationField` is the last row: it renders `cityOptions` and `localityOptions`
itself inside a `Fieldset`, rather than taking the full four-level cascade.

## Hydration: id vs names

`useLocationValueFromId` returns `EMPTY_LOCATION` until the admin list has loaded, then fills in
country/state/city/pincode from the matched doc. Do not treat that first empty render as "the
user cleared the field" — an effect that writes it back into the form will blank a saved value.

`buildLocationValueFromNames` matches case-insensitively on city (narrowed by state and country
when present) and, when **nothing** matches an admin row, deliberately returns the saved names
with an empty `location_id` rather than an empty value. A profile saved before a city existed in
the Location DB still shows what the user typed instead of silently going blank — but it has no
`location_id`, which is exactly what a Zod `location_id` requirement should catch on save.

## `@duncit/location` vs `@duncit/geo`

`@duncit/geo` is the offline country/state dataset used by the mWeb and native **profile**
forms; it has no cities and no admin linkage. Anything that must line up with admin — venue,
club, pod locality — uses this package. Swapping one for the other produces records that cannot
be matched.

Note also that this package is MUI-only, so it is a portal/mWeb component. The native app cannot
import it (rule 29); a native equivalent has to be built on Tamagui against the same
`ADMIN_LOCATIONS` query.

## The query is shared on purpose

`useAdminLocations` runs `ADMIN_LOCATIONS` with `fetchPolicy: 'cache-first'`, so the small,
rarely-changing list is fetched once per session and reused by every location field on the page.
Do not re-declare the query in a portal with `network-only` — that turns one request into one per
field. `ADMIN_LOCATIONS` is exported for tests and `MockedProvider` mocks; import it rather than
re-writing the document, or the mock will not match.

The query filters `is_active: true`, so a deactivated admin location disappears from new forms
while records already pointing at its id keep rendering through `buildLocationValue`.

## Map helpers

`buildMapQuery(parts, lat, lng)` returns `"lat,lng"` when **both** coordinates are present and
otherwise joins the trimmed, non-empty address parts with `", "` — so a blank locality in the
middle never produces `"Indiranagar, , Bengaluru"`. `mapEmbedUrl` builds the iframe `src` and
`mapSearchUrl` the "open in Maps" deep link; `MapEmbedCard` renders both together and takes
`parts` / `lat` / `lng` / `query` directly.

`mapEmbedUrl` works **without** an API key: with no `apiKey` it falls back to the keyless
`maps.google.com?output=embed` map (zoom 14 instead of 15). Do not gate the map behind a
configured key — pass `hideWhenKeyMissing` on the card only when a keyed map is genuinely
required.

## Coverage

`vitest.config.ts` sets 100/100/100/100 on `src/**` (barrels excluded) in a `jsdom` environment
with `__tests__/setup.ts`. A new branch in the cascade — a level that clears its children, a
disabled state — needs a test in the same commit or the package gate fails.
