## What this is

One pod detail page, rendered by three portals. Admin sees every pod on the platform;
a Club Admin sees the pods of the clubs they administer; a Regional Club Admin sees the
pods under the Club Admins in their region — the **same** sections, the same layout,
the same numbers.

## Scope is not cosmetic

`scope` picks which query set the self-fetching sections run:

```tsx
<PodDetailsPage />                       // ADMIN (default)
<PodDetailsPage scope="CLUB_ADMIN" />    // club-scoped twins
<PodDetailsPage scope="REGIONAL" />      // region-scoped twins
```

This exists because **neither of the other two audiences is a role on the user.** A
club admin is a MEMBERSHIP of a club; a Regional Club Admin reaches a pod through a
CHAIN of memberships — their Club Admins, the clubs those people run, the pods in
them. The admin operations are guarded by `requireRole`, which can express neither, so
they refuse both outright. Five queries therefore have scoped twins, each gated
server-side (`assertClubAdminForPod`, and `assertRegionPod` for the region):

| Admin | Club Admin | Regional |
| --- | --- | --- |
| `adminPodAttendees` | `clubAdminPodAttendees` | `regionPodAttendees` |
| `podAuditLogs` | `clubAdminPodAuditLogs` | `regionPodAuditLogs` |
| `hostByUser` | `clubAdminPodHost` | `regionPodHost` |
| `paymentsTable` | `clubAdminPodPayments` | `regionPodPayments` |
| `podFeedbackSummary` | `clubAdminPodFeedback` | `regionPodFeedback` |

Every club-admin root field is **aliased to the admin field name**, so the components
read one response shape and never branch on who is looking.

### Two deliberate asymmetries

- **Payments take a pod id, not a query input.** The admin `paymentsTable` accepts a
  free-form `TableQueryInput` that can express *"every payment on the platform"*.
  Handing that to a club admin would be a hole, so `clubAdminPodPayments` applies the
  pod filter server-side where the caller cannot widen it.
- **The host profile is scoped to the pod.** A club admin may read the host running
  *their* pod, not look up any host by id.

## Selections are shared, not duplicated

The field selections live once in `queries.ts` and are interpolated into both document
sets. The two sets feed the **same** components, so a field added to one and missed on
the other renders a blank cell for one audience only (rule 34).

## Slots

Coupons are **not** in this package: managing them is platform-wide (`ADMIN_RW`
create/delete) and reaches into the admin coupons page. Admin injects it:

```tsx
<PodDetailsPage footer={(pod) => <PodCouponsSection podId={pod.id} podTitle={pod.pod_title} />} />
```

## Club, and the people who run it

Two cards, not one. **Club** answers *which club is this* — its name, its slug, and
the way through to it. **Club Admin Details** answers *who do I call* — every assigned
admin with their email, phone and WhatsApp as real `mailto:` / `tel:` / `wa.me` links.
They were one card until the second question had no answer on it: a list of names with
no number beside them is not a contact.

Both read the same `AdminPodClubDetail` document, so the pair costs one round trip.

A name links through to the user's page only where such a page exists:

```tsx
<PodDetailsPage userTo={(userId) => `/users/${userId}`} />   // admin portal
<PodDetailsPage scope="CLUB_ADMIN" />                        // no user pages — plain text
```

Omitting `userTo` renders the name as text. Club Admin's console has no `/users` route,
and a name that navigates nowhere reads as a broken page rather than a missing feature.

## Edit is opt-in

`editTo` has **no default**. Pass it and the page shows **Edit pod**; omit it and the
button is absent entirely:

```tsx
<PodDetailsPage editTo={(podId) => `/pods/${podId}/edit`} />   // admin portal
<PodDetailsPage scope="REGIONAL" />                            // reads the region, edits nothing
```

It used to default to `/pods/:id/edit` — the admin portal's own route, encoded in a
shared package. The Regional Club Admin console has no pod editor, so that default
rendered a button that bounced off the catch-all route: the same failure `userTo`
already avoided one section below.

## Attendance

This page's attendee table is **read-only about attendance** — it shows the status, and
nothing on it writes one. Marking somebody present lives in `<PodAttendanceView>` from
`@duncit/host-pod-actions`, which the Partners console injects through `footer` on the
Club Admin route:

```tsx
<PodDetailsPage scope="CLUB_ADMIN" footer={(pod) => <ClubAdminAttendanceSection podId={pod.id} />} />
```

It used to be a bare **Mark present** link in the Status cell that fired
`clubAdminForceAttendance` on one click. That mutation writes the number a completed pod
pays the host on, and a forced mark has no scan behind it — so it now sits behind a
warning that names who is about to be marked, in the same view the host reads. One
document, one set of preconditions.
