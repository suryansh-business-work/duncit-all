## Why this exists

Admin and Partners both create pods, and for a while both owned a full copy of the form: the same
club/venue cascade, the same virtual-vs-physical field rules, the same `CreatePodInput` assembly.
A pod has enough conditional shape — mode, venue slot, place charges, products, finance breakdown,
reel — that two copies diverge within a release. The symptom is always the same class of bug: a
field the schema requires in one console and nulls out in the other, so the server rejects a pod
that the UI said was valid.

One form, one schema, one input builder. The differences between consoles are data, not code: a
`PodFormConfig` object of booleans. `portals/admin/src/pages/pods-page/` and
`portals/partners-app/src/pages/pods-page/` now only own their config and their mutations.

## Use it

From `portals/partners-app/src/pages/pods-page/PartnerPodsSection.tsx`:

```tsx
import { PodForm, blankPodFormValues, buildPodInput, useMediaPickerBridge, type PodFormValues } from '@duncit/pod-form';

const picker = useMediaPickerBridge();

const submit = async (values: PodFormValues, options: { draft: boolean }) => {
  await createPod({
    variables: { input: buildPodInput(values, { draft: options.draft, config: PARTNER_POD_CONFIG }) },
  });
};

<PodForm
  initialValues={blankPodFormValues}
  config={PARTNER_POD_CONFIG}
  clubs={clubs}
  venues={venues}
  products={products}
  getClubVenueIds={getClubVenueIds}
  busy={createState.loading}
  error={opError}
  onCancel={close}
  onSubmit={submit}
  onPickImage={picker.pickImage}
  onPickVideo={picker.pickVideo}
/>
```

### The same values as a **virtual draft**

`buildPodInput({ ...sourdoughPod, pod_mode: 'VIRTUAL', meeting_platform: 'Google Meet', meeting_url: 'https://meet.google.com/abc-defg-hij', meeting_notes: 'Link opens 10 min early.' }, { draft: true, config })`
— only the keys the mode changed:

```js
{
  pod_mode: 'VIRTUAL',
  venue_id: null,          // physical-only fields nulled
  location_id: null,
  venue_slot_id: null,
  meeting_platform: 'Google Meet',
  meeting_url: 'https://meet.google.com/abc-defg-hij',
  meeting_notes: 'Link opens 10 min early.',
  place_charges: [],       // place charges are physical-only
  products_enabled: false, // products are physical-only, regardless of the flag
  product_requests: [],
  is_active: false         // draft: true ⇒ is_active: !draft
}
```

That is the rule worth remembering: switching a pod to `VIRTUAL` **silently drops** its products
and place charges at build time even though the form values still hold them.

```js
3000   // 12 × unit_cost 250
```

A `product_id` with no catalogue match contributes `0` rather than throwing — an unapproved product
quietly prices as free, so validate the ids before trusting the total.

### `makePodSchema(config).safeParse(...)` on a half-filled form

Parsing `{ ...blankPodFormValues, pod_title: 'Su', club_id: '…a3b', pod_description: 'Too short', venue_id: '…a4c' }`:

```js
[
  { path: 'pod_title',     message: 'Title is too short' },
  { path: 'pod_description', message: 'Add a longer description' },
  { path: 'venue_slot_id', message: 'Pick an available slot' },
  { path: 'pod_date_time', message: 'Start date/time required' },
  { path: 'media_text',    message: 'At least one image is required' }
]
```

The slot rule is conditional in a way worth knowing: `venue_slot_id` is only required while
`pod_date_time` is **also** empty. An edited pod that keeps its already-booked slot dates never
forces a re-pick, which is why the same values with a date set report no slot error.

### `podToFormValues(pod)` — the inverse

Given a server pod with `pod_hashtag: ['sourdough', 'baking']` and one image, the round-trip fields:

```js
{
  pod_id: 'DUN-POD-10421',
  pod_hashtag_text: 'sourdough baking',                    // array → space-joined text
  media_text: 'https://ik.imagekit.io/duncit/pods/sourdough-hero.jpg',  // media → newline text
  pod_date_time: Date('2026-08-09T05:00:00.000Z'),         // ISO → Date for the MUI X picker
  pod_type: 'NATIVE_FREE',                                 // absent fields fall back to the blank
  pod_hosts_id: []
}
```

Every key absent from the server pod comes back as its `blankPodFormValues` default, **not**
`undefined` — that is what keeps the RHF fields controlled.

## Props / API

### `<PodForm>` — `PodFormProps`

| Prop | Type | Required | Default | Meaning |
| --- | --- | --- | --- | --- |
| `initialValues` | `PodFormValues` | yes | — | Seed values; the form `reset()`s whenever this identity changes. |
| `config` | `PodFormConfig` | yes | — | Feature flags gating both sections and schema branches. |
| `clubs` | `any[]` | yes | — | Club options for the club select. |
| `venues` | `any[]` | yes | — | Venue options, narrowed by the selected club. |
| `users` | `any[]` | no | `[]` | Local host options when `searchHosts` is not supplied. Admin passes its approved hosts here (`hosts(status: APPROVED)`), not the user directory. |
| `products` | `any[]` | no | `[]` | Approved product catalogue for the products section. |
| `finance` | `PodFormFinance` | no | `undefined` | `platform_fee_pct` / `gst_pct` / `currency_symbol` for the live breakdown. |
| `getClubVenueIds` | `(club: any) => string[]` | yes | — | Portal-specific accessor for a club's linked venue ids. |
| `meetingPlatforms` | `PodOption[]` | no | `undefined` | Renders the meeting platform as a select instead of free text. |
| `onGenerateMeetingLink` | `(input: GenerateMeetingLinkInput) => Promise<string>` | no | `undefined` | Shows an auto-generate button next to the meeting link. |
| `onPickImage` | `() => Promise<string \| null>` | no | `undefined` | Swaps the media textarea for a rich picker. |
| `onPickVideo` | `() => Promise<string \| null>` | no | `undefined` | Swaps the reel URL input for a video picker. |
| `searchHosts` | `SearchPodHosts` | no | `undefined` | Server-backed host search (e.g. `clubAdminHostSearch`). |
| `dateTimeFormat` | `string` | no | `undefined` | MUI X display format, from the admin app settings (rule 11). |
| `busy` | `boolean` | no | `false` | Disables the actions while a mutation is in flight. |
| `error` | `string \| null` | no | `undefined` | Server error rendered as an `Alert` above the actions. |
| `onCancel` | `() => void` | yes | — | Close/dismiss handler. |
| `onSubmit` | `(values, { draft }) => Promise<void> \| void` | yes | — | Final or draft submit; a draft skips the Zod resolver. |
| `onReady` | `(methods: UseFormReturn<PodFormValues>) => void` | no | `undefined` | Hands the RHF methods up (admin AI-fill). |
| `hideDraftOnEdit` | `boolean` | no | `undefined` | Hides "Save as Draft" once a pod exists. |
| `preview` | `ReactNode` | no | `undefined` | Live preview column. Given one, the form lays itself out in two columns and renders this node **inside** its `FormProvider`. |

### `<PodPreview>` — no props

Reads the enclosing `FormProvider` and renders the pod as a member sees it: the
list card and the pod page, stacked and live. Only valid inside `<PodForm>`.
`buildPodPreview(values, data)` is the pure derivation behind it, so the shape
both surfaces render can be asserted without mounting either.

## Live preview

There is **no live preview on this page yet**, and it is not an oversight. `docs-site` now ships a
`<Preview>` component that mounts a real React island, but `PodForm` is not mountable from a static
page as it stands: the hosts, clubs and venue-slot sections read through Apollo, and the date fields
need a `LocalizationProvider` with `AdapterDateFns`. A preview here means adding a mocked Apollo
provider plus the `@mui/x-date-pickers` peer to `docs-site` first.

When that lands, the slot is one section, mounting `<PodForm>` with `sourdoughPod` above as
`initialValues` and `makeNativeParityPodConfig({ showProducts: true })` as `config`. Until then the
worked examples above are the honest version — a screenshot or a fake would go stale silently.

## Config is the only fork — never branch on the portal

`PodFormConfig` is the whole compatibility surface: `showHosts`, `requireHosts`, `singleHost`,
`showLocationZone`, `showVenueSlot`, `showPlaceCharges`, `showInventory`, `showFinance`,
`showIsActive`, `showProducts`, `showReel`. Start from `makeNativeParityPodConfig({ showProducts })`,
which mirrors the native create-pod flow (venue slots on, place charges on, reel on, hosts optional).
Club Admin uses it as-is; Admin spreads its extras (`showFinance`, `showInventory`, `showIsActive`,
`requireHosts: true`, `singleHost: true`) on top.

`requireHosts: false` is not a relaxation to copy casually — the server injects the acting admin as
host when none is supplied, which is true for the Club Admin path and not the Admin one.

`singleHost: true` + `requireHosts: true` is how Admin gets *exactly* one host. It matters because
settlement pays `pod_hosts_id[0]` and nobody else (`settlement.service.ts`), so a second host is a
host who never gets paid; extra hosts belong in `co_hosts`. Club Admin deliberately leaves it off.

Opening an older pod that still carries two ids, `usePodEditorState.openEdit` collapses
`pod_hosts_id` to its first entry — the picker can only *show* one id, so hydrating two would leave
the field displaying one host while the form held another, and MUI suppresses the `onChange` when you
re-pick the option already on screen, so there would be no way to correct it. The `'Select only one
host'` schema rule stays as the invariant for any other caller of `buildPodInput`.

Note `showFinance: false` for Club Admin: anything you add to the finance area is invisible there.
Copy that reads on every console must not live in a finance-gated section.

## `makePodSchema` and `buildPodInput` are a pair

The schema is built from the same config (`makePodSchema(config)`), so a field that the form hides
is also a field the schema stops requiring. `buildPodInput` then nulls out exactly what the mode
and the flags disabled — virtual pods null `venue_id`/`location_id`, physical pods null the meeting
fields, `pod_hosts_id` becomes `[]` when `showHosts` is off, products only ride along when the pod
is physical *and* `showProducts` *and* `values.products_enabled`.

Do not hand-build the mutation input from `PodFormValues`. `venue_slot_id` is only emitted when
`config.showVenueSlot` because `CreatePodInput` has the field and `UpdatePodInput` does not — a
hand-rolled input is where that asymmetry gets forgotten.

`podToFormValues` is the inverse for edit flows; `linesToMedia` converts the newline-separated
media textarea into the `{ url, type: 'IMAGE' | 'VIDEO' }` list (extension-driven), and
`getProductRequestTotal` prices a request list against the product catalogue.

## Page vs bare form — pick by who owns the state

- `PodForm` — the form body plus its actions. You own the page, the mutations and the values.
- `PodEditorPage` + `usePodEditorState` — the whole create/edit screen: heading, back button,
  live preview, initial values and save plumbing. `portals/admin/src/pages/pods-page/pod-editor-page`
  and `portals/partners-app/src/pages/club-admin-pod-editor-page` both take this path. If you are
  writing the editor boilerplate by hand, you picked the wrong one.

The editor is a ROUTE, not a modal. Eight sections, a slot calendar and a media gallery do not
fit a `maxWidth="md"` dialog, and a modal leaves nowhere to show the author what they are
building — which is what the preview column is for. `usePodEditorState` takes the pod being
edited (`editingPod`) and owns only the values and the submit; the route owns which pod that is.

`useMediaPickerBridge` exists because `@duncit/media-picker` is callback-shaped
(`onPicked(url)`) while the form wants promises (`onPickImage: () => Promise<string | null>`). The
hook adapts one to the other and hands back ready-made `accept` / `title` dialog props for the kind
being picked. Do not re-implement the promise bridge at the call site.

## Auto Pod mode

An **Auto Pod** is a pod written without a venue, a host or a club — a venue, a host and a club
admin each enrol later, in any order, and the first to enrol pins it to a city (`@duncit/auto-pods`
renders that side). The Admin and Partners consoles used to open a separate, smaller form for it.
They now open **this** form with `config.autoPod: true`, so an Auto Pod is authored in the same
accordion sections, with the same media picker, place charges, reel and finance breakdown as an
ordinary pod. One form, one schema; the mode is one more config flag.

What `autoPod: true` changes:

| Ordinary pod | Auto Pod mode |
| --- | --- |
| Club picker (category inherited from the club) | `AutoPodCategoryField` — a REQUIRED Super › Sub cascade in the club picker's place. It writes `super_category_id` + `sub_category_id`; only hosts approved in that sub-category and clubs carrying it are ever offered the pod. |
| Hosts, venue slot, mode, date/time | Gone — nothing to pick yet. The When/Where section is dropped. |
| Products section | Dropped. |
| `pod_type` select | Fixed to `AUTO_POD_TYPE` (`'PAID'`) — an Auto Pod is physical and never free. |
| "Save as Draft" | Gone; the template is either saved or not. |

`makePodSchema(config)` swaps the club/venue/host/date rules for the template's own: a category is
required, the ticket price floor is 1, spots are 2–999 (the host attends free, so two is the fewest
that bill anyone) and at least one image. `lockCategory: true` shows the category read-only — a
Club Admin opening one for their club, or a template a host or club has already enrolled on (the
server refuses a category change from then on).

A sensible console config:

```ts
import { makeNativeParityPodConfig, type PodFormConfig } from '@duncit/pod-form';

const ADMIN_AUTO_POD_CONFIG: PodFormConfig = {
  ...makeNativeParityPodConfig({ showProducts: false }),
  autoPod: true,
  showHosts: false,
  showVenueSlot: false,
  showPlaceCharges: true,
  showReel: true,
  showFinance: true, // false on Partners, which has no finance settings
};
```

### `useAutoPodEditorState` — the editor plumbing

The twin of `usePodEditorState`: it seeds the form (`blankAutoPodFormValues` merged with
`createDefaults`, or `autoPodToFormValues(editingAutoPod)` when editing), builds the input with
`buildAutoPodInput`, and routes it to `submitCreate` or `submitUpdate(id, input)`. A content
refusal surfaces as `opError` with the rules it broke, exactly as for an ordinary pod.

```tsx
import {
  PodEditorPage,
  useAutoPodEditorState,
  type AutoPodTemplateRow,
} from '@duncit/pod-form';

const editor = useAutoPodEditorState({
  editingAutoPod, // (AutoPodTemplateRow & { id: string }) | null
  createDefaults: { super_category_id: club.super_category_id, sub_category_id: club.sub_category_id },
  submitCreate: (input) => createAutoPod({ variables: { input, club_id: club.id } }),

  onSaved: () => navigate('/auto-pods'),
});
```

## Peer dependencies, not dependencies

Everything — `react`, `@mui/material`, `@mui/x-date-pickers`, `react-hook-form`, `zod`,
`@hookform/resolvers`, `date-fns`, `@apollo/client` and `@duncit/utils` — is a **peer**. The package
ships no runtime deps of its own, so a consuming portal must already have all of them; adding this
package to a portal that lacks `@mui/x-date-pickers` fails at resolve time, not at render.

MUI throughout means this is portal-only. The mobile app's create-pod flow is Tamagui and shares
nothing here except the shape of the server input.

`clubCategoryKey`, `productMatchesClub` and `filterProductsForClub` are re-exports from
`@duncit/utils` — the club ⇄ product category match must stay identical in the portals, mWeb and
native, so it lives there and is only surfaced here for convenience. Import it from either place;
do not write a second matcher.

## Coverage gate

`vitest.config.ts` sets 100/100/100/100 across all of `src/**` (only barrels are excluded), so a new
branch anywhere — including `src/types.ts`, which is exercised at runtime through the option lists
and `blankPodFormValues` — needs a test before it lands. Genuinely unreachable defensive lines are
marked with `/* v8 ignore next */` and a reason, as in `schema.ts`; add the reason or the gate is
just being silenced.
