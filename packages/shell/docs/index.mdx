## Why this exists

Seventeen consoles is seventeen `main.tsx` files each nesting the same eight providers, seventeen
`App.tsx` files each with the same auth guard, seventeen `lib/session.ts` files each doing the same
`localStorage.getItem(tokenKey)` and SUPER_ADMIN role check, and seventeen login pages. Every one of
those was a real copy at some point. A fix to the redirect-after-login path landed in one portal and
not the other sixteen.

The shell holds the copy once. A portal's `main.tsx` is now a single `mountPortal({...})` call, its
`App.tsx` uses `createAuthed`, its `components/AppShell.tsx` is a ~30-line adapter over the shared
chrome, and its `lib/session.ts` is `createSession(tokenKey, requiredRoles)`.

It is also why the **17 portals share ONE fallback-icon bundle** at `packages/shell/src/fallback-icons/`
(rule 39): every portal renders its chrome through the shell, so 17 copies of the same bytes would be
17 chances to drift.

## Use it

`portals/ads-portal/src/main.tsx` in full:

```tsx
import { mountPortal } from '@duncit/shell';
import { createSessionUserLoader } from '@duncit/user-context';
import { logs } from '@duncit/logs';
import { urlConfigs } from './config/url-configs';
import { apolloClient } from './apollo';
import { appConfig } from './config/app-config';
import App from './App';

mountPortal({
  config: {
    key: appConfig.key,
    name: appConfig.name,
    tokenKey: appConfig.tokenKey,
    colorModeKey: appConfig.colorModeKey,
    accent: appConfig.accent,
  },
  apolloClient,
  graphqlUrl: urlConfigs.graphqlUrl,
  googleClientId: GOOGLE_CLIENT_ID,
  logsPortal: logs.portal['ads-portal'],
  loadUser: createSessionUserLoader(apolloClient),
  children: <App />,
});
```

And the route table (`portals/ai/src/App.tsx`):

```tsx
import { ProfilePage, createAuthed } from '@duncit/shell';

const authed = createAuthed({ getToken, wrap: (el) => <AppShell>{el}</AppShell> });

<Route path="/" element={authed(<WelcomePage />)} />
<Route path="/profile" element={authed(<ProfilePage />)} />
```

## Sample data

A portal's `appConfig` is the main input, and a nav tree is the piece every other feature derives
from. This is the shape `portals/admin/src/config/app-config.ts` holds.

```ts
import { parseEnvRoles, type AppConfig, type AppNavItem } from '@duncit/shell';

export const nav: AppNavItem[] = [
  { label: 'Dashboard', to: '/', icon: 'dashboard' },
  {
    label: 'Pods',
    icon: 'group',
    children: [
      { label: 'All Pods', to: '/pods' },
      { label: 'Pod Ideas', to: '/pod-ideas' },
    ],
  },
  { label: 'Clubs', to: '/clubs', icon: 'diversity_3' },
  { label: 'Settings', icon: 'settings', children: [{ label: 'Branding', to: '/settings/branding' }] },
];

export const appConfig: AppConfig = {
  key: 'admin',
  name: 'Admin',
  fullName: 'Duncit Admin',
  tokenKey: 'admin_token',
  colorModeKey: 'admin_color_mode',
  tagline: 'Run the platform',
  portalLabel: 'Admin Console',
  promoTitle: 'One console for every club, pod and payout',
  promoText: 'Approve pods, settle wallets and keep the category tree clean.',
  loginImage: 'https://ik.imagekit.io/duncit/portals/admin-login.jpg',
  requiredRoles: parseEnvRoles(import.meta.env.VITE_REQUIRED_ROLES, ['ADMIN', 'CLUB_ADMIN']),
```

`AppConfig` extends `PortalBootConfig`, so this one object feeds `mountPortal`, `createSession` and
`AppShell` — there is no second config to keep in sync.

## Worked examples

### `deriveSearchItems(nav)`

The header search is derived, never hand-written. Group headers (no `to`) contribute nothing
themselves but become the `section` of their children:

```js
[
  { label: 'Dashboard', to: '/' },
  { label: 'All Pods',  to: '/pods',              section: 'Pods' },
  { label: 'Pod Ideas', to: '/pod-ideas',         section: 'Pods' },
  { label: 'Clubs',     to: '/clubs' },
  { label: 'Branding',  to: '/settings/branding', section: 'Settings' }
]
```

Top-level items get **no** `section` key at all, not `section: undefined` — the flattening is
depth-aware, so a group nested two deep takes its immediate parent's label.

### `createSession('admin_token', ['ADMIN', 'CLUB_ADMIN'], 'Duncit Admin')`

```js
SUPER_ROLE                              // 'SUPER_ADMIN'

session.hasAppAccess(['ADMIN'])         // true   — matches a required role
session.hasAppAccess(['SUPER_ADMIN'])   // true   — passes every console, always
session.hasAppAccess(['HOST'])          // false
session.hasAppAccess([])                // false  — an empty role list is never access
session.hasAppAccess(null)              // false

session.accessDeniedMessage()
// 'You do not have access to Duncit Admin. Please contact your administrator.'
```

The `SUPER_ADMIN` bypass lives here and nowhere else. A portal writing
`roles.includes('SUPER_ADMIN')` locally is a second copy of the rule.

### Redirect safety — `getSafeRedirectPath`

```js
redirectPathFromLocation({ pathname: '/pods', search: '?edit=DUN-POD-10421', hash: '#media' })
// '/pods?edit=DUN-POD-10421#media'

getSafeRedirectPath('/pods?edit=DUN-POD-10421')     // '/pods?edit=DUN-POD-10421'
getSafeRedirectPath('//evil.example.com')           // ''  ← protocol-relative
getSafeRedirectPath('https://evil.example.com/pods')// ''  ← absolute, off-origin
getSafeRedirectPath('/login?denied=1')              // ''  ← would bounce back to auth
getSafeRedirectPath(null)                           // ''
```

Every rejection returns `''`, never `undefined` and never a thrown error — so the call site's
`getSafeRedirectPath(param) || '/'` fallback is the whole handling you need.

### `parseEnvRoles(raw, fallback)`

```js
parseEnvRoles('ADMIN, CLUB_ADMIN , ', ['ADMIN'])   // ['ADMIN', 'CLUB_ADMIN']   ← trimmed, blanks dropped
parseEnvRoles('', ['ADMIN'])                        // ['ADMIN']                 ← falls back
parseEnvRoles(undefined, ['ADMIN'])                 // ['ADMIN']                 ← non-string falls back
```

An env value that parses to **nothing** falls back rather than yielding `[]`, which matters because
`hasAppAccess([])` is `false` for everyone — an empty required-roles list would otherwise lock a
console shut for all non-super users.

## Live preview

There is no live preview on this page, and unlike the form packages that is not a temporary
limitation worth working around. The shell's components are the *outermost* layer of a running
console: `AppShell` calls `useNavigate`, the sidebar and header read the user context, `AppIcon`
resolves branding through Apollo, and `mountPortal` calls `createRoot` on a real DOM node and
**throws** when it is missing. Mounting any of it inside a docs page means recreating a portal
inside a portal — at which point the preview is testing the harness, not the shell.

The honest preview of `@duncit/shell` is a running console. Every one of the seventeen listed above
*is* that preview; open any of them and the header, sidebar, breadcrumbs, search and profile page on
screen are this package.

`docs-site` does have the `<Preview>` island runtime, so the small leaf pieces —
`AccountSummaryCard`, `SidebarUserCard` — could be mounted with a plain user object once the
package is a `docs-site` dependency. Those are worth adding. The full shell is not.

## `mountPortal` owns the provider stack — do not re-nest it

It renders, in order: `ApolloProvider` → `UserProvider` → `DuncitThemeProvider` →
`AppLocaleProvider` → MUI `LocalizationProvider` (AdapterDateFns) → `GoogleOAuthProvider` →
`BrowserRouter`, plus `PortalModeGate`, `PortalBranding` and `configureLogs`. Adding a second
`BrowserRouter` or `LocalizationProvider` inside a portal is the usual cause of "the date picker
lost its adapter" and "navigate() does nothing".

Two escape hatches exist so you don't have to: `wrap` (wraps the routed tree) and `extras` (siblings
rendered next to it). `themeExtend` layers on the shared theme. `rootId` defaults to `root` and
`mountPortal` **throws** if that node is missing, rather than silently rendering nothing.

Nunito is imported here from `@fontsource/nunito`, self-hosted — do not add a Google Fonts `<link>`
back into a portal's `index.html`.

## `RequireAuth` vs `createAuthed`

Same guard, two ergonomics. `createAuthed({ getToken, wrap })` returns an `authed(element)` helper
for route tables and is what most portals use; `RequireAuth` is the component form, used where the
guard wraps a whole subtree (`portals/admin/src/App.tsx` wraps its entire authed route block in one
`<RequireAuth>`). Pick `createAuthed` unless you need a single guard around many routes.

## Localization: your fallback layers over the shell's

`mountPortal` merges `{ ...SHELL_FALLBACK_FLAT, ...i18nFallback }`, so a portal passes only its own
namespace and can override a shared string without forking the shell bundle (rule 38). `SHELL_FALLBACK`
is the nested shape, `SHELL_FALLBACK_FLAT` the dotted-key one the locale provider consumes — pass the
flat one only when you are building the merged map yourself.

## Chrome, and the adapter each portal keeps

`AppShell` is the shared header + sidebar + breadcrumbs. Each portal still keeps a small local
`components/AppShell.tsx` because the wiring — its own `session.ts`, its own `appConfig`, its own
logout navigation — is genuinely per-portal. That adapter should stay thin; anything in it that
isn't portal-specific belongs here instead.

`deriveSearchItems` builds `HeaderSearch` entries from a nav tree — don't hand-write the item list.
`AppIcon` resolves branding icons through the shared fallback bundle; a remote branding icon that
404s must reach it with the `failed` flag from an `onError` handler, because a URL that fails at
request time is never empty (rule 39).

## Session, Apollo and redirects

`createSession(tokenKey, requiredRoles, fullName)` returns `getToken/setToken/clearToken/hasAppAccess/accessDeniedMessage`.
`SUPER_ROLE` (`SUPER_ADMIN`) passes every console regardless of app role — that check lives here, so
never re-implement `roles.includes('SUPER_ADMIN')` in a portal. `setToken` and `clearToken` emit
`authChanged` so the header/sidebar fill in after a client-side login without a refresh.

`createApolloClient` builds the client with `apolloErrorLink` attached; the link is exported
separately for clients built elsewhere (mWeb). Use `getSafeRedirectPath` / `redirectPathFromLocation`
for any post-login `?redirect=` handling — they reject absolute and off-origin targets, and a
hand-rolled version is an open redirect. `parseEnvRoles` turns a `VITE_*` roles string into the array
`createSession` wants.

## Chat with a coworker

Every portal's header carries it, so it lives here rather than in any one
console. One-to-one only: the pair of user ids IS the thread key, which is why
there is no threads collection and why two people can never end up with two
threads because they each started one.

What it does, and the reasoning worth keeping:

- **Reactions** are three fixed kinds — agree, disagree, love it — not free
  emoji. They are the answers that mean something at a glance, and a reader
  scanning a thread should not have to decode anybody's taste in pictures. One
  per person: reacting again takes it back, a different one replaces it, so the
  row is a summary of who felt what and never a click count. Free emoji belong
  IN the message, which the composer allows.
- **The emoji picker is a hand-picked list, not a dependency.** A full picker is
  a megabyte of sprite sheets and a search index for a problem nobody in a work
  chat has, and it would land in seventeen portal bundles.
- **Screen share replaces the camera track** (`RTCRtpSender.replaceTrack`), so
  the call carries on without a new offer — nothing to renegotiate mid-call.
  That needs a video sender to exist, so it is only offered on a VIDEO call. The
  browser's own "Stop sharing" bar ends the track without telling the page, so
  the camera is restored from `track.onended`, not only from our button.
- **Device pickers** read `enumerateDevices` only while the menu is open, and
  select with `deviceId: { exact }` — a device that has been unplugged should
  fail loudly rather than silently opening a different microphone.
- **The waveform** (`@audiowave/react`, bound to the REMOTE stream) exists
  because an audio call is otherwise a rectangle with a timer on it: nothing on
  screen says the line is carrying anything. It answers "can they hear me / are
  they still there" without anybody saying "hello?" twice.
- **Presence** is in-memory and socket-counted, with a ten-minute idle timer.
  The user can override their own status.
- **Deleted messages keep their row** and lose their words. A line that vanishes
  from the middle of a conversation reads as a bug.

## Screen sharing and remote control

LiveKit carries the screen and the data channel beside it. Credentials live in
**Tech → Environment Variables → LiveKit** (url, api key, api secret); with none
set the feature says so and stays off — it never falls back to anything.

The **API secret never leaves the server**. `staffScreenShareGrant` mints a
LiveKit access token — an ordinary JWT with a `video` grant, signed with the
`jsonwebtoken` the server already has rather than pulling in the LiveKit server
SDK for one signature. The room name is derived from the pair of people, so two
colleagues always land in the same room and nobody can ask for a token to
somebody else's.

`livekit-client` is imported with `await import()` inside the join, not at
module scope: it is a large dependency, every portal loads this shell, and
almost nobody shares a screen.

### What "remote control" means here — the boundary

A browser **cannot** move another machine's mouse, type into another tab, or
touch the browser's own chrome. No library changes that, LiveKit included; it is
the sandbox, not a missing feature. Anything claiming otherwise in a browser is
an extension or a native agent.

What this does instead: both people are inside OUR portals, which is code we
control, so a granted click is **replayed** inside the receiving app —
dispatched at the document position under it — a keystroke goes to whatever that
page has focused, and a scroll offset moves that window. Inside a Duncit console
that is indistinguishable from being driven. At the edge of the page it stops,
and the UI says so rather than pretending.

Everything visual is an overlay: live cursor, laser, freehand annotation and a
ripple where the other person clicked. Positions travel as **fractions of the
viewport, never pixels** — the two ends are different sizes at different zooms,
and a pixel coordinate would land somewhere else while somebody is driving.

Control is asked for, granted and revoked explicitly, and only the SHARER
decides. That rule is enforced in `useRemoteControl`, not in the toolbar,
because a UI check is a suggestion.

Cursor, drawing and scroll frames go out **lossy** (`reliable: false`): they are
only useful while current, and a reliable channel would replay stale ones after
a hiccup, so the cursor would crawl through where it used to be. Control
handover is the exception and is sent reliably.

## Coverage gate

100% statements / functions / lines, with `branches: -3`. That negative threshold caps the number of
*uncovered* branches at three (the documented, unreachable guards in `HeaderSearch.tsx` and
`AppSidebar/nav-items.tsx`), so a fourth uncovered branch fails the run even though the percentage
barely moves. `npm test` also runs `verify-fallback-icons.mjs` against `src/fallback-icons` before
vitest — a missing icon fails the test script, not just the build.
