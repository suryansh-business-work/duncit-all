## Why this exists

Seventeen consoles is seventeen `main.tsx` files each nesting the same eight providers, seventeen
`App.tsx` files each with the same auth guard, seventeen `lib/session.ts` files each doing the same
`localStorage.getItem(tokenKey)` and SUPER_ADMIN role check, and seventeen login pages. Every one of
those was a real copy at some point. A fix to the redirect-after-login path landed in one portal and
not the other sixteen.

The shell holds the copy once. A portal's `main.tsx` is now a single `mountPortal({...})` call, its
`App.tsx` uses `createAuthed`, its `components/AppShell.tsx` is a ~30-line adapter over the shared
chrome, and its `lib/session.ts` is `createSession(tokenKey, requiredRoles)`.

It is also why the **17 portals share ONE fallback-icon bundle** at `packages/shell/src/fallback-icons/`
(rule 39): every portal renders its chrome through the shell, so 17 copies of the same bytes would be
17 chances to drift.

## Use it

`portals/ads-portal/src/main.tsx` in full:

```tsx
import { mountPortal } from '@duncit/shell';
import { createSessionUserLoader } from '@duncit/user-context';
import { logs } from '@duncit/logs';
import { urlConfigs } from './config/url-configs';
import { apolloClient } from './apollo';
import { appConfig } from './config/app-config';
import App from './App';

mountPortal({
  config: {
    key: appConfig.key,
    name: appConfig.name,
    tokenKey: appConfig.tokenKey,
    colorModeKey: appConfig.colorModeKey,
    accent: appConfig.accent,
  },
  apolloClient,
  graphqlUrl: urlConfigs.graphqlUrl,
  googleClientId: GOOGLE_CLIENT_ID,
  logsPortal: logs.portal['ads-portal'],
  loadUser: createSessionUserLoader(apolloClient),
  children: <App />,
});
```

And the route table (`portals/ai/src/App.tsx`):

```tsx
import { ProfilePage, createAuthed } from '@duncit/shell';

const authed = createAuthed({ getToken, wrap: (el) => <AppShell>{el}</AppShell> });

<Route path="/" element={authed(<WelcomePage />)} />
<Route path="/profile" element={authed(<ProfilePage />)} />
```

## `mountPortal` owns the provider stack — do not re-nest it

It renders, in order: `ApolloProvider` → `UserProvider` → `DuncitThemeProvider` →
`AppLocaleProvider` → MUI `LocalizationProvider` (AdapterDateFns) → `GoogleOAuthProvider` →
`BrowserRouter`, plus `PortalModeGate`, `PortalBranding` and `configureLogs`. Adding a second
`BrowserRouter` or `LocalizationProvider` inside a portal is the usual cause of "the date picker
lost its adapter" and "navigate() does nothing".

Two escape hatches exist so you don't have to: `wrap` (wraps the routed tree) and `extras` (siblings
rendered next to it). `themeExtend` layers on the shared theme. `rootId` defaults to `root` and
`mountPortal` **throws** if that node is missing, rather than silently rendering nothing.

Nunito is imported here from `@fontsource/nunito`, self-hosted — do not add a Google Fonts `<link>`
back into a portal's `index.html`.

## `RequireAuth` vs `createAuthed`

Same guard, two ergonomics. `createAuthed({ getToken, wrap })` returns an `authed(element)` helper
for route tables and is what most portals use; `RequireAuth` is the component form, used where the
guard wraps a whole subtree (`portals/admin/src/App.tsx` wraps its entire authed route block in one
`<RequireAuth>`). Pick `createAuthed` unless you need a single guard around many routes.

## Localization: your fallback layers over the shell's

`mountPortal` merges `{ ...SHELL_FALLBACK_FLAT, ...i18nFallback }`, so a portal passes only its own
namespace and can override a shared string without forking the shell bundle (rule 38). `SHELL_FALLBACK`
is the nested shape, `SHELL_FALLBACK_FLAT` the dotted-key one the locale provider consumes — pass the
flat one only when you are building the merged map yourself.

## Chrome, and the adapter each portal keeps

`AppShell` is the shared header + sidebar + breadcrumbs. Each portal still keeps a small local
`components/AppShell.tsx` because the wiring — its own `session.ts`, its own `appConfig`, its own
logout navigation — is genuinely per-portal. That adapter should stay thin; anything in it that
isn't portal-specific belongs here instead.

`deriveSearchItems` builds `HeaderSearch` entries from a nav tree — don't hand-write the item list.
`AppIcon` resolves branding icons through the shared fallback bundle; a remote branding icon that
404s must reach it with the `failed` flag from an `onError` handler, because a URL that fails at
request time is never empty (rule 39).

## Session, Apollo and redirects

`createSession(tokenKey, requiredRoles, fullName)` returns `getToken/setToken/clearToken/hasAppAccess/accessDeniedMessage`.
`SUPER_ROLE` (`SUPER_ADMIN`) passes every console regardless of app role — that check lives here, so
never re-implement `roles.includes('SUPER_ADMIN')` in a portal. `setToken` and `clearToken` emit
`authChanged` so the header/sidebar fill in after a client-side login without a refresh.

`createApolloClient` builds the client with `apolloErrorLink` attached; the link is exported
separately for clients built elsewhere (mWeb). Use `getSafeRedirectPath` / `redirectPathFromLocation`
for any post-login `?redirect=` handling — they reject absolute and off-origin targets, and a
hand-rolled version is an open redirect. `parseEnvRoles` turns a `VITE_*` roles string into the array
`createSession` wants.

## Coverage gate

100% statements / functions / lines, with `branches: -3`. That negative threshold caps the number of
*uncovered* branches at three (the documented, unreachable guards in `HeaderSearch.tsx` and
`AppSidebar/nav-items.tsx`), so a fourth uncovered branch fails the run even though the percentage
barely moves. `npm test` also runs `verify-fallback-icons.mjs` against `src/fallback-icons` before
vitest — a missing icon fails the test script, not just the build.
