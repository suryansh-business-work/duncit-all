## Why this exists

Picking a slot happened in eleven places — pod create in three portals, mWeb and the app;
venue-rejected resubmit in mWeb and the app; and four onboarding/meeting pickers — and every
one of them had its own answer. The portals showed a flat `<TextField select>` dropdown of
every slot at once. mWeb and the app showed a horizontal rail of day chips over a grid of time
tiles. Each copy re-implemented `dayKey`, `dayLabel` and the price label, and they had already
drifted: `₹1,500` in one, `₹1500` in another, `h:mm a` here and `hh:mm a` there.

Worse, all of them bucketed slots by the **device's** calendar day while the server matches
venue holidays in IST. A 11:30 PM IST slot lands on the previous day for a viewer in London,
so the two sides disagreed about which day a slot belonged to.

This package is the single answer: one set of helpers that group and label slots through the
admin-configured formatter, and two thin views — MUI and Tamagui — that render the identical
two steps from those helpers.

The venue owner's side of the same coin lives here too. Which slot may be added, and what a
recurring run creates, used to be answered in the Partners console alone; the moment mWeb and
the native app grew the same calendar, those rules had to move somewhere all three could
import — and this package is the one framework-free module the app already compiles.

## Where each piece lives

| Import | Contains | Used by |
| --- | --- | --- |
| `@duncit/slots` | Types and pure functions. No React, no toolkit. | everything, including Node and tests |
| `@duncit/slots/mui` | `SlotCalendar` on MUIX `DateCalendar` | the portals and mWeb |
| — | the app renders the same logic through its own Tamagui view in `app/mobile-app/src/components/slots/` | the app |
| `@duncit/availability-calendar` | the MUI venue-availability editor built on the rules below | Partners, Onboarding, mWeb |

The Tamagui view lives in the app rather than here on purpose: the native app typechecks and
bundles linked packages from their own SOURCE, so a `react`/`tamagui` import inside this package
resolves by walking up from `packages/slots/` and finds nothing in CI or Docker. Keeping the
view in the app is what every other native-consumed package already does — the two calendars
still render the same steps from the same helpers. The same constraint is why the rules below
import nothing but `date-fns`, and why the app compiles them with `noUncheckedIndexedAccess`
on: every index read in here is guarded.

## The one slot shape

Venue availability and onboarding meeting slots normalise into `CalendarSlot`, so one calendar
serves both:

```ts
interface CalendarSlot {
  id: string;              // meeting slots have no id — their start_at IS the identity
  start_at: string;
  end_at?: string | null;  // meetings have an implied length
  price?: number | null;   // meetings are free
  caption?: string | null; // the venue space, or "Currently booked for this pod"
  disabled?: boolean;      // a meeting slot the server marked unavailable
}
```

## Worked example

```tsx
import { SlotCalendar } from '@duncit/slots/mui';
import { useDateFormat } from '@duncit/app-settings';

const fmt = useDateFormat();

<SlotCalendar
  slots={venueSlots.map((s) => ({
    id: s.id,
    start_at: s.start_at,
    end_at: s.end_at,
    price: s.price,
    caption: s.space_label,
  }))}
  loading={loading}
  selectedSlotId={value}
  onPick={(slot) => field.onChange(slot.id)}
  fmt={fmt}
  labels={t.slots}
  required
/>;
```

`labels` is **required** and has no English default. Rule 38 forbids shipping literals in
shared UI, so each surface passes its own translated copy — `mweb.slots.*` for mWeb and the
app, `shell.slots.*` for the portals.

## What the helpers guarantee

- `groupSlotsByDay` buckets in the **admin** zone via `fmt.dayKey`, so every surface agrees
  which day a late-night slot belongs to. Slots with an unparseable `start_at` are dropped
  rather than collected under a `''` day.
- `resolveSlotDay` resolves a **day**, never a slot: an explicit tap wins, then the day holding
  the current selection, then the first day with slots. It deliberately never auto-selects a
  "nearest" slot — doing so on hydration would silently re-route a live booking and push a
  partner-venue pod back to `PENDING`.
- `withCurrentSlot` re-offers the slot a pod already booked. A booked slot is no longer
  *available*, so without it an edit form would clear a valid saved choice.
- `slotDayBounds` derives the calendar's min/max from the data, so the arrows cannot page into
  months that can never hold a slot — no hardcoded horizon.

## Slot draft / whole-day window

The venue owner's add-slot form is judged by one pure function, so the MUI drawer and the
native twin cannot disagree about which slot is addable.

| Export | Signature | Meaning |
| --- | --- | --- |
| `emptyDraft` | `(date: Date) => SlotDraft` | A draft seeded on the clicked day: no times, no price, no space picked (`NO_SPACE`, because `''` is a real space — the whole venue). |
| `checkSlotDraft` | `(draft, now) => { start; end } \| SlotIssueCode` | The window the draft asks for, or the ONE thing wrong with it. `now` is a parameter so the same draft can be re-judged against a moving clock. |
| `isDraftIncomplete` | `(code) => boolean` | True for `pickDates` / `pickSlotTimes` — unfinished, not wrong. Say it on submit; never shout it mid-typing. |
| `minTimeOn` / `minEndTime` | `(…, now) => Date \| undefined` | The picker bounds: "now" on today, a minute past the start while the slot sits on one day. An hour that has gone by is never offered. |
| `slotIssueMessage` | `(code, t) => string` | The single place a code becomes a sentence — literal `availability.*` keys, the namespace every surface ships. |
| `wholeDayWindow` | `(startDate, endDate, now?) => { start; end }` | A whole-day booking across a date range. Today's starts five minutes from now, never at a midnight that has passed. |
| `slotCoversDay` / `slotCoveredDays` | `(slot, day)` / `(slot)` | Which calendar cells a slot touches. The end is exclusive, so a block ending at midnight does not claim the next day. |
| `MAX_FUTURE_DAYS` | `60` | Mirrors the server cap in `validateSlotWindow`. |

```ts
import { checkSlotDraft, emptyDraft, slotIssueMessage } from '@duncit/slots';

const now = new Date('2026-09-14T14:30:00');
const draft = {
  ...emptyDraft(new Date('2026-09-14T00:00:00')),
  startTime: new Date('2026-09-14T09:00:00'),
  endTime: new Date('2026-09-14T10:00:00'),
};

checkSlotDraft(draft, now);        // 'startInFuture' — 9am is already gone at 2:30pm
slotIssueMessage('startInFuture', t); // "Start time must be in the future."
```

## Recurring availability

`generateRecurringSlots` is the whole engine behind the recurring dialog: the live preview,
the "Create N slots" label and the batch actually sent to `createVenueSlots` all come from one
call, so they can never drift. It walks every day in the range, keeps the chosen weekdays,
skips weekly-offs / holidays / past windows / anything beyond the advance cap, and emits one
slot per time range per space, each priced for that space.

```ts
import {
  generateRecurringSlots,
  readVenueSettings,
  recurringErrorMessage,
} from '@duncit/slots';

// A Koramangala turf: two courts, weekday evenings, Wednesday the 16th a holiday.
const settings = readVenueSettings({
  operating_hours: { open: '06:00', close: '23:00' },
  holidays: ['2026-09-16'],
  rules: { max_advance_days: 60, buffer_minutes: 0 },
});

const run = generateRecurringSlots(
  {
    startDate: new Date('2026-09-14T00:00:00'),
    endDate: new Date('2026-09-18T00:00:00'),
    weekdays: [1, 2, 3, 4, 5],
    wholeDay: false,
    timeSlots: [
      { start: '18:00', end: '20:00' },
      { start: '20:00', end: '22:00' },
    ],
    spaces: [
      { label: 'Court 1', capacity: 10, price: 399 },
      { label: 'Court 2', capacity: 10, price: 599 },
    ],
    bufferMinutes: settings.rules.buffer_minutes,
    skipWeeklyOff: true,
    skipHolidays: true,
  },
  settings,
  new Date('2026-09-14T06:00:00'),
);

run.summary.total;             // 16 — 4 days × 2 windows × 2 courts (the holiday skipped)
run.summary.estimatedRevenue;  // 7984
run.summary.skippedHolidays;   // 1
run.errors;                    // []
```

A run that cannot be generated comes back with `slots: []` and one or more **codes** in
`errors` — `'pickDates'`, `'pickWeekday'`, `'addTimeSlot'`, `'invalidTime'`, `'endAfterStart'`,
`'beforeOpen'`, `'afterClose'`, `'overlap'`, `'bufferGap'`, `'addSpace'`, `'negativePrice'`,
`'endDateAfterStart'`. Codes rather than sentences, because the engine is framework-free and
shared with the native app; `recurringErrorMessage(code, t, settings)` turns one into the
sentence the dialog shows, reading the venue's hours and buffer for the ones that name them:

```ts
recurringErrorMessage('bufferGap', t, settings);
// "Keep at least a 30-minute gap between time slots."
```

`weekdayLabels(t)` gives the repeat picker its seven short and full names (Sunday first, the
order `Date#getDay` counts in), and the settings helpers normalise what the server sends:
`readVenueSettings` fills a venue registered before settings existed with the defaults
(`DEFAULT_VENUE_RULES`, `DEFAULT_AUTO_EXTEND`), `effectiveMaxAdvance` clamps
`rules.max_advance_days` into `[1, MAX_ADVANCE_DAYS_CAP]`, and `timeToHHMM` / `hhmmToDate` /
`parseHHMM` move between a picker's `Date` and the `'HH:mm'` the server stores.
