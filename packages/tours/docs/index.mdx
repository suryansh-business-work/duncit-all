What each guided tour says and which tours a user has already seen. No overlay,
no storage, no framework — mWeb renders React Joyride and native renders
`rn-tourguide` (a react-native-svg scrim with the highlight cut out of it), two
libraries with different geometry and animation, but the *content and sequence*
are written once here.

That split is deliberate. Rule 27 asks mWeb and native to match, and with two
different tour libraries pixel parity is not achievable; identical steps in an
identical order is.

## Adding a tour

One entry in `TOURS`, plus the matching anchors on the screen. Neither overlay
changes — that is the "extensible for future screens" requirement:

```js
{
  id: 'club',
  titleKey: 'mweb.tours.club.title',
  captionKey: 'mweb.tours.club.caption',
  path: '/clubs',            // mWeb route
  nativeRoute: 'Home',       // native stack screen — must open with no params
  nativeTab: 'Clubs',        // …and, when the landing is a bottom tab, which one
  steps: [
    {
      anchor: 'club-follow',
      titleKey: 'mweb.tours.club.follow.title',
      bodyKey: 'mweb.tours.club.follow.body',
    },
  ],
}
```

**The registry holds structure, never words.** Each entry names catalogue keys
under `mweb.tours.*`, and whichever overlay is drawing resolves them with its
own translator — so a tour translates like every other screen (rule 38) and mWeb
and native cannot describe the same screen differently. Add a tour by adding its
copy to `packages/i18n/src/bundles/mweb.ts` first, then pointing the entry at it;
the keys are written out in full because `verify-translation-keys.mjs` greps
source for the literal string.

**A tour's steps must all live on ONE screen.** Both runners resolve a tour
against what has rendered and then freeze, so a step whose element only appears
on the next screen never resolves: the tour opens on the reachable steps alone
and records itself as shown. That rules out splitting a walkthrough across a
list and a detail screen, or across the pages of a wizard.

**A landing that needs an id is not a landing.** Club, pod and booking tours all
describe a screen whose URL carries an id, so they land on the list that leads
there and stay armed — nothing opens until the user picks something, which is
why those captions end in "open any club/pod/booking to start". Neither surface
times out waiting.

`anchor` is the contract between copy and screen. mWeb tags the element
`data-tour="club-follow"`; native wraps it in `<TourAnchor tour="club"
anchor="club-follow">`. Anchors are unique across every tour, which the suite
asserts — a duplicate would make a step highlight the wrong element on whichever
screen rendered first.

Neither surface hard-codes a step number. mWeb resolves selectors and native
resolves anchor names, both against what actually rendered, and a step whose
element is absent is dropped — a screen legitimately varies (no clubs yet → no
clubs section). Native then *freezes* that resolved list before opening the
overlay, because `rn-tourguide` addresses a highlight by its zone number: a
section arriving mid-walkthrough would otherwise renumber every step behind it.

## Completion state

```js
tourStorageKey('66f1a2…')          // 'duncit.tours.completed.66f1a2…'
readCompletedTours(raw)            // TourId[] — never throws
markTourCompleted(completed, 'home')
shouldAutoStartHomeTour(completed, isFirstSignup)
```

**Keyed by user id, and that matters.** Every other persisted flag in these apps
is device-scoped with no user id, so a second person signing in on the same
phone or browser inherits the first person's state. For a "show this once" flag
that is the difference between a new user getting their tour and silently never
seeing it.

`readCompletedTours` treats anything unreadable — absent, empty, malformed JSON,
a tampered array — as "none completed". A corrupt value must not cost a user
their tour and must never throw during app start.

Skipping counts as completed. The brief says "shown once by default", and a user
who dismissed the tour has been shown it; restarting is always available from
the Tour Guide centre.

## What is NOT here

Storage itself. mWeb passes `localStorage`, native passes AsyncStorage, and the
package stays dependency-free so native can import it without pulling a web API.
The auto-start decision is a pure function of (completed, isFirstSignup) — each
surface supplies both.
