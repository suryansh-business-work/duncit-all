## Why this exists

Every portal dashboard had a KPI tile. Every detail page had a label/value row, a spinner, an
error `Alert` and a "not found" `Alert`, in that order. Every list page had a `useState` +
`useEffect` + `setTimeout` debounce for its search box. None of them were quite the same: the
tile was `SummaryTiles` in admin, `StatGrid` in ads-portal, a KPI card in crm; the guard trio
was re-typed on every page that loads one entity.

This package holds one copy of each. It is the MUI layer above `@duncit/utils`, which is the
package's only runtime dependency — `QueryGuard` uses `parseApiError` from it rather than
re-deriving the message.

## Use it

From `portals/ads-portal/src/pages/ads/AdDetailsPage.tsx` and
`portals/admin/src/pages/dashboard/SummaryTiles.tsx`:

```tsx
import { BackHeader, QueryGuard, StatusChip, StatCard } from '@duncit/ui';

<BackHeader title={ad.title} eyebrow="Ad" backTo="/ads" actions={<EditButton />} />

<QueryGuard loading={loading && !ad} error={error} notFound={!ad}>
  {() => (
    <>
      <StatusChip status={ad.status} />
      <StatCard label="Total spend" value={formatINR(ad.spend)} layout="split" />
    </>
  )}
</QueryGuard>;
```

`children` accepts a **function** as well as a node. Pass a function whenever the content
dereferences the entity — it defers evaluation past the `notFound` branch, so
`{() => <div>{ad.title}</div>}` cannot throw on a null `ad`.

## Worked examples

Real values, produced by running the exports (jsdom + `@testing-library/react`), not
paraphrased.

`usageColor` — the tech server's usage-bar convention:

```ts
usageColor(42);  // 'success'
usageColor(78);  // 'warning'
usageColor(91);  // 'error'
usageColor(100); // 'error'
```

`mergeSx` — never a spread, always an array, so a caller's override wins without dropping
the component's defaults:

```ts
mergeSx({ p: 2 });
// { p: 2 }                                   ← no override, defaults returned as-is

mergeSx({ p: 2, borderRadius: 3 }, { p: 0 });
// [{ p: 2, borderRadius: 3 }, { p: 0 }]      ← borderRadius survives; p is overridden

mergeSx({ p: 2 }, [{ mb: 1 }, { color: 'red' }]);
// [{ p: 2 }, { mb: 1 }, { color: 'red' }]    ← an array override is flattened, not nested
```

`STATUS_CHIP_COLORS` and what a rendered `StatusChip` resolves to:

```ts
STATUS_CHIP_COLORS;
// {
//   APPROVED: 'success', REJECTED: 'error', DENIED: 'error',
//   PENDING: 'warning',  DRAFT: 'warning',  SUBMITTED: 'info',
// }
```

```tsx
<StatusChip status="PENDING" />
// <Chip> class MuiChip-colorWarning, label "PENDING"

<StatusChip status="ESCALATED" />
// MuiChip-colorDefault — an unmapped status falls back to `fallbackColor` ('default')

<StatusChip status="SUBMITTED" colorMap={{ ...STATUS_CHIP_COLORS, SUBMITTED: 'warning' }} />
// MuiChip-colorWarning
```

`QueryGuard`, all four branches (the error text is `parseApiError`'s, from `@duncit/utils`):

```tsx
<QueryGuard loading>{() => <PodBody />}</QueryGuard>
// → a centred <CircularProgress /> in a Stack with py: 6

<QueryGuard error={{ graphQLErrors: [{ message: 'Pod not found' }] }}>…</QueryGuard>
// → <Alert severity="error">Pod not found</Alert>

<QueryGuard error={new Error('Network request failed')}>…</QueryGuard>
// → <Alert severity="error">Unable to connect to server. Please check your internet
//    connection and try again.</Alert>       ← parseApiError recognises the offline shape

<QueryGuard notFound notFoundText="This pod no longer exists." notFoundSeverity="warning">…</QueryGuard>
// → <Alert severity="warning">This pod no longer exists.</Alert>  (MuiAlert-standardWarning)

<QueryGuard>{() => <div>Weekend Pottery Pod</div>}</QueryGuard>
// → Weekend Pottery Pod
```

`LanguageSelect` with a single configured language renders **nothing** — the container comes
back as an empty string, not a one-option dropdown. `showSingle` opts out of that, for a surface
whose job is to say which language is set rather than to offer a choice:

```tsx
render(<LanguageSelect value="en" options={[{ code: 'en', label: 'English' }]} onChange={fn} />);
// container.innerHTML === ''

render(<LanguageSelect showSingle value="en" options={[{ code: 'en', label: 'English' }]} onChange={fn} />);
// → the select, with English in it — what the taskbar's clock tray renders
```

### `ImagePreview`

A remote document/photo as a square thumbnail that opens full-screen on click. Use it
anywhere a review screen used to render an "open in new tab" button for a KYC document —
the reviewer stays in the dialog.

```tsx
import { ImagePreview } from '@duncit/ui';

<ImagePreview src={host.passport_photo_url} label="Passport photo" />;
```

| Prop | Type | Required | Default | Meaning |
| --- | --- | --- | --- | --- |
| `src` | `string` | yes | — | Remote image URL. |
| `label` | `string` | yes | — | Accessible name **and** the caption under the thumbnail. Drives `Enlarge {label}` / `Close {label}`. |
| `size` | `number` | no | `96` | Thumbnail edge length in px (square). |

Open state is internal — there is nothing to wire at the call site. A `src` that fails to
load swaps the thumbnail for a plain external link to the same URL, so a document that has
been deleted or moved server-side is still reachable instead of rendering a blank box.

### `Loader` — the one spinner

Every surface used to hand-roll the same three lines, which is why some waits
showed a spinner, some showed nothing, and no two were the same size. The
wrapper is a live `status` region carrying the label, so a wait is audible where
the spinner is the only thing on screen.

| Prop | Type | Required | Default | Meaning |
| --- | --- | --- | --- | --- |
| `variant` | `'block' \| 'page' \| 'inline' \| 'overlay'` | no | `'block'` | `block` = a section with nothing to draw yet; `page` = the whole viewport (boot); `inline` = beside a control; `overlay` = content refreshing under a scrim. |
| `size` | `number` | no | 40 / 44 / 16 / 32 per variant | Spinner diameter. |
| `label` | `string` | no | `'Loading…'` | What is being waited on. Localize it (rule 38). |
| `showLabel` | `boolean` | no | `false` | `inline`/`overlay`: draw the label beside the spinner. |
| `sx` | `SxProps<Theme>` | no | — | Merged over the variant's layout. |

`LoadingOverlay` wraps both halves — `open`, `children`, plus every `Loader`
prop — because the scrim is absolute and its parent has to be positioned, which
is the line every call site forgot.

### `TopProgressBar` — the console-wide answer to "did that do anything?"

A three-pixel indeterminate bar across the top of the viewport, above dialogs
because most actions are pressed inside one. The portals mount it once via
`@duncit/shell`'s `GlobalProgress`, wired to the Apollo transport's in-flight
count — nothing else has to opt in.

| Prop | Type | Required | Default | Meaning |
| --- | --- | --- | --- | --- |
| `busy` | `boolean` | yes | — | True while anything is in flight. |
| `label` | `string` | no | `'Loading…'` | Screen-reader name. |
| `sx` | `SxProps<Theme>` | no | — | Style override. |

It appears only after 180ms and then stays 400ms: below that a cached answer
flashes a bar, and a page firing several queries strobes.

## `StatusChip` — the default map has already drifted

`STATUS_CHIP_COLORS` is the repo-wide default for the approval vocabulary
(`APPROVED`/`REJECTED`/`DENIED`/`PENDING`/`DRAFT`/`SUBMITTED`). Several portals genuinely
disagree with it today: onboarding cards and products `brandStatus` render `SUBMITTED` as
warning, products renders `DRAFT` as default.

When migrating one of those call sites, pass a full `colorMap` that preserves the colours it
shows now. `colorMap` is a **full replacement, not a merge** — that is deliberate, so a domain
vocabulary (refund, meeting, campaign, lead stage) stays exactly as authored. To change one
entry of the default, spread it:

```tsx
<StatusChip status={s} colorMap={{ ...STATUS_CHIP_COLORS, SUBMITTED: 'warning' }} />
```

Silently adopting the defaults during a migration is a visual regression that no test catches.

## Picking a layout instead of writing a new component

`StatCard` and `InfoRow` are supersets of the shapes that already existed, selected by a
`layout` / `variant` prop. Reach for one of these before adding a component:

| Component | Value | Where it came from |
| --- | --- | --- |
| `StatCard` | `default` | finance, tech, partners-app, onboarding, crm dashboards |
| `StatCard` | `valueFirst` | support, challenge-portal dashboards |
| `StatCard` | `split` | admin `SummaryTiles` |
| `InfoRow` | `stacked` | dialog / detail `Field` rows |
| `InfoRow` | `inline` | fixed-width label then value |
| `InfoRow` | `split` | space-between label/value, `bold` for total rows |

`usageColor(percent)` is the tech server convention for a usage bar: `error` at ≥90,
`warning` at ≥75, otherwise `success`.

`ChipList({ items, empty })` draws a list of short values — hashtags, perks, what a pod
offers — as outlined chips, or the caller's `empty` text when there is nothing to draw.
It lives here because two read-only summaries of the SAME Auto Pod render it: the
template's review step in `@duncit/pod-form` and the admin console's offer page. A reader
compares those two, so a second copy is the drift rule 40 exists to stop.

## `mergeSx` — always merge, never overwrite

Every component here takes an `sx` override and merges it through `mergeSx(defaults, override)`,
which flattens both sides into an array so later entries win. That is what lets a caller tweak
one property without losing the component's built-in styles.

If you add a component to this package, route its `sx` prop through `mergeSx` too. Spreading
(`{ ...defaults, ...sx }`) silently drops the defaults whenever a caller passes an array or a
callback `sx`, which MUI fully supports.

## `RICH_TEXT_BODY_SX` — the reader's half of the rich-text editor

`@duncit/rich-text` styles what an author sees. This is what a **reader** sees: the same
element styling for HTML rendered outside the editor, through `dangerouslySetInnerHTML` on the
policy pages in mWeb and partners-app.

```tsx
import { RICH_TEXT_BODY_SX, mergeSx } from '@duncit/ui';

<Box
  sx={mergeSx(RICH_TEXT_BODY_SX, { '& h1, & h2, & h3': { fontWeight: 900 } })}
  dangerouslySetInnerHTML={{ __html: policy.content }}
/>;
```

It lives here rather than in `@duncit/rich-text` because mWeb and partners-app render this HTML
without ever mounting the editor, and must not pull tiptap into their bundles to style it.

Keep it in step with the editor: tables are the reason it exists as a shared export. A browser
gives a bare `<table>` no borders at all, so a table authored in Legal and read on a policy
page reads as prose — indistinguishable from a table that never saved — unless this block is
applied.

## Peer dependencies, including the router

`react`, `react-dom`, `@mui/material`, `@mui/icons-material` and `react-router-dom` are all
peers — nothing here bundles a second React or MUI. The router peer is easy to miss: `BackButton`
renders `component={RouterLink}` when given `to`, so a `BackHeader`/`BackButton` used with `to`
**must be inside a router context** or it throws. Pass `onClick`/`onBack` instead if there is no
router (that path renders a plain `<Button>`).

## `useDebouncedValue` is not needed inside a table

`DuncitTable` already debounces its own search box before `fetchRows` sees the query state.
Use `useDebouncedValue` for the standalone filter inputs that sit outside a table — adding it on
top of a `DuncitTable` search only stacks two delays.

## `PodParticipationTimeline` — one booking's story, drawn once

What happened to one person's place in one pod: joined, backed out (once or several times,
possibly partially), the spot filled or not, the refund, attendance, or the pod being cancelled
out from under them. mWeb's Pod History, Finance's Backout Refunds detail and Admin's pod
attendee rows all render **this** component, because three MUI copies of one workflow is how
three screens start telling the same person three different stories about the same booking.

The nodes and the words both come from `@duncit/utils` — `buildPodParticipationTimeline` builds
the tree, `timelineCopy` names each node — so the native app draws the identical story in
Tamagui from the same model (rule 27).

| Prop | Type | Required | Default | Meaning |
| --- | --- | --- | --- | --- |
| `input` | `PodParticipationInput` | yes | — | Build it with `participationInputFrom(participation, podDateTime)` — the API returns the fields under `participation` on `PodMember`, `BackoutRefundRequest` and `AdminPodAttendee`. |
| `formatDateTime` | `(value: string) => string` | yes | — | Admin-configured formatter; mWeb passes `useDateFormat().formatDateTime`, the portals pass their own. |
| `highlightBackoutNo` | `string` | no | — | Marks one branch as the request this screen is about. Finance passes the DUN-BKO id of the row it was opened from, which is what proves the line and the row are the same request. |

```tsx
import { PodParticipationTimeline } from '@duncit/ui';
import { participationInputFrom } from '@duncit/utils';

<PodParticipationTimeline
  input={participationInputFrom(request.participation, request.pod?.pod_date_time)}
  formatDateTime={fmtDate}
  highlightBackoutNo={request.backout_no}
/>;
```

The branches **nest**: a backout leads to the spot being filled or not, and each of those leads
somewhere else again. A flat list can show the same events but not which followed from which,
and "why was I not refunded" is a question only the shape answers.

## `SpotsStepper` — one slider for a pod's size, wherever it is set

A pod's capacity is picked twice: once in Create-a-Pod, and again in Edit Pod once the pod is
live and the host discovers the space holds more people than they published. Those were about
to be two sliders. They are one.

```tsx
import { SpotsStepper, mwebSpotsLabels } from '@duncit/ui';

<SpotsStepper
  labels={mwebSpotsLabels(t)}
  value={spots}
  onChange={setSpots}
  min={limits.min}
  max={limits.max}
  slidable={limits.slidable}
  boundsHint={`The space this pod booked holds ${limits.venue_capacity} people.`}
/>;
```

| Prop | Type | Required | Default | Meaning |
| --- | --- | --- | --- | --- |
| `value` | `number` | yes | — | Total spots, the host's own seat included. |
| `onChange` | `(next: number) => void` | yes | — | Already clamped to `[min, max]`. |
| `labels` | `SpotsStepperLabels` | yes | — | The surface's words — see below. |
| `min` / `max` | `number` | no | `0` / `10000` | The range. |
| `slidable` | `boolean` | no | `false` | True renders the slider; false, the ± stepper. |
| `boundsHint` | `string` | no | — | Where the floor and ceiling come from. Outranks `labels.hint`. |
| `readOnly` | `boolean` | no | `false` | Capacity is fixed — render the number, no control. |
| `error` | `string` | no | — | Field error under the control. |

It ships **no copy of its own**: mWeb's `mweb.createPod.*` keys are already translated in
every locale, and moving them into a `ui.*` namespace would throw that away. Each surface
hands over its own namespace instead — `mwebSpotsLabels(t)` for mWeb and the native app,
`shellSpotsLabels(t)` for the portals, which ship the same words word-for-word (rule 27).

**Where the range comes from matters.** Creating a pod, it is derived on the client from the
slot being picked (`spotsBounds` in `@duncit/utils`). Editing a live one, the slot is
BOOKED — `venueAvailableSlots` no longer returns it, and the seats already sold were never on
the client at all — so the range comes from the server's `podSpotLimits`, which also guards
the write. A host may only ever raise it; a Club Admin or an admin may also lower it, never
below `seats_taken`.

## `PodSeatsCell` — seats and bookings are two numbers, not one

`pod_attendees` is an IDENTITY list: a booking for seven seats writes ONE id into it, because
duplicating the id there would corrupt chat access, permissions and audience fan-outs. The seats
past the buyer’s own live in `Pod.extra_seats`, and the server adds them up as `seats_taken`.

Every table that counted the list instead reported a sold-out pod as nearly empty — a pod filled
by three people who bought 1, 7 and 2 seats read as **3 / 10**. This cell renders both: the seat
count on top, the bookings behind it underneath, and the multi-seat split in the hover.

| Prop | Type | Required | Notes |
| --- | --- | --- | --- |
| `seats` | `number` | yes | Seats held. Get it from `podSeatsTaken(pod)` in `@duncit/utils` — never `pod_attendees.length`. |
| `bookings` | `number` | yes | `pod_attendees.length` — the people holding those seats, hosts included. |
| `total` | `number | null` | no | Capacity. `0` or absent means uncapped, and the `/ N` is dropped rather than rendered as `/ 0`. |

Admin’s Pods table, the Partners pods list and the Become-a-Host list all render this one
component: three copies of the same arithmetic is three chances for two portals to quote
different numbers for the same pod (rule 40).

## Localization and coverage

`LanguageSelect` renders each option as its own endonym plus the English name, so a user who has
switched into a script they cannot read can still switch back — and it renders **nothing** when
fewer than two languages are configured, unless `showSingle` says otherwise. Any user-facing string you add to this package must
come from a Localization key with a fallback bundle entry first (rule 38); the defaults here
(`'Not found.'`, `'Back'`, `'Language'`) are prop-overridable for exactly that reason.

`vitest.config.ts` gates at 100/100/100/100 with the barrels excluded, and every layout /
variant branch has to be exercised — a new `StatCardLayout` value ships with the test that
renders it.
