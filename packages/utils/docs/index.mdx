## Why this exists

Each of these modules replaced a byte-for-byte copy that had been pasted into every surface.
`parse-api-error.ts` existed once in mWeb and once in all sixteen portals.
(`duid.ts` lived here too, until the native app started sharing the id — it moved to
`@duncit/user-core`, which the app can consume without a transitive `@duncit/*` dependency.)
The base64 → Blob → anchor-click download flow was rewritten in admin, finance, crm (twice),
support and legal. `fileToDataUrl` had eight implementations, one of them inside
`@duncit/media-picker`. Money formatting had a `formatMoney`, a `money(symbol, v)` and a `fmt`
in partners-app, finance, products and crm that all rounded differently.

The domain modules are here for a stronger reason: a wrong copy is a wrong number.
`payableSpots` encodes "the host sits in `pod_attendees` and never pays", and
`buildEarningsStatement` is the single builder mWeb and the native app both render at
Create-a-Pod Step 4 — rule 27 says those two screens must be identical, and sharing the builder
is how that is enforced rather than hoped for.

Zero runtime dependencies, on purpose. `parse-api-error.ts` types the Apollo error
**structurally**, so this package never has to depend on `@apollo/client`.

## Use it

From `app/mweb/src/apollo.ts` and `portals/crm/src/components/ExcelImportDialog.tsx`:

```ts
import { fileToBase64, parseApiError, formatMoney } from '@duncit/utils';


try {
  const base64 = await fileToBase64(file);
  await importLeads({ variables: { file: base64 } });
} catch (err) {
  setError(parseApiError(err));
}

formatMoney(125000);                                   // "₹1,25,000"
formatMoney(1250, { symbol, decimals: 2, grouping: false }); // "₹1250.00"
formatMoney(125000, { compact: true });                // "₹1.3L" — rounds to 1 decimal
```

And the Step-4 statement, identically in `app/mweb/.../price-panel/index.tsx` and
`app/mobile-app/src/components/create-pod/price-panel/index.tsx`:

```ts
import { buildEarningsStatement, formatStatementMoney } from '@duncit/utils';

const statement = buildEarningsStatement(waterfall, { has_venue: !!slotId, symbol, t });
```

And the four-way split every surface shows a pod's money as — the host's earning first, then
Venue Take, Club Admin Take and Duncit Commission & Govt Charges, adding back to the collection
exactly (the engine's own invariant). `viewer: 'host'` titles the first bucket "Your Earning
(Host)"; `'staff'` titles it "Host Earning". Rendered by `@duncit/ui`'s `EarningsSplitView`
on the web and `EarningsSplitAccordion` in the native app:

```ts
import { buildEarningsSplit } from '@duncit/utils';

const split = buildEarningsSplit(waterfall, { symbol: '₹', t, viewer: 'staff' });
split.buckets.map((b) => [b.key, b.amount]);
// [['host', …], ['venue', …], ['club', …], ['duncit', …]] — always sums to waterfall.amount
split.reconciled; // true
```

The Duncit bucket is GST + platform fee + both commissions. It is NOT the server's
`duncit_revenue`, which also carries the club admin cut — showing that beside a separate club
row would count the cut twice.

The partner studio OPTIONS — one catalogue mWeb, the native app and the Partner console all render. Switching into a studio puts ONE highlighted entry in the sidebar (`studioOptionsEntryFor`); it opens the studio's Options page, which lists `studioOptionsFor(mode, roles, { autoPods })` — each option with a title, a hint, an icon, and its mWeb `path`, native `route` and Partner console `portal` path (an app with no screen for an option opens the console).

The catalogue is ONE flat list, so every Options page lists it in order. An option may name the sub-menu it belongs to with the optional `group` field (today only `'food'`: the venue's food Dashboard, Menu, Food Orders and Food Coupons). `studioOptionGroups(options)` splits any list of options into `{ main, food }`, each in catalogue order — the Partner console sidebar draws the venue studio as a "Venue Options" group and a "Food" group from it. An option without `group` is in `main`.

```ts
import { studioOptionsFor, venuePodPhase } from '@duncit/utils';

studioOptionsFor('VENUE', roles, { autoPods }); // [] in User mode or once the role is revoked
studioOptionGroups(studioOptionsFor('VENUE', roles, { autoPods }));
// { main: [dashboard, venues, …], food: [food-dashboard, food-menu, food-orders, food-coupons] }
venuePodPhase('ONGOING'); // 'CURRENT' — the Upcoming / Current / Past tabs of Pods at your venue
```

The Studio role switcher (mWeb and native). The apps show ONE "Studio" sidebar entry for every partner and put the role switcher at the top of the Studio page itself; which roles it offers, which role the Studio opens on and where the entry points are one rule, here.

| Export | Signature | Meaning |
| --- | --- | --- |
| `heldStudioModes` | `(roles, access?) => PartnerStudioMode[]` | The partner roles the switcher offers, in switcher order (`HOST`, `VENUE`, `ECOMM`, `CLUB`) — only the ones held, and never `ECOMM` while `access.products` is off. One entry means no switcher is drawn. |
| `studioModeFor` | `(mode, roles, access?) => PartnerStudioMode \| null` | The role the Studio opens on: the remembered mode while it is still held, otherwise the first held role. `null` without a partner role. |
| `studioEntryFor` | `(mode, roles, access?) => StudioOptionsEntry \| null` | The single "Studio" sidebar entry — the `studioModeFor` role's Options `path` / `route` / `portal` under the `mweb.studioOptions.studioEntry` title and hint. `null` without a partner role. |
| `STUDIO_ROLE_LABEL_KEY` | `Record<PartnerStudioMode, string>` | The translation key of each role's short name on the switcher (Host, Venue, Brand, Club Admin). |

```ts
import { heldStudioModes, studioEntryFor, studioModeFor } from '@duncit/utils';

const roles = ['VENUE_OWNER', 'ECOMM_MANAGER'];

heldStudioModes(roles);                       // ['VENUE', 'ECOMM']
heldStudioModes(roles, { products: false });  // ['VENUE'] — one role, so no switcher
studioModeFor('USER', roles);                 // 'VENUE' — first held role
studioModeFor('ECOMM', roles);                // 'ECOMM' — the remembered role
studioEntryFor('ECOMM', roles)?.path;         // '/products/options'
```

### Checkout bill — `checkout-bill`

| Export | Signature | Meaning |
| --- | --- | --- |
| `round2` | `(n: number) => number` | The finance engine's single-round rule; non-numbers become `0`. |
| `clampPayable` | `(amount: number) => number` | What is left to charge: rounded, never below zero. |
| `applyBillDiscounts` | `(gross: number, discounts: BillDiscount[]) => DiscountedBill` | Takes the deductions off in order, stopping at zero. |
| `roundUpBill` | `(amount: number) => { rounded, roundOff }` | The round-off rule: a bill rounded UP to the next whole rupee, and what that added (`0 ≤ roundOff < 1`). Server twin: `roundUpBill` in `payment.roundoff.ts`. |
| `maxRedeemableCoins` | `(balance: number, payableAfterCoupon: number) => number` | Whole coins the bill can absorb — the balance, capped at the bill rounded up to the whole rupee. |
| `settleBill` | `(payableAfterCoupon: number, coinsApplied: number) => { coins, payable, roundOff, taxable }` | The couponed bill settled the way the server does it: rounded up, then coins taken. `payable` is always whole rupees; `taxable` is what GST is extracted from (never includes the round-off). |
| `exclusiveOfGstBill` | `(gross, discounts, taxable, gstPct) => { subtotal, discounts }` | The bill restated GST-compliantly: subtotal and each deduction net of GST, so subtotal − discounts = taxable value. |

A coupon and Duncit Coins cut the same gross and neither may cut past zero. `applyBillDiscounts`
caps each line at what was still owed when its turn came, so the printed rows always reconcile
to `payable` and the leftover discount is simply dropped — never refunded, never carried:

```ts
applyBillDiscounts(399, [{ key: 'coupon', label: 'WELCOME', amount: 500 }])
// { discounts: [{ key: 'coupon', label: 'WELCOME', amount: 399 }], discountTotal: 399, payable: 0 }

clampPayable(359.1 - 358)           // 1.1  — not 1.0999999999999773
```

Every payment is charged in whole rupees. The bill is rounded UP **after the coupon and before
the coins**, so whole coins can always clear all of it, and whatever is left to charge is a
whole number. The difference is the payment's round-off — its own row on the bill, never part
of the taxable value, the GST or a fee:

```ts
roundUpBill(101.47)                 // { rounded: 102, roundOff: 0.53 }
roundUpBill(118)                    // { rounded: 118, roundOff: 0 } — already whole, nothing added
maxRedeemableCoins(500, 101.47)     // 102 — the whole rounded bill (the floor used to leave ₹1.47 to pay)

settleBill(101.47, 0)               // { coins: 0,   payable: 102, roundOff: 0.53, taxable: 101.47 }
settleBill(101.47, 60)              // { coins: 60,  payable: 42,  roundOff: 0.53, taxable: 41.47 }
settleBill(101.47, 102)             // { coins: 102, payable: 0,   roundOff: 0,    taxable: 0 }
```

`taxable + roundOff = payable` whenever anything is charged. When coins clear the whole bill the
round-off was paid in coins, so `roundOff` is `0` and there is no charge left for a row to explain.
mWeb and native both read `settleBill` through their `useCoinRedemption` hook and print the
"Round off" row (`mweb.checkout.roundOff`) only when it is above zero.

A discount shown on the invoice comes off the value BEFORE GST (CGST Act s.15(3)(a)), so every
breakdown — mWeb, native and the Finance payment card — reads ticket → subtotal (excl. GST) →
discounts (excl. GST) → taxable value → GST → total. `exclusiveOfGstBill` takes the taxable value
from the charged quote, so the GST row is always the tax actually charged:

```ts
exclusiveOfGstBill(750, [{ key: 'ticketDiscount', amount: 37.5 }], 603.81, 18)
// { subtotal: 635.59, discounts: [{ key: 'ticketDiscount', amount: 31.78 }] }
// 635.59 − 31.78 = 603.81 taxable, + 108.69 GST = 712.50
```

### The Explore reel feed — `reel-feed`

The Explore reels play in a random order that never runs out. Each pass over
the pods is a *cycle*, shuffled on its own; when the viewer gets within
`REEL_PRELOAD_DISTANCE` of the end, the surface deals one more. mWeb and the
native app share this and nothing else — the players stay separate.

The order is a hash of `seed` + cycle + pod key, so a refetch (a like, a save)
moves nothing; a new `seed` (a new visit) deals a new order. Where a cycle
would open on the reel the last one closed on, it is rotated by one.

```ts
const [seed] = useState(() => Date.now());
const [cycles, setCycles] = useState(1);
const reels = useMemo(() => reelFeed(pods, (pod) => pod.id, seed, cycles), [pods, seed, cycles]);
// Swiped near the end → deal the next shuffled pass.
if (shouldExtendReelFeed(activeIndex, reels.length)) setCycles((count) => count + 1);
```

| Export | Signature | Returns | Notes |
| --- | --- | --- | --- |
| `reelFeed` | `(items, keyOf, seed, cycles) => ReelFeedEntry[]` | — | `cycles` shuffled passes; each entry's `key` is `<pod key>~<cycle>`, unique across passes. |
| `shouldExtendReelFeed` | `(activeIndex, length) => boolean` | — | True once the reel on screen is within the preload distance of the end. |
| `isReelPreloaded` | `(index, activeIndex) => boolean` | — | Whether a reel should be buffering — the ones within `REEL_PRELOAD_DISTANCE` either side. |
| `REEL_PRELOAD_DISTANCE` | `2` | — | Reels kept loading ahead of and behind the one on screen. |

### Pod phase — the Home rails

A pod is not simply "upcoming or past". It leaves the upcoming feed the moment
it STARTS — nobody can join a pod that is running, and the server refuses the
booking — but it is not *previous* until it is actually over. Between those two
instants it is **ONGOING**, and Home gives it its own rail on both mWeb and
native. Before this split a pod that was happening right now dropped straight
into Previous Pods.

A pod's end is `pod_end_date_time` when the host set one, and
`pod_date_time + POD_LIVE_TAIL_MS` (4h) when they did not — the same fallback
the server states as a Mongo predicate in `pod.lifecycle.ts`, which is why the
tail is one constant rather than a number typed out per surface. mWeb's
`podStatus` and native's `podStatus` both read this, so a status chip and the
rails can never place the same pod differently.

### Studio modes

Which studios exist, and which a person may switch into. mWeb draws the switcher in MUI and
the native app in Tamagui, but the RULE is one thing and lives here — the two apps cannot end
up disagreeing about whether a studio exists (rules 27 + 40). Each app keeps its own landing
map beside its re-export: mWeb has paths, native has route names, and each keeps
its own `STUDIO_LABEL` — no user-facing word lives in this package.

| Export | Signature | Meaning |
| --- | --- | --- |
| `STUDIO_OPTIONS` | `readonly StudioOption[]` | The catalogue, in switcher order: `USER`, `HOST`, `VENUE`, `ECOMM`, `CLUB`, each with the role behind it. |

| `resolveMode` | `(mode, roles, access?) => StudioMode` | A persisted mode, or `'USER'` once the user no longer qualifies for it. |

`access.products` is the `is_product_visible` system flag. Off, and the E-commerce studio is
not offered at all — its landing page is gated, so switching in would only bounce the partner
home. It defaults to on, so a caller with no reason to know about products is unaffected.

```ts
const roles = ['HOST', 'ECOMM_MANAGER'];

availableModes(roles, { products: false }).map((o) => o.mode) // ['USER', 'HOST']

resolveMode('ECOMM', roles)                    // 'ECOMM'
resolveMode('ECOMM', roles, { products: false })  // 'USER' — the saved studio is gone
resolveMode('VENUE', roles)                    // 'USER' — never held the role
```

## The grievance form is one spec, four validators

The same grievance is raised from mWeb, the native app and the main website, and gated
again by the server. Four validators means four chances to disagree about whether a field
is required or how long it may be — so the numbers live here once and each surface builds
its own schema from them:

```ts
GRIEVANCE_MAX_LENGTH.subject;          // 200 — the same number the server enforces
GRIEVANCE_OPTIONAL_FIELDS;             // ['address'] — the only field you may leave blank
isGrievanceFieldRequired('address');   // false
isGrievanceFieldRequired('phone');     // true
grievanceFieldLabelKey('subject');     // 'grievance.field.subject'
GRIEVANCE_FIELDS;                      // render order, shared so the two apps match
```

The value SHAPES are deliberately NOT here — email and phone patterns belong to
`@duncit/regex`, which already owns them. This module owns lengths, order and
optionality; nothing else.

`SUBMIT_GRIEVANCE_SDL` and `GRIEVANCE_OFFICER_SDL` are the operations as plain strings,
because the three surfaces wrap documents differently: Apollo's `gql` on mWeb,
`graphql-tag` in native, a bare `fetch` on the Astro site. A string is the one form all
three accept.

```ts
isGrievanceOpen('RECEIVED');   // true  — still owed an answer
isGrievanceOpen('RESOLVED');   // false
```

A signed-in person's form opens with their contact details filled in from `me`, so mWeb
and native seed it the same way:

```ts
grievanceDraftFromUser({
```

## `fileToBase64` vs `fileToDataUrl` — they are not interchangeable

Two behavioural families exist because two families of server calls exist:

- `fileToDataUrl` resolves the **full** `data:<mime>;base64,…` URL (support, website-app,
  mWeb, media-picker payloads).
- `fileToBase64` resolves the **bare** base64 with the prefix stripped (crm, finance payloads).

Pick the one the endpoint you are calling already received. Swapping them ships a payload the
server cannot decode, and nothing type-checks the difference — both are `Promise<string>`.

## The host's spot is free — never bill the raw capacity

`payableSpots(total)` is `total − 1`, and returns `0` for `0` (unlimited/unset) and `1`
(host-only) rather than going negative. Every money figure derived from a spot count must go
through it: a 30-spot pod can only ever sell 29 seats. The server mirrors this in
`server/src/modules/finance/finance/breakdown.math.ts`; if the two ever disagree, Create-a-Pod,
the finance calculator and the real settlement disagree by exactly one ticket.

`payingAttendees(attendeeIds, hostIds)` is the head-count equivalent — hosts are written into
`pod_attendees` at creation, so counting the array raw over-states income by one ticket per host.

`payingSeats(pod, hostIds)` is the one to bill against. `payingAttendees` counts PEOPLE, and a
buyer who takes seven seats appears in `pod_attendees` exactly once — a pod that sold 29 seats to
10 buyers reported ten tickets of revenue. It mirrors `payingSeats` in the server’s
`breakdown.math.ts`, which reads `extra_seats` directly where the client reads the `seats_taken`
the server already resolved from it.

`HOST_FREE_SPOT_NOTE` is the copy that must sit next to any spots-driven figure.

## The earnings statement adds no math

`buildEarningsStatement` takes the `potentialPodEarnings` waterfall **verbatim**. It sums the
server's own lines for section subtotals, formats the formula strings, and sets `reconciled`
when all three audit identities hold. It does not compute a fee, a rate or a tax anywhere.

If a number looks wrong, the fix belongs in the server waterfall, not here — re-deriving it
client-side is how the two surfaces started disagreeing in the first place. GST is charged once
and extracted from the GST-inclusive collection, so the statement shows the real taxable base
rather than inventing per-charge tax rows — and states the GST row's arithmetic on the
collection, which is the only base a reader can see on the panel.

Grouping is the one thing it does decide, and the commissions are where that matters. Duncit
takes a cut from each side of the split — `host_commission_*` off the host's remainder and
`venue_commission_*` off the venue's slot price — and only the first is money leaving the
host's collection. Reading one label off the other's amount is exactly the bug this grouping
now prevents.

## Google signed you in, Duncit has never met you

`loginWithGoogle` answers `GOOGLE_ACCOUNT_NOT_FOUND` for a verified Google account no Duncit
account is linked to. Both apps now treat that as an invitation rather than a refusal, and
these three carry the credential from the invite into signup — so "yes" continues on the
Google door instead of dropping the person on a signup screen to press the same Google button
a second time.

The whole reason they live here is that the credential must be spent **at most once**, and
every way of hitting the flow twice has to collapse to one signup:

| Way in twice | What stops it |
| --- | --- |
| A second tap while the exchange is still in the air | `openGoogleSignup(current, idToken, email)` returns the invite already open for that same token — referentially equal, so no second invite and no swapped credential |
| The invite pressed twice | The screen clears the invite before navigating, so the second press has nothing to send |
| Signup remounted, reloaded, or reached again via Back | `claimGoogleSignupHandoff` answers once per credential and `null` after that, so re-reading the same router state or navigation param is a no-op |
| Two `signupWithGoogle` calls reaching the server anyway | The unique partial index on `auth.google_id`, inside the mutation's transaction — the last line, not the first |

```ts
// The login screen holds it, idempotently in the token.
setInvite((current) => openGoogleSignup(current, idToken, verifiedEmail))

// The signup screen claims it, once.
const CLAIMS = createGoogleSignupClaims() // module scope: it must outlive the mount
const carried = readGoogleSignupHandoff(location.state?.googleSignup)
const claimed = claimGoogleSignupHandoff(CLAIMS, carried) // null on every call after the first
```

### Apple rides the same door

`loginWithApple` refuses exactly as `loginWithGoogle` does, with `APPLE_ACCOUNT_NOT_FOUND` in
place of `GOOGLE_ACCOUNT_NOT_FOUND`, so the same three functions carry an Apple credential too.
The handoff takes two optional extras: which `provider` refused (absent means Google) and the
`name` Apple shared — Apple never puts a name in its token and shares it only on the first
authorisation, so it is carried rather than asked again.

```ts
setInvite((current) =>
  openGoogleSignup(current, idToken, verifiedEmail, { provider: 'APPLE', name: 'Riya Sharma' }),
);
```

The rest of what differs per provider lives in `social-auth`, once for both apps:

| Export | What it answers |
| --- | --- |
| `SOCIAL_NOT_FOUND_CODE[provider]` | The refusal that opens the signup invite — `GOOGLE_ACCOUNT_NOT_FOUND` / `APPLE_ACCOUNT_NOT_FOUND` |
| `SOCIAL_AUTH_COPY[provider]` | The copy keys that name the provider — invite detail, link consent, details subtitle, policy intro. Literal, so the translation gate sees them |
| `SOCIAL_PROMPT_COPY[prompt]` | The copy keys of the two pre-account questions: `INVITE` (login door — "no Duncit account yet, make one?") and `EXISTS` (signup door — "you're already on Duncit, log in?", asked from the `socialSignupStatus` query before any code is sent). `SOCIAL_PROMPT_TEST_IDS[prompt]` holds the dialog's test ids for both apps |
| `socialSignupNeedsName(credential)` | `true` for an Apple credential that carried no name — the details step then asks it |
| `isSocialProvider(value)` | Whether a value read off navigation is `'GOOGLE'` or `'APPLE'` |

```ts
socialSignupNeedsName({ provider: 'APPLE' }); // true — ask the name on the details step
socialSignupNeedsName({ provider: 'APPLE', name: 'Riya Sharma' }); // false
SOCIAL_AUTH_COPY.APPLE.linkTitle; // 'mweb.login.appleLinkConsentTitle'
SOCIAL_PROMPT_COPY.EXISTS.accept; // 'mweb.signup.existingAccountLogin'
```

`readGoogleSignupHandoff` is deliberately strict about shape: router state survives a reload
and a navigation param survives a remount, so it is reading something possibly stale. Anything
that is not a complete, non-blank pair reads as `null` — signup opened normally, which is the
safe reading of a malformed one.

## The referral link and its message

`referralLink(code, baseUrl)` and `readReferralCode(search)` are two halves of one agreement:
mWeb builds the link, the native app builds the same link, and mWeb's signup reads the code
back out of it. The parameter name lives here once (`REFERRAL_PARAM`) so none of the three can
drift.

`renderReferralMessage(template, { code, link, coins })` fills in what Finance wrote at
**Finance → Referrals**. The template is stored on the server with its placeholders intact —
`{code}`, `{link}`, `{coins}`, listed as `REFERRAL_MESSAGE_TOKENS` — and rendered per member at
share time, so one edit in Finance changes every share sheet at once. A blank template falls
back to `DEFAULT_REFERRAL_MESSAGE`; the coin count is never hardcoded in either, because a
message that promises fifty while the rate says ten is worse than no message.

```ts
renderReferralMessage('', { code: 'DUN-9F3A2C', link, coins: 50 })
// 'Join me on Duncit! We both earn 50 Duncit Coins. Use my code DUN-9F3A2C or sign up here: …'
```

## Every share is a tracked link

A link a member hands out is a marketing channel — usually the biggest one — so it is minted
as a `duncit.com/<code>` short link under a campaign, exactly like a link a marketer creates by
hand. `share-link.ts` is the contract both surfaces send: `SHARE_LINK_MUTATION` (a plain
string, because this package has no GraphQL client and must stay framework-free for Metro),
and `trackedShareUrl`, which asks once per thing and caches the answer for the session.

The surfaces never build the tracked URL. They say **what** is being shared — a target and the
id of the thing — and the server looks it up, builds the destination and returns the link. That
is what makes the mutation safe to leave unauthenticated: an id that resolves to nothing mints
nothing, so it can never be pointed somewhere we did not choose.

```ts
// mWeb: Apollo. The app: graphql-request. Same document, same answer.
const url = await shareUrl('POD', pod.id, `${origin}/club/${slug}/pod/${podSlug}`);
```

`plainUrl` is what the surface would have shared on its own, and it is what comes back when the
API cannot be reached. Sharing is the member's action, not the tracking's: a share sheet must
never fail to open because analytics did. A failed attempt is forgotten rather than cached, so
the next share retries.

`trackedPodShareLinks` resolves the **pair** a shared pod carries — the pod page and its venue
map — in one round trip. The map link is an external destination (Google Maps), and it is
counted like every other link: `buildPodShareMessage({ …, mapUrl })` takes the tracked one, and
falls back to the plain `podMapLink` search when it has none.

| Export | Signature | Meaning |
| --- | --- | --- |
| `SHARE_LINK_MUTATION` | `string` | The `shareLink(target, ref)` document, parsed by each surface's own client. |
| `ShareLinkTarget` | `'POD' \| 'POD_LOCATION' \| 'POD_FEEDBACK' \| 'POD_MEDIA' \| 'CLUB' \| 'PROFILE' \| 'POST' \| 'POD_IDEA' \| 'GIFT_CARD' \| 'REFERRAL'` | Mirrors the server enum. Each one has its own campaign. |
| `trackedShareUrl` | `(fetcher, target, ref, plainUrl) => Promise<string>` | The link to hand out; `plainUrl` when it cannot be minted. |
| `trackedPodShareLinks` | `(resolve, podId, plainUrl, plainMapUrl) => Promise<PodShareLinks>` | The pod link and its venue map link together. |
| `clearShareLinkCache` | `() => void` | Drops the session cache — sign-out and tests. |

A host hands out two addresses per pod — the rating form and the Upload Pod Media page — and

```ts
podFeedbackPath('665f…')                    // '/pod/665f…/feedback'
podMediaPath('665f…')                       // '/pod/665f…/media'
```

## Badge vocabulary — the goal and the window it happens in

Every badge states two things a member has to read before it means anything: the GOAL
(`BADGE_GOAL_KEY`, whose copy takes the badge's threshold as `{target}`) and the WINDOW that
goal has to happen inside (`BADGE_WINDOW`, keyed to a label by `BADGE_WINDOW_KEY`). The window
follows from the CONDITION, never from an admin field — a monthly count resets with the
calendar wherever it is rendered, and no one can configure that apart:

```ts
import {
  BADGE_GOAL_KEY,
  BADGE_WINDOW,
  BADGE_WINDOW_KEY,
  badgeProgressPercent,
  sortBadgeProgress,
} from '@duncit/utils';

t(BADGE_GOAL_KEY.POD_ATTEND_COUNT, { vars: { target: 10 } }); // 'Attend 10 pods'
BADGE_WINDOW.MONTHLY_POD_ATTEND_COUNT;                        // 'CALENDAR_MONTH'
t(BADGE_WINDOW_KEY.CALENDAR_MONTH);        // 'Must all happen inside one calendar month'

badgeProgressPercent({ achieved: false, current: 4, target: 10 }); // 40
// An achieved badge always reads 100 — the metric can drift back below the
// threshold (a cancelled ticket) and a bar sliding backwards under an
// "Achieved" chip reads as a bug.
badgeProgressPercent({ achieved: true, current: 3, target: 10 }); // 100

sortBadgeProgress(rows); // earned first, then closest to unlocking
```

The placeholder is `{target}`, never `{count}`: the translator reserves `count` for its own
plural counter and blanks an unmatched one out of the sentence.
## The app-open popup — one dismissal, one set of dimensions

The marketing popup is rendered three times — MUI in mWeb, Tamagui in the native app and in
the native web build — so the two things that must never drift live here.

**Dismissal is a LIST OF POPUP IDS, never a `hasSeenPopup` flag.** Marketing publishes a new
campaign by creating a new id, and a single flag would silently swallow every campaign after
the first. The server also records a dismissal per user, but only after a round trip that can
fail: the local write is what hides the popup on the same frame and survives that failure, and
the server write is what carries it to that person's other devices.

```ts
import {
  readDismissedPopupIds,
  rememberDismissedPopup,
  isPopupDismissed,
} from '@duncit/utils';

// `storage` is described structurally, so each surface passes its own: `localStorage` in
// mWeb, `expo-secure-store` on a phone (which is `localStorage` again on native web).
const ids = await readDismissedPopupIds(storage);
isPopupDismissed(ids, 'popup-a'); // true  — closed on this device already
isPopupDismissed(ids, 'popup-b'); // false — new campaign, show it

await rememberDismissedPopup(storage, 'popup-b'); // ['popup-a', 'popup-b']
```

Storage can be unavailable — private browsing, a locked keystore — and every function above
absorbs that. The cost is the popup showing once more, never a throw on app open.

**Dimensions come from the artwork, not the screen.** Campaign images arrive in whatever
aspect the designer exported, so a fixed box letterboxes one and crops the next. The card is
sized to the picture instead, capped at `APP_POPUP_MAX_WIDTH` and at
`APP_POPUP_HEIGHT_FRACTION` of the viewport:

```ts
appPopupAspect({ width: 1080, height: 1350 }); // 0.8
appPopupAspect(null); // 0.8 — the portrait default, so the card cannot resize under the user

appPopupImageSize({ width: 1080, height: 1350 }, appPopupLimits({ width: 390, height: 844 }));
// { width: 342, height: 428 } — touches the width limit, well inside the height one
```

The native app calls `appPopupImageSize` against `useWindowDimensions`. mWeb expresses the
same rule as a CSS `min()` built from the same three constants, so a browser re-solves it on
every resize and orientation change without a listener.

`detectClientPlatform(userAgent)` answers which store build a BROWSER stands in for. Both
browser surfaces use it: a campaign aimed at Android has to reach an Android phone whether
the person opened mWeb or the native web build (rule 27).

## The @handle, and where a member may be messaged

Two things mWeb and the native app render identically (rule 27), so their LOGIC lives here
and only the MUI card and the Tamagui card differ (rule 40).

### The @handle is minted, then owned

A handle is minted ONCE by the server from the member’s name (`generateUsername` in
`server/src/modules/access/user/username.ts`, backfilled on `me` for accounts that predate
handles), and its owner may then change it from **Edit profile**. The field there is
debounced against `usernameAvailability` and the Save button is the profile’s own — which is
the whole reason `usernameBlocksSave` exists.

`usernameStatus` is the one place the field’s state is decided. Order matters: your OWN
handle reads as `CURRENT` rather than `TAKEN` (it IS taken — by you), and the shape is
checked before anything is sent, so typing a space never costs a round trip.

```ts
const idle = { current: 'ravi-9x3m', checking: false, available: null, reason: null };

usernameStatus({ ...idle, value: 'ravi-9x3m' });                        // 'CURRENT'
usernameStatus({ ...idle, value: 'Ravi Sharma' });                      // 'INVALID' — never sent
usernameStatus({ ...idle, value: 'ravi-plays' });                       // 'CHECKING'
usernameStatus({ ...idle, value: 'ravi-plays', available: true });      // 'AVAILABLE'
usernameStatus({ ...idle, value: 'admin', available: false, reason: 'RESERVED' }); // 'RESERVED'
```

`usernameBlocksSave(status, hasCurrent)` answers for the WHOLE form, because the handle
shares its Save with the name and the address beside it. `CHECKING` blocks too: the check is
400ms behind the last keystroke, so without it a fast typist reaches Save while the answer is
still in flight and the button reports the previous handle. An account with no handle yet is
the one case an empty field is fine — there is nothing to clear and nothing to break.

```ts
usernameBlocksSave('AVAILABLE', true); // false — the only handle that reaches the server
usernameBlocksSave('CHECKING', true);  // true  — the answer is still in flight
usernameBlocksSave('IDLE', true);      // true  — a profile cannot go back to no address
usernameBlocksSave('IDLE', false);     // false — pre-handle account, save the rest anyway
```

`scheduleUsernameCheck` owns the round trip itself — the 400ms debounce, the shape guard that
keeps a malformed handle on the device, and the cleanup that drops a reply for a value no
longer in the field. It returns that cleanup, which is exactly a React effect’s contract, so
each app supplies only its transport and its logger and neither owns the logic:

```ts
useEffect(
  () =>
    scheduleUsernameCheck({
      value,
      current,
      ask: (candidate) => client.query({ query: USERNAME_AVAILABILITY, variables: { username: candidate } })
        .then((r) => r.data.usernameAvailability),
      onState: setCheck,          // starts from IDLE_USERNAME_CHECK
      onError: (error, candidate) => logs.mWeb.error('useUsernameCheck', 'availability', { error, candidate }),
    }),
  [client, current, value],
);
```

A failed `ask` falls back to `IDLE_USERNAME_CHECK`, which `usernameStatus` reads as CHECKING —
telling somebody their handle is taken because the network blinked would be worse than making
them wait, and Save is disabled either way.

`usernameFieldState` is everything the field renders, derived once for both surfaces — the
MUI field and the Tamagui field disagree about how to draw a text box and agree about
absolutely everything else. Note the link: it previews the handle being TYPED once the server
has said yes, and otherwise the one that works today.

```ts
const settled = { checking: false, available: true, reason: null };
usernameFieldState({ value: 'ravi-plays', current: 'ravi-9x3m', check: settled, origin });
// { status: 'AVAILABLE', link: 'https://mweb.duncit.com/u/ravi-plays', errored: false }

usernameFieldState({ value: 'ravi-plays', current: 'ravi-9x3m', check: IDLE_USERNAME_CHECK, origin });
// { status: 'CHECKING', link: 'https://mweb.duncit.com/u/ravi-9x3m', errored: false }
```

The same pair is on the PROFILE, under the name and next to Share.

```ts
profileUrl('https://mweb.duncit.com', 'ravi-9x3m'); // 'https://mweb.duncit.com/u/ravi-9x3m'

const labels = buildUsernameLabels(t);
labels.handle('ravi-9x3m');                  // '@ravi-9x3m'
labels.status('AVAILABLE', 'ravi-plays');    // '@ravi-plays is available.'
labels.copyLink;                             // the button beside it
```

### Gender and Pet Owner

Two single-selects on **Edit profile**, identical on mWeb and native. `GENDERS` restates
the server's GraphQL `Gender` enum. Pet Owner is stored as a boolean but picked as Yes / No,
so the form holds `'YES' | 'NO' | ''` and maps at the edges. An unanswered field maps to
`undefined`, which the mutation omits, so a save never clears an answer.

```ts
toGenderValue('FEMALE');   // 'FEMALE'
toGenderValue(null);       // ''
toPetOwnerValue(false);    // 'NO'
fromPetOwnerValue('YES');  // true
fromPetOwnerValue('');     // undefined — left out of UpdateMyProfileInput

const labels = buildProfileDemographicsLabels(t);
labels.genderOptions;      // [{ value: 'MALE', label: 'Male' }, …]
labels.petOwnerOptions;    // [{ value: 'YES', label: 'Yes' }, { value: 'NO', label: 'No' }]
```

### Communication preferences

One row in Profile Settings opens a hub listing Email / WhatsApp / SMS; each of those opens
the screen that owns every switch for that channel, including its Authentication messages
switch. Nothing is settable from two places, so `commChannelSummary` (the hub’s one line per
channel) only ever reads.

```ts
const labels = buildCommPreferenceLabels(t);

commChannelSummary({ channel: 'EMAIL', reachable: true, destination: 'ravi@duncit.com', otp_enabled: true, otp_can_disable: true }, labels);
// 'ravi@duncit.com · Authentication messages on'
commChannelSummary({ channel: 'SMS', reachable: false, destination: '', otp_enabled: false, otp_can_disable: true }, labels);
// 'Add a phone number to get messages here.' — "off" and "no number" are different answers
```

`commRowState` answers what ONE channel’s switch may do, and `authMessageCardState` turns
that into the whole card the channel screen renders — title, body, the status line under it,
and whether a switch is offered at all:

```ts
commRowState({ channel: 'SMS', reachable: false, destination: '', otp_enabled: true, otp_can_disable: false });
// { canToggle: false, locked: false, unreachable: true } — nothing to send to, so no switch

commRowState({ channel: 'EMAIL', reachable: true, destination: 'ravi@duncit.com', otp_enabled: true, otp_can_disable: false });
// { canToggle: false, locked: true, unreachable: false } — on, and the last channel that can reach them
```

`locked` is the case worth naming: a disabled switch with no sentence beside it reads as a
bug, so `authMessageCardState` puts `labels.authLocked` in `note` whenever it is true. The
server decides `otp_can_disable`, because it is the only side that can see all three channels
at once — an account with nowhere to receive a code cannot sign in.

`findCommChannel(channels, channel)` is the one lookup both apps use, so a screen that wants
one channel out of the sheet never writes its own `.find`.

### Changing a contact detail

Email, phone and WhatsApp are the three profile fields whose change has to be PROVED, so
they are not fields of the edit-profile form at all. Each is a read-only row with its own
two-step dialog: type the new value, then type the code sent **to that new value**. mWeb
renders it in MUI and the native app in Tamagui; everything below is what they share.

`currentContactValue` is what the row displays, and it never shows a lone country code —
an account with an extension but no number has no number.

```ts
const account = {
  email: 'ravi@duncit.com',
  phone_extension: '+91',
  phone_number: '9845012345',
  whatsapp_extension: '+91',
  whatsapp_number: '',
};

currentContactValue(account, 'PHONE');    // '+91 9845012345'
currentContactValue(account, 'WHATSAPP'); // '' — the row falls back to "No WhatsApp number yet"
contactDraftFrom(account, 'PHONE');       // { email: '', extension: '+91', number: '9845012345' }
```

All three are REQUIRED. Nothing about them rides the edit-profile Save — each is its own
write — so a missing one cannot be caught by a Zod rule over a field the form does
not have. `contactDetailsComplete` is what holds the button instead, and it is one function
rather than one per surface so mWeb and native cannot disagree about whether a profile is
reachable:

```ts
contactDetailsComplete(account);                              // false — no WhatsApp number
contactDetailsComplete({ ...account, whatsapp_number: '9845012345' }); // true
```

`contactValueVerified` is the "Verified" badge beside a number. The server stamps a number
verified only when a code sent to it came back (`is_phone_verified`, `whatsapp_verified_at`)
and clears the stamp when the number moves, so a number with no stamp was typed but never
answered. The email row never carries one, and an empty row has nothing to vouch for:

```ts
contactValueVerified({ ...account, is_phone_verified: true }, 'PHONE');    // true
contactValueVerified({ ...account, is_phone_verified: false }, 'PHONE');   // false — typed, never answered
contactValueVerified({ ...account, whatsapp_verified_at: '2026-09-18T10:30:00.000Z' }, 'WHATSAPP');
// false — the stamp outlived the number; this account has no WhatsApp number
```

`contactChangeNeedsOtp` is which of the three still has to be PROVED before it is stored.
The address and the WhatsApp number always are — both are delivery channels whose whole
worth is that a message arrives, and a typo in either goes unnoticed until something
silently fails to reach anybody. The contact number follows the `phone_otp_verification`
feature flag (`PHONE_OTP_FLAG`), which each surface reads and passes in as `phoneOtp`: off,
the number is saved as typed and stored unverified; on, an SMS code (sent through MSG91) proves
it when it is added and on every change:

```ts
contactChangeNeedsOtp('PHONE', false);    // false — one step, stored on submit
contactChangeNeedsOtp('PHONE', true);     // true  — an SMS code goes to the new number
contactChangeNeedsOtp('EMAIL', false);    // true  — a code goes to the new address
contactChangeNeedsOtp('WHATSAPP', false); // true  — a code goes to the new number
```

The server agrees from its own side: `setContactPhoneNumber` takes no code and is refused
while the flag is on, and the other two refuse without one.

`contactDraftIsUnchanged` is the refusal that runs BEFORE a code is sent. A code costs the
person an SMS and a wait, so a draft matching what the account already holds is turned back
rather than delivered. For a phone the country code counts — `+1 9845012345` is a different
number from `+91 9845012345`, however alike the digits look:

```ts
contactDraftIsUnchanged(account, 'PHONE', { email: '', extension: '+91', number: '9845012345' });
// true — same number, no code sent
contactDraftIsUnchanged(account, 'PHONE', { email: '', extension: '+1', number: '9845012345' });
// false — same digits, different country

contactDraftValue({ email: 'Ravi@Duncit.com', extension: '', number: '' }, 'EMAIL');
// 'ravi@duncit.com' — what the server is asked to store
```

`contactSubmitAction` is the one answer both dialogs act on, and `applyContactDraft` is what
they fold into the rows afterwards — the dialog closes onto those rows, and one still showing
the old number while the refetch is in flight reads as a change that failed. Its last argument
is whether a code proved the value, so a number saved straight never keeps the old badge:

```ts
contactSubmitAction(account, 'PHONE', { email: '', extension: '+91', number: '9845012345' }, false);
// 'UNCHANGED' — same number, nothing to do
contactSubmitAction(account, 'PHONE', { email: '', extension: '+91', number: '9845099999' }, false);
// 'SAVE' — stored on this submit
contactSubmitAction(account, 'PHONE', { email: '', extension: '+91', number: '9845099999' }, true);
// 'SEND_CODE' — the flag is on, so an SMS code proves it first
contactSubmitAction(account, 'EMAIL', { email: 'ravi@duncit.in', extension: '', number: '' }, false);
// 'SEND_CODE' — a code goes to the new address first

applyContactDraft(account, 'PHONE', { email: '', extension: '+91', number: '9845099999' }, false);
// { …account, phone_extension: '+91', phone_number: '9845099999', is_phone_verified: false }
```

The new number is checked as it is typed. Each dialog runs signup's `useSignupPhoneCheck` on
`CONTACT_NUMBER_FIELDS` — the server leaves the signed-in account out, so its own number is never
"taken" — and hands the status to `contactValueStepView`, which decides the button and the lines
under the box once for both surfaces, plus the hint above it (the contact number's hint names
the SMS code only while `phoneOtp` is on). A number another account holds, or one still being
checked, keeps Send code / Save number shut:

```ts
const labels = buildContactChangeLabels(t);
contactValueStepView('WHATSAPP', labels, {
  busy: false,
  blocked: false,
  isValid: true,
  numberStatus: 'TAKEN',
  phoneOtp: false,
  snapshot: account,
  draft: { email: '', extension: '+91', number: '9845099999' },
  edited: true,
});
// { hint: 'We'll send a code to this number on WhatsApp…', buttonLabel: 'Send code',
//   disabled: true,
//   numberLines: { hint: '', error: 'This number already exists on another account. …' } }
```

The box opens on the account's own number, which is never somebody else's. The view reads
`snapshot` and `draft` through `contactNumberIsCurrent`. While the box holds that number the
button stays shut and the check's answer is ignored. The line under the box stays empty until the
person has edited the box (`edited`). If they then type the same number back, it says this is
their current number. Only the channel's OWN value counts: the WhatsApp number may also be the
contact number, so typing the contact number into the WhatsApp box is a real change.

`edited` lives in each dialog's state. `noteContactEdit` is the update every keystroke applies:
it drops a refusal about the old value and records the edit, and returns the same object once
neither changes, so typing does not re-render the dialog.

```ts
contactNumberIsCurrent(account, 'PHONE', { email: '', extension: '+91', number: '9845012345' });
// true — the number the phone row already holds
contactNumberIsCurrent(account, 'WHATSAPP', { email: '', extension: '+91', number: '9845012345' });
// false — the contact number, offered as the WhatsApp number too
contactValueStepView('PHONE', labels, {
  busy: false,
  blocked: false,
  isValid: true,
  numberStatus: 'IDLE',
  phoneOtp: false,
  snapshot: account,
  draft: { email: '', extension: '+91', number: '9845012345' },
  edited: true,
});
// { …, disabled: true,
//   numberLines: { hint: '', error: 'This is your current phone number, enter a different number to make a change.' } }

setState(noteContactEdit); // { …, error: null, edited: true }
```

Nothing here validates a SHAPE. Each surface's dialog is a real form (rule 10), and the
patterns it checks live in `@duncit/regex`, which this zero-dependency package cannot
import.

### Recovering a forgotten password

Three steps: pick where the code goes, prove it, set the password. mWeb renders it as one
card and the app as one screen, and both drive the state machine below — a second copy of it
drifts on exactly the question of whether a person can go back a step.

`PasswordRecoveryChannel` is `Extract<ContactChannel, 'EMAIL' | 'PHONE'>` and the draft is
`ContactDraft`, so the two files cannot disagree about what a phone number is.

```ts
previousRecoveryStep('CODE');     // 'CHANNEL'
previousRecoveryStep('PASSWORD'); // 'CODE'
previousRecoveryStep('DONE');     // null — the password already changed; Back would
                                  // offer to change it again with a spent code

passwordRecoveryStepIndex('CODE'); // 2
PASSWORD_RECOVERY_STEP_COUNT;      // 3 — DONE is an outcome, not a step to fill in
```

"Forgot password?" sits beside the password box, so it already knows where the code should go:
the tab the person is on and what they typed. `recoveryHandoffFrom` packs that up, recovery
reads it back with the strict `readRecoveryHandoff`, opens on that channel with
`recoveryStateFrom`, and sends at once when `recoveryHandoffSendable` says the destination is
complete (the regexes are passed in — this package has none):

```ts
const handoff = recoveryHandoffFrom('PHONE', { email: '', phoneExtension: '+91', phoneNumber: '9876543210' });
recoveryHandoffSendable(handoff, { email: EMAIL, extension: DIAL_CODE, number: PHONE_INTL }); // true
recoveryStateFrom(handoff).channel; // 'PHONE' — the code goes to the number, not an email
```

`recoveryResendSeconds` counts from when the last code was SENT rather than from a server
timestamp, because the button being counted down is on the screen that sent it — a clock a
few seconds off the server must not leave somebody pressing a button that answers "wait 1s"
forever:

```ts
const sent = { lastSentAt: Date.now() - 12_000, resendAfterSeconds: 30 };
recoveryResendSeconds(sent);                       // 18
recoveryResendSeconds({ ...sent, lastSentAt: 0 }); // 0 — never below zero

recoveryDestination('PHONE', { email: '', extension: '+91', number: '9845012345' });
// '+91 9845012345' — what "We sent a code to …" says back
```

`buildOtpLoginLabels` is Continue with OTP — passwordless sign-in. It returns the SAME
label shape, overriding only the words that mean something different when a correct code
opens a session instead of a password form (the headings, and the verify button), so both
apps render the same channel and code steps for both flows:

```ts
buildOtpLoginLabels(t).verify; // 'Verify & sign in' — recovery says 'Verify code'
buildOtpLoginLabels(t).resend; // identical to recovery: same cooldown, same mechanics
```

### Joining Duncit, one question at a time

Signup is four steps, and the order is the point: the two that cost nothing come first (who
you are, how we reach you), the password comes third so it is typed once the person is already
committed, and the WhatsApp code is last because it is the step that CREATES the account —
nothing exists until it is answered, which is why there is no way past it on either door.

`SIGNUP_STEP_FIELDS` is what "Continue" validates: RHF's `trigger` takes exactly that list, so
a step can only be left once its OWN boxes are right and nobody is told off about a box two
screens ahead.

```ts
SIGNUP_STEP_FIELDS.WHO;       // ['name', 'dob', 'referralCode']
SIGNUP_STEP_FIELDS.CONTACT;   // includes 'whatsappIsMobile' — the tick box is CONTACT's
nextSignupStep('CONTACT');    // 'SECURITY'
stepSubmitsAccount('SECURITY'); // true — the last step with boxes; VERIFY spends the answers
canLeaveSignupStep('VERIFY'); // false — the account exists; Back would offer a spent form
```

Both apps render the same four steps from `buildSignupStepperLabels`; the MUI and Tamagui
components stay separate and thin (rule 40).

Google is the same four steps with the first three answered for it, so it lands straight on
VERIFY — where it has to ask for the WhatsApp number and the date of birth before it can ask
for the code, because a Google credential carries neither. `detailsTitle` / `detailsSubtitle`
are that half-step's words, and `sameAsMobile` / `sameAsMobileHint` are the tick box's,
rendered from the same builder so neither door words it differently.

### What signup is holding, and what it is doing

`signupFlowReducer` is the state machine both doors run on. Nothing is created until the
WhatsApp code answers, so signup spends three steps HOLDING things: the form's answers, or —
on the Google door — a credential that has proved an address and nothing else. Exactly one of
`pendingForm` / `pendingGoogle` is ever set, which is how the last step knows which door it is
finishing without the code step knowing about either.

The reducer had been written twice, byte-identical, in the two `useSignupFlow` hooks. It is a
function, not a hook, so this zero-dependency package can own it while the effects that differ
per surface — Apollo vs the native services, navigate vs flipping the auth gate — stay in each
app (rule 40). The form values are a type parameter because their schema lives in
`@duncit/forms`, which this package cannot import; all the machine needs from them is the
three number boxes in `SignupNumberFields`.

```ts
let state = initialSignupFlowState<SignupFormValues>();
state.step;              // 'WHO' — holding nothing yet

state = signupFlowReducer(state, { type: 'GOOGLE_ACCEPTED', credential });
state.step;              // 'VERIFY'
state.askingNumber;      // true — Google brought no number to send a code to, and no birthday

state = signupFlowReducer(state, {
  type: 'DETAILS_GIVEN',
  values: { ...whatsappNumberValues, dob: '1998-04-23' },
});
state.askingNumber;      // false — both doors meet at the code step now
state.verifying;         // { extension: '+91', number: '9845012345', alsoMobile: true }
state.googleDob;         // '1998-04-23' — what signupWithGoogle is sent, since Google never had it

signupNumberOf({ phoneExtension: '+91', phoneNumber: '9845012345', whatsappIsMobile: false });
// { extension: '+91', number: '9845012345', alsoMobile: false }
```

The email door skips the number step entirely: `FORM_FILLED` sets `verifying` from the answers
it already carries, because that form asked for the number two steps earlier.

### The contact step, checked as it is typed

"Email already in use" used to be discovered on the LAST step: the code request was the first
time the email and the number were looked up, so a taken one was a refusal two screens after
the box that asked for it — with a code already on its way. Both boxes ask the server as they
are typed now, and the step cannot be left while one of them is somebody's.

The round trip is `scheduleAvailabilityCheck`, which the @handle field shares: the 400ms
debounce, the cleanup that drops a reply for a value no longer in the box, and a failed ask
reported as `failed` rather than as an answer. `scheduleSignupContactCheck` is that trip typed
to a yes/no, and `signupContactStatus` is what the answer means:

```ts
signupContactStatus(null, IDLE_SIGNUP_CONTACT_CHECK);                                   // 'IDLE'
signupContactStatus('riya@duncit.com', { checking: true, answer: null, failed: false }); // 'CHECKING'
signupContactStatus('riya@duncit.com', { checking: false, answer: false, failed: false }); // 'TAKEN'
signupContactStatus('riya@duncit.com', { checking: false, answer: null, failed: true });  // 'UNKNOWN'

signupContactsBlockContinue(['AVAILABLE', 'CHECKING']); // true — the answer is still in flight
signupContactsBlockContinue(['AVAILABLE', 'UNKNOWN']);  // false — a hint that could not be fetched never blocks signup
```

`UNKNOWN` deliberately does not block: the person is one step from a code request that checks
the same thing, and an outage of this query must not become an outage of signup. The shapes are
handed in rather than restated, because they are `EMAIL`, `DIAL_CODE` and `PHONE_INTL` from
`@duncit/regex` — the very patterns the signup schema runs, so a box only asks about what the
form would accept:

```ts
signupEmailCandidate(' Riya@Duncit.com ', EMAIL);                         // 'riya@duncit.com'
signupEmailCandidate('riya@', EMAIL);                                      // null — still being typed
signupPhoneCandidate('+91', '9845012345', { extension: DIAL_CODE, number: PHONE_INTL });
// '+91 9845012345'

signupContactLines('TAKEN', { hint, checking, taken });    // { hint, error: taken }
signupContactLines('CHECKING', { hint, checking, taken }); // { hint: checking }
```

On both surfaces the FORM runs the two checks — its `useSignupEmailCheck` /
`useSignupPhoneCheck` watch the boxes and own the round trip, because a package the native app
consumes cannot import React — gates Continue (and the Google door's Send code) on
`signupContactsBlockContinue`, and passes each status down as a prop. The step and the
WhatsApp row only render `signupContactLines` under the box — the refusal on the error line,
the "checking" line in place of the hint — from copy prebuilt as
`buildSignupStepperLabels(t).contactCopy.email` / `.phone`, so neither surface spells a key.
`requestSignupWhatsAppOtp` and `register` still refuse a taken contact: this is the correction
beside the box, not the gate.

### The follow button, and the follow rows in the inbox

Following a PRIVATE profile is a REQUEST, not a follow. The server is the only thing that
writes a follow edge; `followActionFor` / `nextFollowStatus` exist so the button predicts the
same outcome the server will produce, which is what makes an optimistic update safe.

```ts
followActionFor('REQUESTED');        // 'CANCEL_REQUEST' — there is no edge to unfollow yet
nextFollowStatus('NONE', true);      // 'REQUESTED' — a private profile is asked
nextFollowStatus('NONE', false);     // 'FOLLOWING'
```

The button's label knows the OTHER direction too. `PublicProfile.follows_viewer` says whether
this person already follows the viewer, and `followButtonLabelKey` turns the resting state
into "Follow Back" — the same words the inbox uses for the same tap, so a profile and the
notification about that person never disagree. Only NONE changes; REQUESTED and FOLLOWING
read as they always have.

```ts
followButtonLabelKey('NONE', true);       // 'mweb.follow.followBack' — they follow you, you don't follow them
followButtonLabelKey('NONE', false);      // 'mweb.follow.follow'
followButtonLabelKey('FOLLOWING', true);  // 'mweb.follow.following' — mutual, nothing to offer
```

A request is answered from two places — the inbox row, and the profile itself, which
carries `inbound_request_id` (the owner's OPEN ask against the viewer) so Accept / Deny can
sit above the button. Both act on the same FollowRequest; whichever the viewer reaches first
is the one that counts.

`followRequestRowState` is the same idea for the notification inbox. It takes a row exactly
as `myNotifications` returns it and says what that row offers:

```ts
followRequestRowState({ actionType: 'FOLLOW_REQUEST', requestId: 'fr-4821', status: 'PENDING' });
// 'ANSWER'      — Accept / Deny
followRequestRowState({ actionType: 'FOLLOW_REQUEST', requestId: 'fr-4821', status: 'ACCEPTED', followBackStatus: 'NONE' });
// 'FOLLOW_BACK' — 'Accepted', and an offer to follow them back
followRequestRowState({ actionType: 'FOLLOW_REQUEST', requestId: 'fr-4821', status: 'CANCELLED' });
// 'HIDDEN'      — withdrawn by the requester; the server deletes the row, and a stale one
//                 must not read as "Denied", an answer the viewer never gave
followRequestRowState({ actionType: 'NEW_FOLLOWER', actorId: 'u-aarav', followBackStatus: 'NONE' });
// 'FOLLOW_BACK' — no request behind it, so the button stands alone
followRequestRowState({ actionType: 'NEW_FOLLOWER', actorId: 'u-meera', followBackStatus: 'FOLLOWING' });
// 'HIDDEN'      — already followed back, so there is nothing to offer
```

`followOutcomeLabelKey` is the line a settled row states in place of Accept / Deny —
`'mweb.follow.accepted'`, `'mweb.follow.rejected'`, or null when there is nothing to state
(still open, withdrawn, or a NEW_FOLLOWER row).

`offersFollowBack` is the question the row asks once the ask is settled: is there somebody
here the viewer chose to let in and does not follow yet? Follow Back is the SECOND step of
this flow, never a parallel one — a PENDING request offers Accept / Deny alone, because
offering the button beside them let a viewer follow somebody whose request they were about
to deny. It is exactly the `FOLLOW_BACK` state, plus a check that there is an `actorId` to
act on.

```ts
const asking = { actionType: 'FOLLOW_REQUEST', requestId: 'fr-4821', status: 'PENDING', actorId: 'u-riya', followBackStatus: 'NONE' };
followRequestRowState(asking);  // 'ANSWER'  — Accept / Deny
offersFollowBack(asking);       // false     — ...and nothing else until one of them is tapped
offersFollowBack({ ...asking, status: 'ACCEPTED' });             // true  — 'Accepted', and the button
offersFollowBack({ ...asking, status: 'DENIED' });               // false — the viewer said no
offersFollowBack({ ...asking, status: 'ACCEPTED', followBackStatus: 'FOLLOWING' });  // false — already followed
offersFollowBack({ ...asking, status: 'ACCEPTED', actorId: null });                  // false — nobody to act on
```

`NEW_FOLLOWER` matters more than it looks: a PUBLIC profile never receives a follow request,
so "X started following you" is the only follow row it ever gets. Without it there is no way
to follow anybody back from the inbox at all. Rows written before the actor column existed
carry no `actorId` and stay inert rather than rendering a button with nobody to act on.

`followBackLabelKey` and `canFollowBack` split the button's two live states: an open ask
reads "Requested" and stops accepting taps, because a pending request has nothing to re-send.

## An Auto Pod enrols venue → host → club admin, and the first partner pins its city

A fresh physical offer is visible to venues only; once a venue has fixed a slot it reaches
hosts, and once a host is on it, club admins. A virtual offer has no venue and reaches hosts
first. `autoPodNextRole(row)` names whose turn it is, and `autoPodActionable(row, role)` is true
only for that role while the offer is pre-live and the viewer has not enrolled — so the venue ›
host › club order in `AUTO_POD_ROLES` is the dependency as well as how the chips are drawn. A
venue or host may take their enrolment back until the club admin's claim completes the pod
(`autoPodWithdrawable(row, role)`), at the Account Health cost the row carries in
`withdraw_penalty_points`; a club admin's claim is final.

What the first enrolment DOES fix is the city. An offer starts with `location: null`; the first
partner to enrol pins it to one admin Location row — a venue brings `venue.location_id`, a club
`club.location_id`, and a host the city selected at the top of their Auto Pods page. From then on
only partners in that city are offered it, and the server refuses a venue or club from anywhere
else. Two consequences a surface must render, and both come from here:

- `autoPodHostNeedsLocation(row, locationId)` — a host has no venue or club to bring a city with,
  so on an unpinned offer their "Assign Myself" is locked until they have selected one
  (`labels.pickLocationFirst`), and enrolling then pins it (`labels.willPinTo(city)`). On a
  pinned offer the selection is not consulted.
- `autoPodCityLabel(row.location)` — the card's city line, `labels.pinnedTo(city)` once pinned
  and `labels.unpinned` before, in exactly the same words on mWeb, native and every portal.

`autoPodMissingRoles(row)` feeds `labels.waitingFor(roles)` — "Waiting for a venue, a host" —
the card's line naming everyone still to come, in the order they will.

## Adding a helper

`src/index.ts` is a pure re-export barrel and is coverage-excluded; everything else is under a
100/100/100/100 vitest gate. A new helper needs its branches tested before it will build, and it
must stay framework-free — no React, no MUI, no Tamagui, no Apollo. If a helper needs one of
those, it belongs in `@duncit/ui` (MUI) or the consuming app, not here.

## Host Studio insights

`host-insights.ts` is the data behind the four Host Studio charts. mWeb draws them with
`@mui/x-charts` and the app with `gifted-charts` — two views that can never be shared — but the
NUMBERS have to be identical, because a host reads them beside the money the settlement pays
out. They were two near-identical ~190-line files (`app/mweb/.../insights.ts` and
`app/mobile-app/src/utils/host-insights.ts`), and the app's copy had already hard-coded the
donut palette instead of reading the shared tokens.

```ts
buildPodsOverTime(dates, 'PAST_6_MONTHS'); // pods per month, empty months at 0
buildParticipantTrend(pods); // seats taken minus the host(s), per pod, in date order
buildStatusSlices(counts, semantic, t); // the donut, coloured by the caller's palette
buildEarningsBars(rows); // "2026-08" -> { label: 'Aug', value: 4200 }
allZero(series); // what drives the empty state
```

Two arguments are injected rather than held here, and both for the same reason — this package
has **zero dependencies**:

- **the palette.** Both surfaces pass `semantic` from `@duncit/auth-tokens`. Keeping the hex
  codes here would be a zero-dependency copy of the design tokens, which is exactly how the
  app's donut got its own literals.
- **the translator.** Every label is a `mweb.hostDashboard.insights.*` key (rule 38). The range
  names and chart titles were English literals inside both copies before this moved.

`hostRangeOptions` and `hostRangeMeta` and `buildPodsOverTime` also take an optional `now`, so a
test run on 31 December does not disagree with one run on 1 January.

`buildParticipantTrend` counts **seats**, not people: it sits beside money, and the settlement
it has to agree with is priced per seat. It also copies before sorting — the caller's array is
usually the Apollo cache's, and sorting that in place is a render-loop bug waiting to happen.

## Parcel weights and packaging presets

`parcel.ts` is the arithmetic ShipRocket bills by, for the product forms' live readout. A
courier charges the **higher** of the packed weight and the volumetric weight
(L × B × H in cm / 5000), so a light toy in a big box costs what the box would. The server keeps
a twin (`shiprocket.parcel.ts`) because it imports no `@duncit/*` package; their tests pin the
same numbers.

| Export | What it answers |
| --- | --- |
| `volumetricWeightKg(l, b, h)` | L × B × H / 5000, in kg |
| `chargeableWeightKg(dims)` | The weight the courier bills |
| `parcelWeights(dims)` | `{ volumetric, chargeable, boxHeavier }` — `boxHeavier` drives the "box is too big" hint |
| `packagingGaps(dims)` | The dimension fields still missing or under the minimum |
| `PACKAGING_PRESETS` | Six one-click packs (small pouch … bed/large), each with a `labelKey` |
| `PACKAGING_LIMITS` | The bounds the server enforces (0.05–50 kg, sides ≥ 0.5 cm) |

```ts
import { parcelWeights, PACKAGING_PRESETS } from '@duncit/utils';

const foodBag = PACKAGING_PRESETS.find((p) => p.id === 'food-bag-10')!;
parcelWeights(foodBag); // { volumetric: 7.2, chargeable: 10.4, boxHeavier: false }
parcelWeights({ weight_kg: 2.5, length_cm: 70, breadth_cm: 50, height_cm: 20 });
// { volumetric: 14, chargeable: 14, boxHeavier: true } — the bed ships at 14 kg
```

## The brand onboarding wizard — `brand-wizard`

`brand-wizard.ts` is the ten-step brand registration the Partners console runs and the Products
console reviews: which steps exist, which count towards completion, and when each is done. The
server keeps a twin (`ecommBrand.completion.ts`) because it imports no `@duncit/*` package;
the server's number is what the **Your brands** table shows, this copy is the wizard's live
readout while the partner is still typing.

| Export | What it answers |
| --- | --- |
| `BRAND_WIZARD_STEPS` | The ten steps in order — Integration LAST — each with its `labelKey`, whether it is `required` and whether it `gatesReview` |
| `brandStepComplete(facts, key)` | Is this step done? `review` is done once every review step before it is (integrations are not owed) |
| `brandStepStates(facts)` | Every step with its `complete` flag — what the vertical stepper draws |
| `brandCompletionPercent(facts)` | Required steps done, as a whole number; 100 = ready to go live |
| `brandReviewReady(facts)` | Can the brand be submitted? Every `gatesReview` step done and the consent signed — integrations may still be pending |
| `brandIntegrationReady(facts)` | Can an approved brand go live? Razorpay connected and shipping settled |
| `brandNextStepIndex(facts)` | Where a saved draft opens — the first required step still to do |
| `BRAND_CONSENT_POLICY_SLUG` | The Legal-portal policy signed before submitting |
| `brandShippingReady(mode, ownConnected)` | Is shipping settled? `DUNCIT_COURIER` needs nothing from the brand; its own ShipRocket must be connected |

Payout is optional (it never lowers the percentage) and Review is derived. Integration is the last
step and does not gate review: a brand is submitted and approved on its business facts and consent,
and goes **live** in the pod shop (server `EcommBrand.live`) once it is connected. Integration needs
Razorpay connected plus the brand's shipping settled: `shipping_mode` is `DUNCIT_COURIER` (Duncit's
courier carries the parcels) or the brand's own ShipRocket is connected. Connection is something
only the server can say — pass the brand's `shipping_mode`, `integrations.*.connected` and
`consent.accepted` through as facts.

```ts
import { brandCompletionPercent, brandStepStates } from '@duncit/utils';

const facts = {
  brand_name: 'Yonex', description: 'Badminton gear for club players.', contact_email: 'ops@yonex.in',
  registered_business_name: 'Yonex India Pvt Ltd', gstin: '29AABCY1234F1ZP',
  address_line1: '14 MG Road', city: 'Bengaluru', state: 'Karnataka', postal_code: '560001',
  product_categories: ['Sports Equipment'], logo_url: 'https://ik.imagekit.io/duncit/brands/yonex.png',
  documents: [{ type: 'GST certificate', url: '…' }],
  shiprocket_connected: true, razorpay_connected: false, consent_signed: false,
};
brandCompletionPercent(facts); // 75 — consent and integration still to do
brandStepStates(facts).filter((s) => s.required && !s.complete).map((s) => s.key); // ['consent', 'integration']
brandReviewReady({ ...facts, consent_signed: true }); // true — submit now; connect Razorpay to go live
```

## Product-order fulfilment

`product-orders.ts` is the status vocabulary for an add-on product order. Three surfaces render
the same order — the buyer in mWeb's Pod History and in the app, the seller in the Products
portal — and they held three copies of the list. The two the buyer saw **disagreed with the one
the seller drives**:

| | seller (Products portal) | buyer (mWeb + app), before |
| --- | --- | --- |
| SHIP flow | starts at `PENDING` | started at `AWAITING_SHIPMENT` |
| PICKUP flow | has `PICKUP_SCHEDULED` | had no such rung |

`buildOrderTimeline` falls back to the first rung for a status its flow does not contain, which
is right — the timeline is never empty or broken — but it is also what hid both bugs. A
just-placed shipped order read "Preparing shipment" before anyone had touched it, and an order
the seller had scheduled for collection read back to the buyer as "Order placed".

The flows here are the seller's, because that is what the server moves through.

```ts
fulfilmentFlow('SHIP'); // PENDING → AWAITING_SHIPMENT → AWB_ASSIGNED → SHIPPED → OUT_FOR_DELIVERY → DELIVERED
fulfilmentFlow('PICKUP'); // PENDING → PICKUP_SCHEDULED → READY_FOR_PICKUP → PICKED_UP
buildOrderTimeline(order, t); // the flow with `done` / `current` marked
isTerminalFulfilment('RTO'); // true — the timeline collapses to one step
statusLabel('AWB_ASSIGNED', t); // 'Courier assigned'
trackingUrl(awb); // '' until an AWB exists, so the caller shows no link
shiprocketOrderUrl(order.shiprocket.order_id); // the order in the ShipRocket seller panel, '' until ShipRocket has it
brandOrderActions(order); // { book, editAddress, documents, cancel, refreshTracking } — the brand desk in the Partner console, mWeb and the native Studio
BRAND_CANCELLABLE.has(order.fulfilment_status); // the states `cancel` is offered in: before the courier has the parcel (the server enforces the same set)
```

Labels are `fulfilment.*` keys (rule 38). The portal previously ran a `humaniseStatus` that
title-cased the raw code — it rendered "Awb Assigned" and "Rto", and reached no translator at
all. An **unknown** code still renders as itself: the server can add a state before any client
knows about it, and a visible `AWAITING_QUANTUM_TUNNEL` beats a blank chip.

`FULFILMENT_TONE` names the chip weight by meaning (`pending` / `moving` / `done` / `failed` /
`neutral`) and `TONE_CHIP_COLOR` maps it onto MUI's palette, so no surface picks its own
colours — the same shape [@duncit/verification](/packages/verification) uses.

## Pod Shop returns and refunds — `pod-shop-returns`

My Product Orders reads the same rules in mWeb and the app (rule 27): which orders can still be
returned and until when, what a refund line says, and what a return's status is called. They
were two line-for-line copies; the duplicate-code gate is why they live here.

The server decides what is returnable — each order carries `returnable[]` (units left and the
deadline, from the return window the brand set on the product when it was bought) and a
`refund` record. These helpers only read it:

```ts
openReturnLines(order.returnable); // lines with units left — empty hides "Return items"
```

## The buyer's order detail page — `order-tracking`

mWeb's `/orders/:orderId` and the app's `OrderDetail` screen render one order in full (rule 27).
What they decide is here; each app only draws it.

```ts
buildDetailedOrderTimeline(order, t);
// SHIP order that is SHIPPED → the whole ladder, first rung first:
// [{ status: 'PENDING', done: true, at: order.created_at, scans: [] }, …,
//  { status: 'SHIPPED', current: true, tone: 'moving', at: '2026-10-02T09:00:00.000Z',
//    location: 'Hyderabad Hub', note: 'Bag received',
//    scans: [{ label: 'PICKED UP', location: 'Bengaluru', note: '…', at: '…' }, { label: 'IN TRANSIT', … }] },
//  { status: 'OUT_FOR_DELIVERY', at: null, tone: 'neutral', scans: [] }, …]

courierScanStatus('Reached at destination hub'); // 'SHIPPED' — null for a label that says nothing we track
orderSupportDraft(order, t); // { subject: 'Help with order #ord_1', category: 'QUESTION', message: '…' }
orderDownloads(order); // { invoice: true, sellerInvoice: false }
```

**The timeline** is `buildOrderTimeline`'s ladder with the stored `tracking_events` folded in.
It is always in **ladder order** (first rung first, scans oldest first under their rung) on both
apps.

| Order | What is drawn |
| --- | --- |
| On its ladder | Every rung of the flow: done, current, still ahead (`at: null`). |
| Came to rest off the ladder — cancelled, lost, failed, returned (`RTO`, `RTO_DELIVERED`) | The rungs it really reached, then **one closing step** for where it stands. Nothing it never reached is drawn. |
| Still moving, in a status its ladder does not carry — a booked shipment waiting for its courier pickup (`PICKUP_SCHEDULED` on a `SHIP` order), a failed attempt (`NDR`), a status no client knows yet | The rungs it reached, then that status as the current step, then the rest of the ladder still ahead — never an empty timeline, and never "Order placed" again. |

A rung's `at` is the order's own date where it has one (`created_at` for the first rung,
`delivered_at` for delivery or collection, `cancelled_at` for a cancellation), else the first
event that proves the rung. Two kinds of event are stored and they are treated differently:

- **Courier scans** (`code` set) carry the courier's label, place and note. `courierScanStatus`
  maps the label onto our lifecycle — the same rules as the server's `mapShiprocketStatus` — to
  file the scan under its rung. A scan it cannot place stays on the rung the parcel was already
  on; a scan never files under a rung the order has not reached.
- **Platform events** (`code` 0 — a booking step, an operator's manual move) give a rung its
  time only. Their notes are written for operators and are never shown; a cancelled step's
  `note` is the order's `cancel_reason`.

**The support draft** is what "Get help with this order" prefills. A ticket can only reference a
pod, so the order's references go in the body, as `paymentTicketDraft` does: order number, items,
status, and the AWB and payment reference when they exist. The copy is `mweb.orderDetail.support*`
through `t`, because the buyer reads and edits it before sending. `category` is one of the
values both ticket forms offer: `PAYMENT` when the order is cancelled or a refund is recorded,
else `QUESTION`.

**Downloads**: the Duncit invoice whenever a payment stands behind the order; the seller's tax
invoice once a `SHIP` order has a ShipRocket shipment — the server refuses it before that, and a
collected order never has one.

| Export | Signature | Meaning |
| --- | --- | --- |
| `buildDetailedOrderTimeline` | `(order, t) => DetailedTimelineStep[]` | The ladder with times, places, notes and scans. |
| `courierScanStatus` | `(label) => FulfilmentStatus \| null` | A courier scan label as one of our statuses. |
| `orderSupportDraft` | `(order, t) => { subject, category, message }` | The prefilled support ticket for an order. |
| `orderDownloads` | `(order) => { invoice, sellerInvoice }` | Which documents the detail page offers. |

## Employee expense claims

`employee-expense.ts` is the shape the two ends of one flow agree on. An employee files a
claim in the Employee console; Finance approves or rejects it in the Finance console. Same
row, same categories, same selection — read by two different portals.

Both halves were plausible to write independently, and both would have been wrong the same
way. A category added on the server and to one portal's list is a claim the other portal
renders with a blank cell. A field added to one console's selection is a column the other
console shows as empty, with nothing failing anywhere.

```ts
EMPLOYEE_EXPENSE_CATEGORIES; // ['TRAVEL', 'FUEL', 'MEALS', … 'MEDICAL', 'OTHER']
EMPLOYEE_EXPENSE_STATUSES; // ['PENDING', 'APPROVED', 'REJECTED']
EMPLOYEE_EXPENSE_STATUS_COLORS.PENDING; // 'warning' — one meaning of amber, both consoles
EMPLOYEE_EXPENSE_STATUS_KEYS.REJECTED; // 'employeeExpense.status.REJECTED'
EMPLOYEE_EXPENSE_SELECTION; // the GraphQL field list both queries interpolate
```

The status keys are written out rather than composed from the status value. The rule-38 gate
only sees a key that appears somewhere as a quoted literal, so a key built inside a template

sees them.

of one screen, and rule 40's twin clause applies — they share the shape, never the UI.

## A link into another city

`location-mismatch.ts` is the question both apps ask before they open a pod, club or venue
that arrived as a shared link: is this thing somewhere other than where the viewer is
browsing? A viewer set to Mumbai who opens a Bengaluru pod used to land on it with a Mumbai
header, a Mumbai feed behind the Back button and nothing on the page saying so. Now a dialog
names both places and offers to switch.

```ts
locationMismatch(
  { id: '66f1…2a70', city: 'Mumbai', zone: 'Bandra' }, // the header's selection
  { id: '66f1…2a6e', city: 'Bengaluru', zone: 'Indiranagar' }, // pod.location_id + pod.zone_name
);
// {
//   current: 'Mumbai · Bandra', currentCity: 'Mumbai',
//   target: 'Bengaluru · Indiranagar', targetCity: 'Bengaluru',
//   targetId: '66f1…2a6e', targetZone: 'Indiranagar',
// }

locationMismatch({ id: 'x', city: 'Pune' }, { id: 'x', city: 'Pune', zone: 'Baner' }); // null — same city
locationMismatch({ id: '', city: '' }, { id: 'y', city: 'Pune' }); // null — header not hydrated yet
locationLabel('Bengaluru', 'Indiranagar'); // 'Bengaluru · Indiranagar'
```

It compares **cities**, never areas: two localities of one city share a feed, so a link into
the next zone is not a change of place. It answers `null` whenever either side is unknown —
the selection has not hydrated, the entity carries no `location_id`, or the id cannot be
named — because a dialog that opens over a half-loaded page, or reads "Switch to ", is worse
than none.

The `*City` fields exist for the two buttons ("Switch to Bengaluru", "Continue in Mumbai"),
which would otherwise carry the full `City · Area` label and wrap. `targetId` + `targetZone`
are what the switch selects, so the header lands on the pod's own area, not just its city.

The MUI dialog is mWeb's `LocationMismatchDialog`; the Tamagui one is the native app's. Each
surface's `useLocationMismatch` hook resolves the two ids to names against its own location
list and hands this result to its dialog — rule 40's twin clause: one rule, two views.

## Theme tokens — bundled, or the admin's

`theme-tokens.ts` decides which light and dark palettes mWeb and the native app theme with.

## Tracking consent — `consent` + `web-attribution`

GDPR / ePrivacy: nothing optional is stored about a visitor until they say yes. Two optional
categories exist — `analytics` (page views, taps, daily-active pings, Google Analytics) and
`marketing` (short-link click ids, utm tags, the cross-site link decorator). Everything else the
apps keep — the session, the cart, the language, the choice itself — is strictly necessary.

"Undecided" and "declined" behave the same: nothing optional runs. The only difference is that
an undecided visitor still sees the banner. A choice older than `CONSENT_MAX_AGE_DAYS` (365)
reads as undecided, so the question is asked again yearly.

The web surfaces keep the answer in ONE first-party cookie on `.duncit.com`, so answering on the
website answers on mWeb and every portal too. The native app keeps the same serialised string in
secure storage. Every request carries it to the server as `x-consent`, and the server refuses to
store analytics or attribution without it — a call site that forgets to gate still cannot write.

```ts
import {
  consentAllows,
  consentHeaderValue,
  makeConsent,
  readWebConsent,
  whenWebConsentAllows,
  writeWebConsent,
} from '@duncit/utils';

writeWebConsent(makeConsent({ analytics: true, marketing: false }));
consentHeaderValue(readWebConsent()); // 'analytics'
consentAllows(readWebConsent(), 'marketing'); // false
whenWebConsentAllows('analytics', () => loadAnalytics()); // runs now, or the moment it is allowed
```

`startWebShortLinkAttribution(serverUrl, search?)` is how every web surface starts attribution.
The landing is always reported, so the link's click count stays honest. The server stores it with
nothing that identifies the visitor unless `?c=1` (`SHORT_LINK_CONSENT_PARAM`) says marketing was
allowed. The click id is kept on the device only with that consent. If consent arrives after the
page loaded, `rememberShortLinkAttribution` fills it in then, without reporting the visit again.
`captureShortLinkAttribution` now takes a required `consent` flag.

| `parseConsent` / `serializeConsent` | `(raw) => ConsentChoice \| null` / `(choice) => string` | Storage format; expired or malformed reads as `null`. |

## Wallet statement periods — `statement-period`

The partner console, mWeb and the native app all offer "Download statement" on the wallet. This
module is the one definition of what each period preset means, so the same tap asks the server
for the same days on every surface.

A period is two calendar days, both inclusive, written `yyyy-MM-dd` — the shape the server's
`WalletStatementInput` takes. "Today" is read in the **business time zone** you pass in (the
admin's `time_zone`, from `useDateFormat().timeZone`), never the device's. The Indian financial
year runs 1 April – 31 March and turns over at midnight in that zone.

```ts
import {
  STATEMENT_PRESETS,
  STATEMENT_PRESET_LABEL_KEYS,
  STATEMENT_RANGE_ERROR_KEYS,
  resolveStatementRange,
  statementPresetRange,
  statementRangeError,
} from '@duncit/utils';

const now = new Date('2026-10-11T06:30:00Z'); // 12:00 on 11 Oct in Kolkata
const zone = 'Asia/Kolkata';

statementPresetRange('THIS_MONTH', now, zone); // { from: '2026-10-01', to: '2026-10-11' }
statementPresetRange('LAST_MONTH', now, zone); // { from: '2026-09-01', to: '2026-09-30' }
statementPresetRange('LAST_3_MONTHS', now, zone); // { from: '2026-07-12', to: '2026-10-11' }
statementPresetRange('THIS_FINANCIAL_YEAR', now, zone); // { from: '2026-04-01', to: '2026-10-11' }
statementPresetRange('LAST_FINANCIAL_YEAR', now, zone); // { from: '2025-04-01', to: '2026-03-31' }
statementPresetRange('CUSTOM', now, zone); // null — the reader picks the days

// One minute apart, two financial years:
statementPresetRange('THIS_FINANCIAL_YEAR', new Date('2026-03-31T23:59:00+05:30'), zone);
// { from: '2025-04-01', to: '2026-03-31' }
statementPresetRange('THIS_FINANCIAL_YEAR', new Date('2026-04-01T00:00:00+05:30'), zone);
// { from: '2026-04-01', to: '2026-04-01' }

statementRangeError({ from: '2026-06-30', to: '2026-04-01' }, now, zone); // 'ORDER'
statementRangeError({ from: '2026-10-01', to: '2026-10-12' }, now, zone); // 'FUTURE'
statementRangeError({ from: '2025-10-09', to: '2026-10-10' }, now, zone); // 'TOO_LONG' (367 days)
statementRangeError({ from: '2026-04-01', to: '2026-06-30' }, now, zone); // null

// What the form sends: the preset's days, or the custom ones exactly as picked.
resolveStatementRange({ preset: 'CUSTOM', from: '2026-04-01', to: '2026-06-30' }, now, zone);
// { from: '2026-04-01', to: '2026-06-30' }

const label = t(STATEMENT_PRESET_LABEL_KEYS.LAST_FINANCIAL_YEAR); // 'Last financial year'
const problem = t(STATEMENT_RANGE_ERROR_KEYS.FUTURE); // 'A statement cannot include future dates'
```

| Export | Signature | Meaning |
| --- | --- | --- |
| `STATEMENT_PRESETS` | `readonly StatementPreset[]` | The seven presets in picker order: this month, last month, last 3 and 6 months, this and last financial year, custom. |
| `STATEMENT_FORMATS` | `readonly ['PDF', 'CSV']` | The file formats; the values are the server's `WalletStatementFormat` members. |
| `STATEMENT_MAX_DAYS` | `366` | The longest period a statement may cover — one leap financial year. |
| `STATEMENT_PRESET_LABEL_KEYS` | `Record<StatementPreset, string>` | The `withdraw.statement.preset*` key for each preset. |
| `STATEMENT_RANGE_ERROR_KEYS` | `Record<StatementRangeError, string>` | The `withdraw.statement.error*` key for each refusal. |
| `zonedToday` | `(now: Date, timeZone: string) => string` | Today's `yyyy-MM-dd` in that zone. An unknown zone falls back to the UTC day. |

"Last 3 months" and "Last 6 months" are rolling windows that end today, clamped to month length:
three months back from 31 May starts on 1 March, in a leap year or not. "This financial year" ends

statement for the wrong period. The Zod schema the three forms share is `makeWalletStatementSchema`
in `@duncit/forms/schemas`, which calls `statementRangeError`.

## A venue's food menu and its QR order — `venue-food`

A guest scans the QR on the table, opens the venue's public page on its menu, fills a cart, pays the
venue's own Razorpay account and follows the order to the table — with no sign-in. This module is
the framework-free half of that: the menu and order types, the three documents (as plain strings,
like `public-page`), the cart math, and the keys every status is worded with.

```ts
import {
  PLACE_VENUE_FOOD_ORDER_MUTATION,
  VERIFY_VENUE_FOOD_ORDER_MUTATION,
  VENUE_FOOD_ORDER_QUERY,
  buildFoodOrderTimeline,
  foodOrderErrorCode,
  foodOrderErrorKey,
  foodOrderPollMs,
  formatFoodMoney,
  groupFoodMenu,
  priceFoodCart,
  reconcileFoodCart,
} from '@duncit/utils';

const groups = groupFoodMenu(venue.food_menu); // category headings, first-appearance order; uncategorised last
const { cart, dropped } = reconcileFoodCart(storedCart, venue.food_menu); // drops dishes that left the menu
const price = priceFoodCart(
  lines.map((line) => ({ unit_price: line.item.price, quantity: line.quantity })),
  venue.food_ordering.discount_pct,
);
formatFoodMoney(price.total, currencySymbol); // whole rupees stay whole

// A refused order → the sentence to show
t(foodOrderErrorKey(foodOrderErrorCode(error)));

// The order page
const everyMs = foodOrderPollMs(order); // 8000 unpaid, 20000 in the kitchen, 0 once served or cancelled
const steps = buildFoodOrderTimeline(order, t); // DetailedTimelineStep[], the product-order timeline's shape
```

`priceFoodCart` is the server's own arithmetic, in integer paise: each line is
`round(price × 100) × quantity`, the discount is `floor(subtotal × pct / 100)` — rounded down, so a
venue never gives away more than the percent it set — and the total is what is left. It is display
only; the server prices the order again from its own menu. `belowMinimum` is true under one rupee,
which the server refuses to send to the gateway.

`FOOD_ORDER_LIMITS` carries the server's limits (30 different dishes, 20 of one dish, the name,
table and note lengths) so a form refuses exactly what the server would. `FOOD_ORDER_ERROR` names
the two codes that change the page rather than just the message: `FOOD_ORDERING_CLOSED` (keep the
menu, drop the cart) and `FOOD_ITEM_UNAVAILABLE` (re-read the venue; `reconcileFoodCart` then drops
the dish), plus `CONFLICT` (repeat the same `client_key` a moment later) and `FOOD_COUPON_REJECTED`
(the order's coupon can no longer be used and nothing was placed — see the coupon section below).

The `client_key` is minted once per checkout attempt and repeated on every retry of it — the server
answers a repeated key with the order it already made, which is what makes a double tap harmless.

The checkout steps both apps share are here too, so mWeb and the native app cannot drift:

```ts

  foodCartSignature,
  priceFoodCartLines,
  tryPlaceFoodOrder,
  wait,
} from '@duncit/utils';

const lines = foodCartLines(venue.food_menu, cart); // FoodCartLine[] — { item, quantity }, in menu order
const price = priceFoodCartLines(lines, venue.food_ordering.discount_pct); // priceFoodCart at menu prices
const signature = foodCartSignature(lines); // changes whenever the cart's contents do

// One per screen. The app passes its own UUID source — this package has none.
const clientKey = createFoodClientKey(() => globalThis.crypto.randomUUID());
const input = buildFoodOrderInput({
  venueId: venue.id,
  lines,
  details: values, // { name, phone, table, note } — an empty table or note is sent as null
  clientKey: clientKey.keyFor(foodAttemptSignature(signature, values)), // same cart + details → same key
});

const { placement, error } = await tryPlaceFoodOrder(() => place(input)); // never throws
if (!placement) refuse(error); // `error` is null when the server answered with no order
else clientKey.reset(); // once the order is done with: the next one gets a new key
```

`createFoodClientKey` is built on the pure `foodAttemptKey(current, signature, mint)`, which answers
the `FoodAttempt` to keep: the current one for an unchanged signature, a newly minted key otherwise.
On a `CONFLICT`, `await wait(FOOD_ORDER_CONFLICT_RETRY_MS)` before placing again with the same key.

### A venue's coupon on a food order

A venue's owner can give its food guests coupon codes. The coupon is the venue's own — valid for
that venue's food orders only, funded by the venue — and has nothing to do with the Duncit coupons of
the pod and store checkouts. A guest needs no account to use one.

```ts
import {
  FOOD_COUPON_REJECTION_KEYS,
  FOOD_ORDER_ERROR,
  PREVIEW_VENUE_FOOD_COUPON_QUERY,
  buildFoodOrderInput,
  foodAttemptSignature,
  foodCouponRejectionOf,
  foodOrderErrorCode,
  foodOrderLineInputs,
  normalizeFoodCouponCode,
  priceFoodCartLines,
  type VenueFoodCouponPreview,
} from '@duncit/utils';

// 1. Ask the server what the code does to this cart. Public, and it changes nothing.
const preview: VenueFoodCouponPreview = await query(PREVIEW_VENUE_FOOD_COUPON_QUERY, {
  input: {
    venue_id: venue.id,
    coupon_code: normalizeFoodCouponCode(typed), // trimmed, upper case — as the server stores it
    items: foodOrderLineInputs(lines),
    customer_phone: values.phone || null, // lets the per-person limit be checked early
  },
});
if (!preview.ok) show(t(FOOD_COUPON_REJECTION_KEYS[preview.reason ?? 'INVALID'])); // amounts are the cart's without the code

// 2. Show the cart with it. An accepted preview is the coupon priceFoodCart takes.
const price = priceFoodCartLines(lines, venue.food_ordering.discount_pct, preview.ok ? preview : null);
price.discount; // the venue's automatic discount, as before
price.coupon; // what the coupon takes off
price.couponUnmet; // the cart fell under the coupon's minimum order: it takes nothing off

// 3. Place the order with it. The coupon rides in `details`, so the SAME object keys the attempt.
const details = { ...values, coupon: preview.ok ? preview.coupon_code : null };
const input = buildFoodOrderInput({
  venueId: venue.id,
  lines,
  details,
  clientKey: clientKey.keyFor(foodAttemptSignature(signature, details)),
});

// 4. A code that stopped being usable between the preview and the tap refuses the order.
if (foodOrderErrorCode(error) === FOOD_ORDER_ERROR.couponRejected) {
  show(t(FOOD_COUPON_REJECTION_KEYS[foodCouponRejectionOf(error) ?? 'INVALID']));
}
```

The arithmetic, which `priceFoodCart` mirrors and the server alone decides:

- the venue's automatic discount comes off the subtotal first, rounded down to a paisa;
- the coupon's percent comes off **what is left**, rounded down too;
- the coupon is then trimmed — never refused — so the guest still pays what the largest discount a
  venue may set (`FOOD_ORDER_LIMITS.maxDiscountPct`, 90%) would leave, and at least the one rupee the
  gateway can charge (`minTotalPaise`);
- a coupon's minimum order is compared with the subtotal, before any discount.

`discountPaise` / `discount` keep meaning the venue's automatic discount alone; `couponPaise` /
`coupon` are new beside them, and `totalPaise` is the subtotal less both. `priceFoodCart(lines, pct)`
without the third argument prices exactly as it always did.

An order carries `coupon_code` (null without one), `coupon_pct` and `coupon_discount_amount` beside
`discount_pct` / `discount_amount`; both order documents ask for them. `total` stays what was charged.

**GST.** The fourth argument is the GST the venue's orders are priced with — `foodCartTaxOf(venue.food_ordering)`
reads the `tax_mode` / `gst_pct` the server RESOLVED (the venue's own override, or Finance's food
default), so a client never decides which applies. GST meets what is left after both discounts (the
"net"), rounded **half up** to a whole paisa in integer arithmetic:

- `INCLUSIVE` — the net already holds the tax: `taxablePaise = round(net × 100 / (100 + pct))`,
  `taxPaise = net − taxablePaise`, and the total does not move;
- `EXCLUSIVE` — the tax is added on top: `taxablePaise = net`, `taxPaise = round(net × pct / 100)`.

Either way `totalPaise = taxablePaise + taxPaise`. `belowMinimum` is still judged on the net — GST added
on top never makes a cart payable. A percent that is not a whole positive number is no tax, and
`priceFoodCart(lines, pct, coupon)` without the fourth argument prices exactly as before.

```ts
import { foodCartTaxOf, foodTaxLine, priceFoodCartLines } from '@duncit/utils';

const price = priceFoodCartLines(lines, venue.food_ordering.discount_pct, coupon, foodCartTaxOf(venue.food_ordering));
// EXCLUSIVE 5% on a 180 net → { taxablePaise: 18000, taxPaise: 900, totalPaise: 18900 }
foodTaxLine(price.taxMode, price.gstPct, price.tax); // { mode: 'EXCLUSIVE', pct: 5, amount: 9 } — null at 0%
```

An order (and a coupon preview) carries `tax_mode`, `gst_pct`, `taxable_amount` and `tax_amount` —
all optional on an order read by an older document; an order from before GST reads as INCLUSIVE at 0%.
`foodTaxLine(order.tax_mode, order.gst_pct, order.tax_amount)` is the line the totals block draws.
`FOOD_GST_LIMITS` (`{ min: 0, max: 28 }`) and `VENUE_FOOD_TAX_MODES` mirror the server's bounds. The
shared fixture `__tests__/fixtures/venue-food-pricing.json` pins this and the server's `foodTotals`
to the same paise, GST cases included.

**The coupon is part of the attempt.** The server answers a repeated `client_key` with the order it
already priced — even if the coupon has since expired — so applying, changing or removing a code
must mint a new key. `foodAttemptSignature` reads `details.coupon` for exactly that (compared as the
server compares it, so `welcome10` and `WELCOME10` are one attempt); pass the same `details` object
to it and to `buildFoodOrderInput`, which sends `coupon_code` only when there is one.

The reasons a code is refused are `VenueFoodCouponRejection`: `INVALID` (no such code at this venue,
or switched off — the two are deliberately indistinguishable), `NOT_STARTED`, `EXPIRED`,
`MIN_ORDER_NOT_MET`, `USAGE_LIMIT_REACHED`, `PER_PERSON_LIMIT_REACHED` and `NO_DISCOUNT` (the order
already has the largest discount it can take). `FOOD_COUPON_REJECTION_KEYS` maps each to its sentence
under `mweb.venueFood.coupon.rejected.*`; the preview also carries the server's own `message`, whose
`MIN_ORDER_NOT_MET` wording includes the amount. `FOOD_ORDER_LIMITS.couponCodeMin` / `couponCodeMax`
(3–30) bound the code field.

Copy lives under `mweb.venueFood.*`; `FOOD_ORDER_STATUS_KEYS`, `FOOD_PAYMENT_STATUS_KEYS`,
`FOOD_DIET_KEYS` and `FOOD_SPICE_KEYS` map each enum to its key, `FOOD_SPICE_HEAT` to the number of
flames it is drawn with, and `isVegFood` answers the veg-only filter. Web renderer: mWeb's
`pages/VenueDetailsPage/food` and `pages/venue-food-order-page`.

**After the payment.** A paid order (`invoice_available`) has an invoice — the venue's own bill,
carrying the `venue_gstin` and `venue_address` the order snapshotted when it was placed:
`VENUE_FOOD_ORDER_INVOICE_QUERY` answers a base64 PDF and `foodInvoiceFileName(orderNo)` names the
file. A served order can be rated once: `canRateFoodOrder(order)` says when to show the form,
`FOOD_FEEDBACK_LIMITS` (1–5 stars, 500 characters, 3 photos) are the server's limits, each photo is
POSTed with its own single-use pass from `VENUE_FOOD_FEEDBACK_UPLOAD_PASS_MUTATION` (a guest has no
account to ask for one), and `SUBMIT_VENUE_FOOD_FEEDBACK_MUTATION` answers the order id with the
`feedback` it saved, so a cached order updates by itself.

**The events tick.** `FoodOrderDetails.subscribe` is the checkout's "tell me about events here" box;
`buildFoodOrderInput` sends `subscribe_events: true` only when it is ticked, and — like the coupon —
it is part of `foodAttemptSignature`, so ticking or unticking it is a new attempt. The server
subscribes the number once the order is paid; `order.subscribe_events` reads it back.

```ts
import { canRateFoodOrder, foodInvoiceFileName, downloadBase64File } from '@duncit/utils';

if (order.invoice_available) downloadBase64File(pdfBase64, foodInvoiceFileName(order.order_no), 'application/pdf');
const showRatingForm = canRateFoodOrder(order); // SERVED and not rated yet
```

**The table label.** Beside the A4 poster a venue can print a table label (`VENUE_TABLE_LABEL_QUERY`,
`publicPageTableLabelFileName`). `publicPageHeadlineKey(kind, offersFood)` picks what both print: a
venue with a menu (`PublicPageInsights.offers_food`) says "Scan to see the Menu & pods happening here".

**Per-table stickers — `venue-food-tables`.** A cafe lists its tables (`food_tables`): typed
(`parseFoodTables("1, 2, Patio")` — trimmed, blanks dropped, repeats kept once ignoring case) or from
a count (`foodTablesFromCount(12, limit)` → "1, 2, …, 12"). `VENUE_TABLE_STICKERS_QUERY` prints every
saved table's QR sticker in one PDF (`publicPageTableStickersFileName`); each QR opens the menu with
`?table=<label>` (`FOOD_TABLE_PARAM`), and `foodTableFromParam` turns it into the checkout's table
field (first value, trimmed, cut to `FOOD_ORDER_LIMITS.tableMax`).

**Struck-through MRP — `food-price-display`.** `foodPriceDisplay(dish)` answers `{ price,
originalPrice, saving }`: struck through only when `original_price` is a number above `price`; a
percent is rounded DOWN (never promises more than is saved) and one that rounds to 0% reads as the
amount. `foodSavingLabel(t, saving, money, 'guest' | 'owner')` words it ("20% off" / "₹40 off").
DISPLAY ONLY — the guest is always charged `price`. `FOOD_CURRENCY_QUERY` is Finance's symbol for
an owner's preview.

**Videos** live in `@duncit/forms/schemas` (`venue-videos`, because they read `@duncit/regex`).
A venue's or a dish's `videos` are uploaded clips or YouTube links in one list. `venueVideoOf(url)` reads the kind from the address (`@duncit/regex` `YOUTUBE_URL`): a
YouTube one carries its privacy-enhanced `embedUrl`, `watchUrl` and `thumbnailUrl`; a file its
`sourceUrl` (`videoSourceUrl`, never a metered re-encode). `venueVideosOf(list)` drops blanks.

## The product cart control — `cart-control`

Every product card answers one question the same way: what does this product's cart button look
like right now. A round "+" until it is in the cart; then a pill with a bin while one unit is
there, a minus from two up, the count, and a "+" that stops at the stock. This module is that
rule and nothing else — no icon, colour or copy — so the MUI control and the Tamagui one draw
the same decision.

```ts
import {
  CART_CONTROL_NOTICE_MS,
  cartControlNotice,
  cartControlState,
  stepCartQuantity,
  type CartControlLabels,
} from '@duncit/utils';

cartControlState(0, 5); // { mode: 'add', decrease: 'remove', canIncrease: true }
cartControlState(1, 5); // { mode: 'stepper', decrease: 'remove', canIncrease: true } — the bin
cartControlState(5, 5); // { mode: 'stepper', decrease: 'decrease', canIncrease: false } — "+" off
cartControlState(0, 0); // { mode: 'add', decrease: 'remove', canIncrease: false } — nothing to sell

stepCartQuantity(4, 1, 5); // 5
stepCartQuantity(5, 1, 5); // 5 — held at the stock
stepCartQuantity(1, -1, 5); // 0 — the caller removes the line

cartControlNotice(0, 1); // 'added'
cartControlNotice(1, 0); // 'removed'
cartControlNotice(2, 3); // null — the number itself says so
CART_CONTROL_NOTICE_MS; // 1600 — how long the notice stays on the card
```

A quantity or a stock that is not a whole positive number — `NaN`, a negative, a fraction read
back from storage — is floored to a whole count, never below zero, before any of the three
answers.

`CartControlLabels` is the copy a surface hands its control, already translated: `add`,
`increase`, `decrease`, `remove`, `quantity` (the count's accessible name), and the two notices
`added` and `removed`. mWeb builds it from `mweb.cartControl.*`. Web renderer:
`CartQuantityControl`, `CartControlNoticeChip` and `useCartControlNotice` in `@duncit/ui`.

## Fit a screen to the window — `fit-scale`

The login landing has to fit a phone without scrolling, on a 640px-tall window and a 900px one
alike. `fitScale` says how much the screen's design must shrink (or may grow) to fit; `fitSize`
spends that scale on one size. Only part of a screen can shrink — buttons keep their touch
target, captions their size — so `fixed` is taken out before the ratio, and the result is
clamped: under `min` text stops being readable, and a screen that still does not fit scrolls.

```ts
import { fitScale, fitSize } from '@duncit/utils';

fitScale(720, 940, 0.55, 1, 380); // 0.607 — (720 − 380) / (940 − 380)
fitScale(1000, 940, 0.55, 1, 380); // 1 — never past max
fitScale(500, 940, 0.55, 1, 380); // 0.55 — never under min; the screen scrolls
fitScale(Number.NaN, 940, 0.55, 1); // 1 — nothing to measure, the design as drawn
fitSize(40, 0.607, 28); // 28 — a heading never drops under its floor
fitSize(24, 0.607); // 15
```

The numbers a screen passes are design tokens, not literals — the auth screens read
`auth.fit` from `@duncit/auth-tokens`. Renderers: native `AuthScaffold` (`useAuthFit`, window
height minus the safe-area insets) and mWeb `AuthBackground` (the viewport height).

| Export | Signature |
| --- | --- |
| `fitScale` | `(available: number, designHeight: number, min: number, max: number, fixed?: number) => number` |
| `fitSize` | `(base: number, scale: number, floor?: number) => number` |
